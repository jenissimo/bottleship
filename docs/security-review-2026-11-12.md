### SR-01 — high — Нет авторизации доступа в комнату

**Места:** [core/src/wire.rs:190](../packages/lan-rust/core/src/wire.rs#L190), [core/src/server.rs:308](../packages/lan-rust/core/src/server.rs#L308), [src/lib.rs:551](../packages/lan-rust/src/lib.rs#L551); TS: [server.ts:82](../packages/lan/src/server.ts#L82). Политика Origin: [src/config.rs:11](../packages/lan-rust/src/config.rs#L11), [transport/src/runtime.rs:727](../packages/lan-rust/transport/src/runtime.rs#L727), [TS server.ts:50](../packages/lan/src/server.ts#L50).

Handshake проверяет формат `version/room/clientId/node`, коллизии адресов и вместимость. Он не проверяет приглашение, пароль, принадлежность к комнате или серверный токен допуска. Новый клиент выбирает собственные `clientId` и свободный `node`. Origin по умолчанию разрешён любой; даже список Origin допускает отсутствие заголовка и не является аутентификацией прямого клиента.

**Сценарий:** атакующий узнаёт или угадывает имя комнаты, подключается со своим идентификатором, получает её broadcast/multicast и отправляет пакеты игрокам на виртуальные порты. Возможны вмешательство в LAN discovery, атаки на гостевой игровой протокол и получение открытых широковещательных данных. Дополнительная аутентификация внутри конкретной игры может ограничить последствия, но не закрывает вход в виртуальную LAN.

**Проверка:** изолированные серверы приняли произвольно созданного Socket.IO-клиента с выбранной комнатой без отдельного секрета или разрешения. Изоляция *между разными именами комнат* работает.

**Фикс:** ввести серверный допуск: например, подписанное приглашение с room, сроком действия и полномочиями; для закрытых инсталляций — аутентифицированный principal и ACL комнаты. Стабильную идентичность/возобновление привязать к этому допуску. Ограничения Origin оставить дополнительной браузерной защитой.

**О сессиях:** обычный клиент создаёт `clientId` через `crypto.randomUUID()` ([relay-link.ts:70](../src/worker/net/relay-link.ts#L70)); занятый адрес нельзя заменить, зная только node, без совпадающего clientId ([server.rs:319](../packages/lan-rust/core/src/server.rs#L319)). Беспарольный вход в комнату не следует путать с доказанным угадыванием UUID чужой сессии: последнее не подтверждено.

### SR-02 — high — Gateway не разделяет полномочия участников

**Места:** [core/src/server.rs:345](../packages/lan-rust/core/src/server.rs#L345), [core/src/server.rs:588](../packages/lan-rust/core/src/server.rs#L588), [core/src/routes.rs:295](../packages/lan-rust/core/src/routes.rs#L295), [server/host.rs:112](../packages/lan-rust/core/src/server/host.rs#L112), [server/tcp_host.rs:56](../packages/lan-rust/core/src/server/tcp_host.rs#L56); TS: [server.ts:171](../packages/lan/src/server.ts#L171), [gateway.ts:331](../packages/lan/src/gateway.ts#L331). Общий лимит владельцев: [core/src/gateway.rs:125](../packages/lan-rust/core/src/gateway.rs#L125).

Routes и listener definitions общие для всех комнат. После допуска участника проверяются конфигурация назначения, lease/binding и квоты, но не право конкретной комнаты/участника использовать route или listener. Ready также раскрывает доступные адреса и идентификаторы listeners. Source-IP ACL native listener ограничивает нативных отправителей, а не того, кто получает право стать host.

**Сценарий:** внешний клиент входит в собственную комнату и отправляет трафик в разрешённый route на loopback/внутренней сети сервера. Если включён listener, он может первым занять его ограниченное число владельцев и принимать разрешённый native ingress либо мешать легитимному host. Для TCP listener это возможно и из другой комнаты. При отсутствии gateway-конфигурации этот путь выключен.

**Проверка:** на локальном Rust-сервере анонимный клиент доставил байты `[7,8,9]` через настроенный UDP route к тестовому сервису на `127.0.0.1`. Не проверялась атака на чужой реальный сервис. Это **не обход allowlist и не произвольный SSRF**: неописанные назначения отклоняются.

**Фикс:** добавить отдельные полномочия `allowedRoutes/allowedListeners` для principal/комнаты и проверять их до создания native operation. Listener lease выдавать только назначенному host. Для опубликованного gateway определить явную политику доступа, а внутренние назначения дополнительно ограничить сетевым egress firewall.

### SR-03 — high — Захват квоты комнат через reconnect grace

**Места:** [core/src/server.rs:326](../packages/lan-rust/core/src/server.rs#L326), [core/src/server.rs:1242](../packages/lan-rust/core/src/server.rs#L1242), [core/src/server.rs:1255](../packages/lan-rust/core/src/server.rs#L1255), [core/src/config.rs:27](../packages/lan-rust/core/src/config.rs#L27); TS: [server.ts:95](../packages/lan/src/server.ts#L95), [server.ts:400](../packages/lan/src/server.ts#L400).

После отключения lease сохраняется по умолчанию 60 секунд, а пустая от активных участников комната продолжает занимать `maxRooms` (128). Сохранённые leases также занимают `maxPeersPerRoom`. Ограничения на частоту создания комнат и удерживаемые offline reservations по principal/IP отсутствуют.

**Сценарий:** один атакующий последовательно создаёт 128 разных комнат и отключается. Новые комнаты легитимных игроков отклоняются, хотя активных соединений атакующего уже нет. Поддержание примерно 128 завершённых входов в минуту достаточно для повторного заполнения окна grace. Аналогично можно заполнить свободные адреса известной комнаты. Глобальный Rust `maxConnections` не останавливает последовательную атаку.

**Проверка:** на реальном Core с уменьшенным `maxRooms=2` два последовательных join/close оставили две комнаты; следующий вход в новую комнату был отклонён. Увеличивать нагрузку до производственных квот не требовалось.

**Фикс:** отделить активную вместимость от ограниченного кеша возобновления; ограничить offline reservations и создание комнат по аутентифицированному владельцу и источнику. При нехватке места освобождать неактивные комнаты по определённой политике, сохраняя защиту от присвоения активного адреса.

### SR-04 — high — Таблицы портов удерживают значительную память вне очередей

**Места:** [core/src/gateway.rs:16](../packages/lan-rust/core/src/gateway.rs#L16), [core/src/gateway.rs:58](../packages/lan-rust/core/src/gateway.rs#L58), [core/src/server.rs:664](../packages/lan-rust/core/src/server.rs#L664); TS: [gateway.ts:242](../packages/lan/src/gateway.ts#L242), [gateway.ts:285](../packages/lan/src/gateway.ts#L285), [server.ts:307](../packages/lan/src/server.ts#L307).

`releasePort` создаёт tombstone для любой допустимой пары protocol/port, даже если binding не существовал. Записи остаются до отключения участника и не учитываются в лимитах байтов очередей. Допускаются 8 × 65 535 пар, плюс отдельная таблица multicast/UDP и потенциальная копия состояния в gateway. Rust ограничивает число соединений, но не бюджет этого долговременного состояния.

**Сценарий:** клиент медленно, ниже лимита сообщений, освобождает все порты всех протоколов и держит соединение открытым. Несколько идентичностей умножают расход памяти и способны привести процесс/контейнер к OOM. Это не бесконечная утечка: пространство ключей конечно и память освобождается при отключении; имеющиеся квоты всё равно допускают опасный объём.

**Проверка:** Core принял 524 280 разных releasePort без отключения. Учёт живых выделений через диагностический allocator показал **15 335 456 дополнительных байт (~14,6 МиБ)** только в ядре одного участника, без native gateway и транспорта. При стандартных 256 участниках это теоретически **~3,66 ГиБ**; массовая нагрузка не запускалась. При 2 000 событиях/с заполнение одного участника занимает примерно 4,4 минуты.

**Фикс:** ввести малый лимит количества bindings/tombstones и общий бюджет состояния участников; резервировать его до вставки, при исчерпании прекращать работу нарушителя. Можно заменить HashMap компактной структурой с заранее учтённым бюджетом. Нельзя просто удалять старые tombstones без замены защиты от поздних пакетов: нужен безопасный epoch/отказ в новых bindings.

### SR-05 — high — TS-сервер не ограничивает соединения до namespace auth

**Места:** [TS server.ts:14](../packages/lan/src/server.ts#L14), [server.ts:53](../packages/lan/src/server.ts#L53), [server.ts:82](../packages/lan/src/server.ts#L82). В Rust соответствующие ограничения есть: [src/config.rs:41](../packages/lan-rust/src/config.rs#L41), [transport/src/runtime.rs:813](../packages/lan-rust/transport/src/runtime.rs#L813), [transport/src/runtime.rs:834](../packages/lan-rust/transport/src/runtime.rs#L834).

TS ограничивает комнаты/участников после Socket.IO auth, но не число принятых TCP/Engine.IO-соединений и незавершённых namespace handshakes. Тайм-аут библиотеки завершает отдельные зависшие подключения, но не задаёт общий предел одновременно созданных ресурсов.

**Сценарий:** внешний атакующий создаёт много Engine.IO WebSocket/polling sessions и не присылает Socket.IO connect/auth, непрерывно заменяя истёкшие подключения. Потребляются сокеты, память и heartbeat-таймеры независимо от `maxRooms/maxPeersPerRoom`.

**Проверка:** при общей вместимости комнаты 2 участника четыре независимых WebSocket Engine.IO sessions без namespace auth одновременно оставались открытыми (`engine.clientsCount=4`). Исчерпание ресурсов не выполнялось.

**Фикс:** не публиковать TS reference как интернет-сервис без дополнительного admission control; добавить общий лимит TCP, Engine.IO sessions, pending auth и квоты по источнику до создания session. Тестировать также освобождение квот после тайм-аутов и upgrade. Предпочтение Rust из документации уменьшает область этой находки, но `dev:lan` по-прежнему запускает TS.

### SR-06 — medium — Rate limit не охватывает все сообщения

**Места:** [core/src/server.rs:414](../packages/lan-rust/core/src/server.rs#L414), [core/src/server.rs:681](../packages/lan-rust/core/src/server.rs#L681), [core/src/server.rs:731](../packages/lan-rust/core/src/server.rs#L731), [core/src/wire.rs:542](../packages/lan-rust/core/src/wire.rs#L542); TS: [server.ts:291](../packages/lan/src/server.ts#L291), [server.ts:304](../packages/lan/src/server.ts#L304). DNS execution: [src/lib.rs:344](../packages/lan-rust/src/lib.rs#L344), [src/lib.rs:381](../packages/lan-rust/src/lib.rs#L381).

`resolve/cancelResolve` не проходят через `rate/withinLimits`. В Rust malformed resolve с допустимым id сразу генерирует ошибку; неизвестные события также игнорируются без временного лимита. Ограничение 16 pending DNS и бюджеты очередей ограничивают одновременно удерживаемые объекты, но не число дешёвых завершённых операций в секунду.

**Сценарий:** клиент непрерывно отправляет неизвестные/некорректные имена и получает сериализованные ответы, расходуя CPU/полосу без списания прикладной квоты. Для настроенных DNS routes он может постоянно занимать resolver permits и создавать повторные OS lookups; произвольные внешние имена через DNS не разрешаются.

**Проверка:** при `maxFramesPerSecond=1` оба реальных сервера ответили на 20 DNS-событий в коротком burst и сохранили соединение. Дополнительно Core выдал 100 ответов с одной временной меткой при той же квоте.

**Фикс:** учитывать все входящие application events, включая неизвестные и ошибки, до dispatch/декодирования прикладной нагрузки. Для DNS добавить отдельный token bucket и кеш/объединение запросов на настроенный host. Сохранить существующие глобальные resolver permits и владение ими до завершения OS call: это полезная уже реализованная защита от cancel/retry.

### SR-07 — medium — Некорректный Socket.IO-заголовок вызывает panic

**Места:** [transport/src/codec.rs:30](../packages/lan-rust/transport/src/codec.rs#L30), [transport/src/runtime.rs:596](../packages/lan-rust/transport/src/runtime.rs#L596), [vendor/engineioxide/src/transport/ws.rs:228](../packages/lan-rust/transport/vendor/engineioxide/src/transport/ws.rs#L228).

Парсер берёт первый байт, затем делает `&s[1..]` до проверки ASCII-типа пакета. Для строки, начинающейся с многобайтного Unicode-символа, индекс 1 находится внутри UTF-8 code point.

**Сценарий:** неаутентифицированный клиент открывает Engine.IO WebSocket и отправляет текст `4é`: Engine.IO снимает префикс message `4`, а Socket.IO codec получает `é` и паникует вместо штатного отказа. Повторы аварийно завершают обработчики и засоряют panic-лог; при сборке с panic=abort последствия распространяются на процесс.

**Проверка:** panic воспроизведён напрямую через настоящий codec и по сети на локальном Rust-сервере. В использованной стандартной сборке сервер продолжил отвечать и штатно завершился с кодом 0. **Падение всего процесса в стандартной конфигурации не заявляется.**

**Фикс:** сначала проверить ASCII discriminator через bytes/split_first и разрешённый набор типов, затем безопасно отделять оставшуюся строку. Любой неверный заголовок должен возвращать CodecError. Проверки добавить для Unicode первого символа и случайных корректных UTF-8 строк на WebSocket и polling.

### SR-08 — medium — Надёжный флуд отключает получателя

**Места:** [core/src/server.rs:440](../packages/lan-rust/core/src/server.rs#L440), [core/src/server.rs:644](../packages/lan-rust/core/src/server.rs#L644), [transport/src/runtime.rs:319](../packages/lan-rust/transport/src/runtime.rs#L319); TS: [server.ts:379](../packages/lan/src/server.ts#L379).

Если reliable output не помещается в очередь получателя, сервер отключает и получателя, и отправителя. Квота общая для получателя, а стоимость конкретного источника не изолирована. Эта политика обеспечивает явный отказ надёжного транспорта, но позволяет одному злонамеренному источнику закрыть всю relay-сессию другого игрока.

**Сценарий:** участник шлёт небольшие DirectPlay/TCP frames медленному игроку быстрее, чем тот опустошает очередь, оставаясь ниже собственной входящей квоты. При превышении 64 frames/1 МиБ по умолчанию закрывается соединение жертвы вместе с её остальными игровыми потоками. Повторный вход атакующего позволяет повторять воздействие.

**Проверка:** на TS с уменьшенной очередью 2 frames polling-получатель после handshake временно не делал новые GET. Burst из 10 DirectPlay frames отключил оба namespace; у жертвы `connected=false`, и её Socket.IO socket удалён из namespace. Для Rust подтверждён такой же явный путь `DeliveryRejected` по коду; отдельное сетевое воспроизведение переполнения Rust не выполнялось.

**Фикс:** ограничить вклад каждого отправителя в очередь адресата до общей перегрузки; при злоупотреблении отключать источник. При невозможности надёжной доставки завершать конкретный виртуальный поток с ошибкой/противодавлением, не разрывая весь relay получателя. Нельзя просто молча выбрасывать reliable frames.

### SR-09 — low — Tokio 1.53.2 попадает под RUSTSEC-2026-0386

**Места:** [Cargo.lock:554](../packages/lan-rust/Cargo.lock#L554), [Cargo.toml:20](../packages/lan-rust/Cargo.toml#L20), [native/Cargo.toml:14](../packages/lan-rust/native/Cargo.toml#L14), [gateway/Cargo.toml:13](../packages/lan-rust/gateway/Cargo.toml#L13), [transport/Cargo.toml:14](../packages/lan-rust/transport/Cargo.toml#L14).

OSV на дату проверки возвращает [RUSTSEC-2026-0386](https://rustsec.org/advisories/RUSTSEC-2026-0386.html): safe-конструкторы Unix AsyncFd допускают некорректное владение descriptor, что при его закрытии/повторном использовании может привести к use-after-free в I/O driver. Зафиксированная версия 1.53.2 затронута; исправлена ветка 1.53.3, также исправления есть в 1.51.6 и 1.54.0.

**Сценарий и применимость:** опасность возникает в Unix-коде, использующем AsyncFd с невалидным/заменённым fd. Прямого использования AsyncFd/AsRawFd в просмотренном коде сервера не найдено; на Windows проверяемого устройства этот Unix API неприменим. Удалённая эксплуатация игроком не доказана. Поэтому это low для данного проекта, а не утверждение о доступном RCE.

**Фикс:** синхронно обновить точные Tokio pins во всех четырёх crate manifests и lock-файлы минимум до совместимого исправленного релиза 1.53.3, проверить upstream migration notes и прогнать сетевые/native тесты на Windows и целевой Unix-платформе. В этом ревью обновление не выполнялось.

## Доверие клиенту и читы

### ARC-01 — условный medium — Relay не проверяет игровое состояние

**Места:** [core/src/server.rs:638](../packages/lan-rust/core/src/server.rs#L638), [core/src/server.rs:646](../packages/lan-rust/core/src/server.rs#L646), [TS server.ts:371](../packages/lan/src/server.ts#L371), [TS server.ts:387](../packages/lan/src/server.ts#L387).

Проверяются оболочка, адреса, порты, размеры и часть транспортных состояний. Координаты, время движения, скорость, урон, попадания, здоровье, инвентарь и ресурсы здесь не декодируются и не рассчитываются. Payload проходит к игровому host/peer без игровой валидации.

**Сценарий:** если конкретная игра доверяет клиентскому сообщению о координате, уроне или ресурсах, модифицированный клиент передаёт завышенное значение внутри допустимого LAN frame, и relay его пересылает. Телепорт, speed hack, подмена урона/ресурсов должны отклоняться самой авторитетной игровой стороной. Ни один такой чит в конкретном игровом протоколе в рамках этой проверки не воспроизводился.

**Решение:** для состязательной игры нужен авторитетный игровой host/server, рассчитывающий движение по серверному времени, столкновения, попадания/урон и операции с ресурсами, с проверкой принадлежности сущностей и последовательности действий. Для legacy peer-to-peer игр следует явно считать участников доверенными или применять специализированный сервер/проверку конкретного протокола. Универсальный LAN relay не даёт гарантии защиты от читов. ARC-01 — ограничение архитектуры относительно запроса, а не десятая доказанная уязвимость конкретной игры.

## Зависимости и выполненные проверки

OSV API проверен через querybatch/query с точными версиями из lock-файлов: 63 registry packages основного Cargo.lock, одна дополнительная версия libc из lock-файлов подcrate, локальная Engineioxide 0.17.7 отдельно и 24 версии JS-пакетов в дереве socket.io/socket.io-client. Найден только SR-09; для остальных запрошенных версий OSV вернул пустые результаты. Это результат базы на дату обращения, а не гарантия безопасности, особенно для локально изменённой Engineioxide.

Ключевые JS-версии: socket.io/socket.io-client 4.8.4, engine.io 6.6.11, engine.io-parser 5.2.3, socket.io-parser 4.2.7, ws 8.21.3, cookie 0.7.2. Источник и изменения vendored Engineioxide описаны в [UPSTREAM.md:3](../packages/lan-rust/transport/vendor/UPSTREAM.md#L3). Dev/build зависимости всего эмулятора и зависимости ОС не включены в этот результат.

Выполнено:

- `bun test ./packages/lan/test`: **34 pass, 0 fail**, 463 assertions.
- Штатный `cargo test --offline --locked --manifest-path packages/lan-rust/Cargo.toml` с отдельным target directory остановился на **MSVC LNK1318 (PDB FILE_SYSTEM)**, не на тестовой проверке.
- После компиляции того же root test module через rustc с существующими библиотеками и `/DEBUG:NONE`: **5 pass, 0 fail**. Это root unit tests, не полный cargo test всех подcrate/integration suites.
- Диагностические проверки использовали текущий Core/codec и реально связанные библиотеки сервера; код подавался компилятору/интерпретатору через stdin, исходники проекта не редактировались.
- На loopback подтверждены анонимный gateway UDP, DNS rate bypass в обоих серверах, сетевой Unicode panic Rust, pre-auth Engine.IO sessions TS и отключение медленного получателя TS.
- Отдельно на Core подтверждены сохранение квоты offline-комнат и размер удерживаемых таблиц bindings. Нагрузка с сотнями клиентов/OOM не запускалась.
- Собственные тестовые серверы завершены; существовавшие процессы разработки не останавливались. Публикации, деплоя и отправки отчёта третьим лицам не было.
