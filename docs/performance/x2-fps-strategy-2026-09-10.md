# Стратегия x2 FPS на NFSU, generic-фиксами

Дата: 2026-09-10. Основание — трасса живой гонки с атрибуцией на гостевые блоки
(`logs/nfsu-race-12s.json.gz`, 534k событий, метка `bottleship.hotblocks` внутри окна),
цензус классов инструкций в той же гонке (покрытие 99.51%) и парные замеры на
codegen-паре. Все числа ниже измерены, а не оценены; где оценка — сказано.

## Что показала трасса

Idle — не резерв: `--idle-shape` даёт «90% простоев длиной 1–5 сэмплов, зажаты WASM/JIT
кадрами → шум сэмплирования вокруг динарека». Планировать возврат этого времени нельзя.
Значит x2 FPS = ровно вдвое меньше BUSY.

| Бакет | % busy | Чей |
| --- | ---: | --- |
| JS HLE + glue | **40.4** | наш |
| код игры (JIT-блоки) | **33.6** | гостевой |
| наш HLE (wasm-гиперколлы) | 10.4 | наш |
| прочее ядро v86 | 6.9 | v86 |
| mmu / decode / irq | 3.7 | v86 |
| indirect-jump (jit cache) | 1.9 | v86 |
| sse primitives | 1.3 | v86 |
| интерпретатор, OUT-трап, dispatch | 1.6 | смешанно |

Наше в сумме — 51.3%. Это опровергает читавшуюся ранее долю «92.5% v86 residual»:
категория `v86` в perfStats означает «всё, что не под таймером thunk'а», и включает
гиперколлы, OUT-трап и glue.

## Почему это не задача одного рычага

| Убрать бакет ЦЕЛИКОМ | FPS |
| --- | ---: |
| весь JS HLE + glue | x1.68 |
| весь гостевой код | x1.51 |
| все гиперколлы | x1.12 |

Ни один трек в одиночку до x2 не дотягивает даже в пределе. Рабочий сценарий:

| Сценарий | JS | гость | гиперколлы | ядро | FPS |
| --- | ---: | ---: | ---: | ---: | ---: |
| осторожный | −50% | −50% | −30% | −20% | x1.75 |
| **рабочий** | **−60%** | **−50%** | **−50%** | **−30%** | **x2.01** |
| целевой | −75% | −50% | −50% | −30% | x2.29 |

Отсюда порядок: сначала самый большой и наименее рискованный бакет (наш JS), затем
гиперколлы, затем кодогенерация. Гость обязателен — без его −50% x2 не собирается.

## Этап 0. Инструменты (без них любой порядок — гадание)

1. **Side-channel эмиттера**: на модуль — таблица `{EIP, длина, диапазоны байт}` с
   категориями (guard, трансляция, кортеж флагов, спилл/перезагрузка, счётчик, диспетчер,
   полезная нагрузка). Самопроверка: сумма диапазонов = длина тела, без перекрытий.
   Без него разложение гостевого бакета невозможно.
2. **Per-draw accounting** в D3D9-бэкенде: draws/кадр, констант-слов/кадр, bind-group и
   pipeline-переключений/кадр. Потолок любого draw-рычага = удельная экономия × эта частота.
3. **Абляционные руки как рантайм-флаги** (шаблон `set_stack_raw_unsafe`): переключаемые
   посекундно, с readback и отказом в production-сборке. Только они дают парный замер
   ВНУТРИ одной загрузки — стенд иначе не разрешает единицы процентов (разброс до 12%).

## Этап 1. JS HLE + glue, 40.4% — самый большой и самый дешёвый по риску

Из трассы (self, % busy): `copyProgrammableBankWithKey` 4.7, `captureDrawState` 2.1,
`drawIndexedPrimitive` 1.7, `setBindGroup` 0.7, `resolveProgrammablePipeline` 0.6,
`setVertexShaderConstantFFromWbufRing` 0.6, `writeProgrammableConstants` 0.4,
`writeShadowSlot` 0.4, `writeBuffer` 0.7. Выше по стеку `handlePortWrite` 27.4% total при
0.7% self — сама граница thunk'а дёшева, дорого то, что она вызывает.

Механизмы:

1. **Версия банка констант ведётся на записи, а не пересчитывается на draw.** Сегодня
   `captureDrawState` копирует весь банк (`state.vsBits.set(...)`) и прогоняет его словом за
   словом с двумя `Math.imul` на слово — отдельно VS и PS, БЕЗ проверки «менялось ли»
   (флага dirty в файле нет). Инкрементальная версия на путях записи убирает и копию, и хеш.
2. **Ключи состояния инвалидируются на записи**, а не пересобираются на draw
   (`refreshStateKeys`, `resolveProgrammablePipeline`).
3. **Bind-group и pipeline по кэшу состояния**, а не по draw (см. память
   `d3d9-ffp-bindgroup-per-draw`: кэшированный shared-layout путь выключен, потому что
   рендерил не ту текстуру — это долг, а не отсутствие идеи).
4. **Батчинг uniform-загрузок** вместо `writeBuffer` на draw.

Generic: всё это слой D3D8/D3D9, общий для каждой игры на нём; ни строчки про NFSU.

## Этап 2. Гиперколлы, 10.4%

В трассе `hypercall_eagl16eagl_read32_cold` встречается ТРИЖДЫ в топ-30 и 125 раз в
брекетах вокруг idle. Имя говорит «cold», а частота — «hot»: первый вопрос, почему
холодный путь берётся постоянно, и что должно было его обойти. Рядом `eagl_class6_bind`
(0.9%), `eagl_apply_walk`, `eagl_dispatch_token`, `eagl_emit_state`.

## Этап 3. Кодогенерация, 33.6% — обязательна, но потолок трека x1.51

Разрыв с нативом измерен НАКЛОНОМ (одиночный замер на 41% состоит из прогрева):
**12.75x** на k3. По семействам: целочисленный код 10–13x, x87 63x.

Порядок внутри этапа — по доле на единицу риска:

1. **Представление флагов.** В `cgk3.wat` 67 записей кортежа на 64 инструкции x86 — больше
   одной на инструкцию, и это крупнее и guard'ов, и регистровых сбросов (32). Семантика не
   требует НИ ОДНОЙ записи в память: только материализация на выходах и перед хелпером,
   который их читает. Не трогает MMU. Рычаг idx21 существует и выключен.
2. **Переиспользование проверки памяти** для доказанно той же страницы внутри блока.
   Потолок по уже измеренной цене проверки (0.51–1.17 нс): 1.3–1.7x на k3, не больше.
   ВАЖНО: read micro-TLB измерен как **−9.8%** при 49.6% попаданий — предикат ПЕРЕД той же
   цепочкой её не убирает. Годится только форма, которая цепочку удаляет.
3. **Регионы и границы модулей.** k1 исполняется через ≥3 модуля, каждое ребро — сброс 8
   регистров, счётчик, dynamic-chaining, перезагрузка на входе.
4. **x87.** Доля измерена в кадре: relaxed-FPU (3.1x на ядре) даёт в гонке 14.44 → 17.12 FPS,
   отсюда x87 = **8.9% времени кадра** (цензус независимо: 8.82% инструкций). Доведение x87
   до целочисленного пути = **+7.6% FPS**. Делать после 1–3.

## Протокол приёмки (одинаковый для всех этапов)

- Потолок считается ДО постройки: удельная экономия × измеренная частота в игре.
  Ниже разрешения стенда — не строить (так закрыт WBUF: 0.11% кадра).
- Разрыв — только НАКЛОНОМ по двум объёмам работы.
- Рычаг переключаемый в рантайме → парные окна ВНУТРИ одной загрузки, ABBA, сброс кэша и
  прогрев на каждом переключении, проверки сцены/presents/физики на каждом окне.
- Контрольная сумма состояния обязана совпасть: более быстрая рука, сделавшая меньше
  работы, — не более быстрая.
- A/A контроль в том же прогоне; результат внутри шума — направленный, не принятый.

## Чем стратегия фальсифицируется

- Частоты взяты из ОДНОЙ 12-секундной трассы одной сцены. Другая сцена (город, трафик,
  меню) может дать другой профиль — этап 0.2 обязан их перемерить.
- Если после этапа 1 доля JS не падает соразмерно снятым механизмам — узкое место не в
  перечисленных функциях, а в том, что их вызывает (число draw-вызовов), и тогда цель
  меняется на сокращение draw'ов, а не их удешевление.
- Если гостевой бакет не поддаётся −50% — x2 недостижим этим набором, и честный результат
  x1.7, а не подгонка протокола.

## Что сделано и измерено (первая итерация этапа 1)

**Landed: блочный хеш банка констант** (`d3d9-device.ts`). Хеш содержимого остаётся ключом
дедупликации загрузок uniform'ов, но считается по блокам в 16 слов, кэш инвалидируется в
единственной точке записи, а целочисленный банк (64 слова на КАЖДЫЙ draw при i#, которые почти
не меняются) кэшируется целиком. Копирование банка переведено на `.set()`.

| | Было | Стало |
| --- | ---: | ---: |
| `copyProgrammableBankWithKey`, self | 4.7% busy | **1.0%** |
| Слов хешируется на кадр | 336 819 | **81 157** |
| Бакет JS HLE + glue | 40.4% | **35.6%** |
| Гостевой код (контроль) | 33.6% | 34.0% |
| progConstWrites / ReuseHits (контроль) | 977 / 2845 | 976 / 2839 |

Корректность: дифференциальная проверка (`__d3d9VerifyBankHash`) в живой гонке — **0
расхождений**; 970 d3d9-тестов и валидаторы зелёные.

**Отрицательный результат по методике измерения.** Три парных in-boot замера ЭТОГО ЖЕ рычага
дали 1.11, 0.83 и 1.005 при абсолютном уровне стенда 14 → 19 → 22 FPS между прогонами. Первый
«+28.6%» разобран: медленными были позиции 1 и 6, а порядок `0,1,1,0,1,0` отдал руке B центр —
это дрейф, совпавший с раскладкой. **Изменение в ~4% busy стенд в FPS не разрешает даже с
чередованием внутри загрузки.** Такие изменения принимаются по ТРАССЕ (доля функции + контроль
на неизменность downstream-счётчиков) и копятся до величины, превышающей шум.

## Почему JS-бакет широкий: батчинг простаивает целиком

Измерено в гонке: **2066 draws/кадр при 167 сменах pipeline**, и при этом

| | На кадр |
| --- | ---: |
| renderBundleHits / Misses | 0 / 0 |
| megaBatchBatches / Fallbacks | 0 / 0 |
| WBUF pairRuns / pairs / pairFallbacks | 0 / 0 / 0 |

Ноль и попаданий, и отказов — код не пытается. Причина: зарегистрирована ОДНА связка
`SetVertexShaderConstantF → DrawIndexedPrimitive` со строгим чередованием, а реальный поток на
кольце — иной:

| Вызов | На кадр | На draw | Избыточных |
| --- | ---: | ---: | ---: |
| SetVertexShaderConstantF | 7998 | 3.9 | **71%** |
| SetTexture | 3458 | 1.7 | 45% |
| SetVertexShader | 2093 | 1.0 | 49% |
| SetPixelShader | 2093 | 1.0 | 49% |
| DrawIndexedPrimitive | 2067 | 1 | — |
| SetPixelShaderConstantF | 950 | 0.5 | **86%** |

Шаблон «одна константа → один draw» не встречается ни разу, поэтому вся машинерия батчинга
инертна. Это единственный рычаг нужного для x2 масштаба: он снимает не одну функцию, а весь
per-draw путь для двух тысяч вызовов.

**Проверено и отклонено по дороге:** `__d3d9PtrShadow` (тени для SetVertexShader/SetPixelShader/
SetTexture, 7644 вызова на кадр, ~47% избыточны). Записанный в коде блокер — «guest OOB в
apply_reg_int» — НЕ воспроизвёлся: игра грузится и гоняется. Но и выигрыша нет: соотношения на
кольце не изменились (SetTexture/Draw 1.674 против 1.673), потому что тени **инертны на пути
EAGL**, а NFSU идёт именно через него (в трассе `eagl_class6_bind`, `eagl_apply_walk`,
`eagl_dispatch_token`). Чтобы это заработало, теневые таблицы EAGL должны покрыть COM-указатели —
это работа в `hypercall_eagl.rs` + дескрипторе, а не флаг.

## Стенд имеет медленный множитель ±30%, и это обесценило часть моих отказов

94 валидных окна, разложенные по времени, дают не шум, а полки:

```
15.7 15.5 16.0 | 20.6 21.3 20.8 20.5 | 14.2 13.9 14.3 13.9 14.0 14.0 14.3 13.9 14.0 14.3 |
18.1 19.2 19.4 19.3 19.5 18.8 18.7 | 20.3 20.7 20.5 21.9 21.9 21.8 21.9 22.1
```

Десять подряд окон на 14.0, потом девять на 19, потом восемь на 21 — при ИДЕНТИЧНОЙ работе на
кадр (progConstWrites 977 против 979, memoMisses 1936 против 1942, pipelineSets 167 в обоих
режимах). Характерное время полки — около пяти минут, то есть длиннее квартета ABBA: весь
квартет попадает в одну полку, и чередование не спасает.

**Следствие: любой отказ, вынесенный по 3–6 окнам в игре, недействителен.** Проверено на
idx21 (флаг-локали): в игре 0.9955 на трёх окнах, на фиксированной работе демки — **−12.5%**
(317 → 277.5 мс, руки 314/319/335/315 против 278/277/281/275, суммы совпали).

Единственный инструмент, который разрешает единицы процентов, — демка с фиксированной работой
(спред 3–6%). Игровой стенд годится только для эффектов больше ~30% либо при 30+ окнах на руку.

## Что осталось, по убыванию отдачи

1. **Калибратор в игре**: эталонная фиксированная нагрузка внутри того же окна, чтобы делить на
   полку. Без него ни один следующий рычаг нельзя ни принять, ни отклонить.
2. **Редизайн per-draw пути**: 2066 draw'ов по 12.8 мкс нашего JS, ни одна функция не весит
   больше 2% — это не набор фиксов.
3. **Флаги в локалях с liveness** сверх idx21: потолок абляции уже почти достигнут idx21 на
   ALU-коде, но на call-плотном (k1) осталось 10 из 12.6 пунктов.

## Чистый стенд и первый реальный рычаг: guard'ы памяти = +10% кадра

Ключевая поправка к предыдущим разделам: **все игровые вердикты выше вынесены на грязном
стенде**. В том же Chrome была открыта вторая вкладка с codegen-бенчем, то есть второй гость
делил CPU. `CLAUDE.md` требует одной вкладки для замеров; правило было нарушено.

После закрытия вкладки и перезапуска Chrome стенд стоит намертво: одиннадцать окон подряд
22.97–23.17 FPS, **разброс 0.9%**, калибратор 1.55–1.58 мс. «Полки» 14→22 были контаминацией,
а не хостом.

Перемерено начисто (16 окон, чередование, калибратор):

| Рычаг | Ratio | Вердикт |
| --- | ---: | --- |
| Блочный кэш хеша банка констант | 0.999 | ноль |
| idx21, флаг-локали | 0.991 | ноль (в игре), при −12.5% на ALU-ядре демки |
| EAGL 4-way курсор | 0.994 | ноль |
| fastmem writes (idx19) | 0.970 | ХУЖЕ на 3% |
| **Элизия guard'ов памяти** | | |
| … только flat 32-битные чтения (mode 2) | **1.0594** | +5.9% |
| … + 8/16-битные чтения | **1.0732** | +7.3% |
| … + записи | 1.0735 | записи не весят ничего |
| … + все чтения, включая POP/строковые (mode 3) | **1.0913** | +9.1% |
| … + read-modify-write | **1.1006** | **+10.1%** |
| … + абляция кортежа флагов сверху | — | 15 окон из 16 отклонены: ломает гостя |

**Guard'ы памяти стоят 10% кадра** — это единственный крупный рычаг, найденный за всю работу, и
он нашёлся только после починки стенда. Элизия НЕ шиппится: она убирает страничный отказ и бит
HAS_CODE. Это потолок, на который должен целиться БЕЗОПАСНЫЙ механизм (permission bitmap из
roadmap 03 или переиспользование доказанной страницы).

Дополнительно измерено: записи в кадре не весят (та же цифра с ними и без), а вся стоимость
сидит на чтениях; и штатный write-map (idx19) не просто не помогает, а отнимает 3%.

## Потолок кадра измерен: +28%, и он разложен на два слагаемых

Абляции на чистом стенде (16 окон, чередование, калибратор, ноль отклонённых):

| Что снято | FPS | Ratio |
| --- | --- | ---: |
| guard'ы всех гостевых обращений к памяти | 22.97 → 25.29 | **1.1006** |
| весь per-draw путь сборки состояния в JS (`__d3d9ForceCaptureMemo`) | 22.37 → 25.26 | **1.1291** |
| **оба вместе** | **22.39 → 28.67** | **1.2804** |

Сумма СВЕРХаддитивна (10.1% и 12.9% дают 28%, а не 23%): снятие обеих статей укорачивает
критический путь кадра, а не просто вычитает две доли.

**Это потолок, не результат.** Обе абляции рисуют неверно, и это проверено глазами, а не
предположено: `logs/capmemo-on.png` против `logs/capmemo-off.png` — розовые кляксы по машине,
белые артефакты, пропавшие элементы HUD. Проверки сцены (физика, presents, raceState) этого не
видят, поэтому одних их для приёмки НЕДОСТАТОЧНО.

Что отсюда следует для инженерной работы:

1. **Per-draw путь JS — 12.9% кадра.** Memo `captureDrawState` попадает в 6.3% случаев, при
   этом 68% draw'ов отличаются от предыдущего ТОЛЬКО константами (счётчик `captureConstOnly`).
   Безопасный ярус «тот же материал, другие константы» забирает бóльшую часть этих 12.9%.
2. **Guard'ы памяти — 10.1% кадра**, целиком на чтениях (записи не весят). Безопасная форма —
   permission bitmap (roadmap 03) или переиспользование доказанной страницы; важно, что форма
   должна цепочку УДАЛЯТЬ: read micro-TLB добавлял предикат перед той же цепочкой и дал −9.8%.

## Безопасных форм для guard-выигрыша в движке НЕТ: обе существующие проигрывают

| Механизм | Ratio (чистый стенд, 16 окон) |
| --- | ---: |
| read micro-TLB (idx 29/30) | 0.902 |
| permission bitmap на чтениях (`set_perm_map_reads`) | **0.9626** |
| элизия guard'а целиком (ceiling, небезопасно) | **1.1006** |

Обе реализованные «безопасные» формы ставят предикат ПЕРЕД той же цепочкой и потому теряют
3.7% и 9.8%. Комментарий в `codegen.rs` про perm-map фиксирует ту же природу: «восемь процентов
выигрыша на разреженном обходе превращаются в четыре процента потери на плотном».

Вывод для инженерной работы: 10.1% headroom на guard'ах существует, но взять его нельзя ни одним
из имеющихся механизмов. Нужна форма, которая цепочку УДАЛЯЕТ, а не предваряет — то есть
доказательство страницы на уровне ЭМИТТЕРА (одна проверка на регион без смены TLB, с
инвалидацией на выходах), а не рантайм-предикат на каждый доступ.
