## 2. Что уже исключено из нового резерва по коду

Проверены не только названия старых оптимизаций, но и действующие ветви:

- `d3d9-pipeline-memo.ts`: prologue memo по умолчанию включён. Новый «кэш pipeline»
  без указания пропущенного им расхода не является гипотезой.
- `d3d9-device.ts:10313`: `captureDrawState` уже возвращает прежний slot при совпадении
  **всех** поколений. Одинаковые последовательные draw-state уже переиспользуются.
- `d3d9-device.ts:10310`: `compactCaptureCache` уже хранит шаблоны внутри кадра,
  исключая гарантированно перезаписываемый VS-prefix из идентичности.
- `d3d9-backend-executor.ts:822`: MegaBatch, fusion и compact по умолчанию включены.
- Rust `crates/d3d9-webgpu/src/arena.rs:996`: storage-ready режим уже разворачивает
  полный шаблон в Wasm; повторное предложение «перенести упаковку JS → Wasm» закрыто.
- `d3d9-backend-executor.ts:5496`: VS/PS upload уже имеет отдельный кэш по bank key
  и длине. Повторный **capture/hash до этого кэша** — другой расход.
- `d3d9-command-recorder.ts:348` и `d3d9-device.ts:11066`: завершённый RenderFrame
  существует, но его executor выполняется синхронно на том же worker.

Draw-front через текущую арену, frame-scoped encoder, обычный RenderBundle,
EAGL handler 133, общие direct chains, inline memory и MAX_PAGES=1 не перезапускались.

### Отсев по потолку

Для +20% нужно убрать 1/6 исходного критического времени; здесь около 10 мс из 60.
Даже полное исчезновение executor даёт лишь около 5,2% в идеальной последовательной
модели этого trace. Исчезновение всей copy/hash области — около 1,3%; это включает
оба банка, а ненужный первый PS hash — только часть. Capture целиком — около 5,3%.
Поэтому ни один из этих трёх расходов отдельно не обосновывает работу ради +20%.

Двукратное ускорение **всего** графического пути при его исторических долях 15–25%
даёт лишь 8–14% в той же модели. Это ориентир для отказа от слишком узкого механизма,
не математически доказанный потолок текущей max-сборки: sampled time не равно
устранимой части критического пути. Большой кандидат должен затронуть несколько
независимых расходов либо изменить перекрытие работы; его запас нужно измерить заново.

## 4. Пять гипотез после исторического screen

Здесь «есть расход» означает доказанный путь в коде, **не доказанную заметную цену**.
`T` — чистое время кадра новой контрольной сборки, `p` — устранимая доля его
критического пути. Для текущей max-сборки каждая доля пока неизвестна. Для +20% необходимо снять `T/6`;
даже двукратное ускорение участка требует `p >= 1/3`.

### Контракты и риски

**Журнал scan/replay.** `vendor/v86/src/rust/cpu/hypercall_eagl.rs:1301` вызывает
`eagl_dispatch_token` дважды. `EaglPass` уже моделирует до 64 изменённых cells,
поскольку ранние shadow writes могут влиять на дальнейшие решения в том же вызове.
Это конкретная повторная работа действующего handler 132, не повтор handler 133,
полной подмены EAGL, read cursor либо inline memory experiment.

Кандидат должен сохранить порядок ring bytes, shadow updates и skip counters,
HRESULT при частичном отрицательном результате, EAX, единственную публикацию head,
границы завершённых entries, поведение faults и отсутствие записей при scan decline.
Guest не исполняется между проходами, но commit сам пишет память: отсутствие aliases
к исходным metadata/payload нужно доказать, а не предположить. При model overflow,
перекрытии входов с записываемыми диапазонами или недостаточном журнале — исходный путь
до каких-либо записей. Не переносить unsafe/pointer lifetime через yield.

Существующий `eagl-token-dispatch.test.ts` проверяет x86 filter/routing; он **не является**
дифференциальным тестом Rust class6 replay. Для кандидата нужен реальный handler oracle:
alias node, повторная запись shadow и возврат к прежнему значению, 65-й cell,
page-crossing constants, subpass recursion, mode 2, неподдержанный I/B, недостаточный
ring, неизвестный тип PS после уже выполненного bind, пересечение payload с writes.
В текущей сессии runtime-кандидат не создан и FPS-эффект этой гипотезы не измерен.

**Раздельные банки.** PS identity включает shader/layout, c/i/b, fog, legacy bump,
hybrid FFP и длину. Нельзя использовать только `psConstantsVersion`: fog/bump могут
измениться отдельно. Snapshot неизменяем до потребления; сброс/рециклинг frame pool
и смена pipeline layout разрывают допустимость ссылки. Начать с удаления первой
ненужной арифметики проще, чем сразу менять владение банками. Полный финальный hash
и байты сравнивать с неизменённой контрольной реализацией.

**Другой worker.** Нынешний RenderFrame содержит GPU-объекты и views в переиспользуемую
Wasm-арену. Простого `postMessage(frame)` здесь недостаточно. Нужны принадлежащие
потребителю ресурсы с числовыми handles/generations, собственный неизменяемый payload,
bounded queue и явные барьеры. Нельзя скрыть стоимость копий или увеличить задержку
за счёт бесконечного render-ahead. Сохраняются COM lifetime, reset/device loss,
GetData/readback/Lock, порядок RT passes, overlays и present serials.

Идеальный предел конвейера: последовательные `G + R` становятся `max(G, R)`;
реально добавляются передача и синхронизация. Это модель, не измерение. CPU-время
CrGpuMain уже перекрывается с worker и повторно из `T` не вычитается.

**Sparse GPU banks.** Все значения передаются как исходные u32, включая NaN payload,
signed integer registers, Boolean bank, pixel-centre/point/clip sidecars. Нужна
корректность относительной адресации c[]. Порядок blending/depth/query и число
логических draw сохраняются; старый compact OFF с потерей prefix draw не контроль.

**Селективные барьеры.** Сначала доказательство независимости конкретного API.
Ресурсные refcounts, чтения guest memory, thread switch, async callbacks, state blocks,
ошибки и overflow могут требовать немедленного drain. Квант и виртуальное время
не меняются. Это не повтор Tier-0-фильтра EAGL: он уже входит в контроль.

## 5. Что измерить первым после освобождения машины

1. Обнаружить targets заново, проверить отсутствие другого активного гостя на всех
   известных CDP endpoints; согласованно приостановленный WWP сохранить для resume.
2. Новый NFSU на `fixtures/nfsu-max`; readback пяти файлов, эффектов и shipping flags,
   `idx21=0`; screenshot пилотной сцены. Извлечь загруженные JS/Wasm bytes отдельно
   от таймингов. Проверить source drift относительно snapshot до каждого запуска.
3. Три независимых A запуска существующим phase runner: один чистый 20-секундный
   raw-present window на boot; observed countdown +8000 mover ticks, допуск 300.
   Три запуска дают начальную оценку разброса, не узкий доверительный интервал.
