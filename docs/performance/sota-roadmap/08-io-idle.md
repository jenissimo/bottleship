# 08. Idle worker: SAB IO или тики между модулями

## Видение

Worker простаивает 5.5 ms медианного кадра (12% сэмплов в трейсе, до 26% по узкому
подсчёту) при 100% кадров сверх бюджета. Простой на узком потоке это чистая потеря.
Классификатор из follow-up дал 27.6% «io-stream», но стеки в этом трейсе плоские, и
различить два кандидата по нему нельзя:

- **Синхронные SAB-чтения.** `SabIoSource.request` паркует worker в `Atomics.wait`, пока
  io-worker читает из бандла. Far Cry стримит из .pak непрерывно; каждый ReadFile это
  round-trip.
- **MessageChannel-прыжки между тиками v86.** `next_tick` отдаёт управление event loop
  каждый тик; при коротких тиках латентность macrotask складывается в idle.

Рычаги разные: для IO это readahead под последовательный паттерн и обслуживание
ReadFile из кэша без round-trip; для тиков это длина тика (retired-бюджет между
выходами в event loop) при сохранении отзывчивости port-сообщений.

## Как снять

Один harness-глагол `idleReport` за окно:

1. `SabIoSource.stats()` (уже есть): `requests`, `_waitsBlocked`, `blockedMs`,
   гистограмма `recordBlock`. Доля `blockedMs` от длины окна это IO-часть idle.
2. Число тиков v86 за окно и средняя длина тика; разница «длина окна минус сумма
   `do_tick`» это event-loop-часть idle.
3. Остаток это неучтённое, и он обязан печататься отдельно, а не растворяться.

Если IO: гистограмма размеров и смещений ReadFile из thunk-ring за окно покажет паттерн
(последовательный, страйдовый, случайный) и размер окна readahead, который его покроет.
Существующий prefetch DDraw-readback показал 0 servedFresh из-за неверной точки pump-а;
здесь та же ловушка: readahead обязан считать `servedFromReadahead`, и ноль это ошибка
конфигурации, а не «не помогло».

Если тики: A/B с удвоенным retired-бюджетом тика при контроле латентности
`postMessage`-ответов (harness `pacing`).

## Синтетические тесты

Correctness:

- **Readahead под записью**: guest читает файл с readahead, пишет в него через WriteFile,
  читает снова. Второе чтение видит запись (кэш инвалидирован по диапазону).
- **Readahead под seek**: последовательное чтение, прыжок назад, чтение. Возвращённые
  данные совпадают с эталоном; счётчик `servedFromReadahead` растёт на последовательной
  части и не растёт после прыжка.
- **Timeout parity**: io-worker намеренно задерживает ответ; guest получает те же данные,
  `SabIoSource: read timed out` не срабатывает раньше, чем без readahead.
- **Self-check**: readahead, отдающий устаревший буфер, обязан быть пойман тестом под
  записью.

Perf fixture: `demo_stream_read` (чтение 200 MB файла блоками по 64 KB с checksum,
режимы sequential/strided/random, SCALE по объёму). Модель `ms = fixed + k × MB`;
readahead обязан снижать k на sequential и не повышать на random.

## Критерий успеха

`idleReport` называет источник idle с остатком ниже 1 ms/кадр; после рычага idle
падает на измеренную величину при паритете correctness-тестов.
