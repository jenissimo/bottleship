# AOT / A0: записать сессию игры и получить с неё выигрыш

Дата: 2026-09-02.

> **Это НЕ ускорение установившегося FPS.** A0 переиздаёт ровно те байты, которые JIT
> сгенерировал бы сам, то есть по построению **1.00×** после прогрева. Снимается только
> стоимость *производства* этих байтов.
>
> Измерено на NFS Underground (макс. настройки): медиана кадра **не сдвинулась вообще** —
> 17.0 мс в обоих армах. Изменился **хвост**: p99 27.0 → 21.5 мс. ВАЖНО: это окно снято
> НЕ в заезде — скриншот показал меню выбора трассы, восьми Enter-ов до гонки не хватило.
> Числа по компиляции покрывают загрузку и фронтенд и остаются в силе; хвост относится к
> меню, а не к геймплею. Если игра тормозит РОВНО, A0 не поможет.

## Что делать

**Кнопками в дев-панели:** `⏺ AOT: Record` → играть → `⏹ AOT: Save`. Рядом `AOT: Auto`
(загружать ли кэш на старте — выключать только для A/B-арма) и `AOT: Status`. Состояние
записи показано текстом рядом с кнопками: ритуал из двух шагов, у которого невыполненный
второй шаг ничего не сохраняет, не должен зависеть от того, помнит ли человек, нажал ли он
первый.

Тем же самым из консоли страницы:

```js
dbg.aotRecord('start')   // писать всё, что скомпилируется с этого момента
// ... играть: пройти те места, которые тормозят ...
dbg.aotRecord('stop')    // сопоставить байты с записями публикации и сохранить
```

Дальше перезагрузить и играть снова — следующий запуск подхватит запись сам (условие
загрузки: «у этой игры есть сохранённые единицы», никакого флага не нужно).

Проверить, что подхватил — кнопкой `AOT: Status`, или из консоли (результат печатается в
консоль ВОРКЕРА, не страницы):

```js
dbg.aot('bootStats')   // {loaded, replayed:{registered, refused, refusedUnits}}
dbg.aotEntered()       // {alive, enteredUnits, entries} — вошли ли единицы РЕАЛЬНО
dbg.aot('recording')   // сколько модулей держит живая запись и сколько отброшено
```

`enteredUnits` должен равняться `alive`. Единица, которая владеет страницей, но не входит,
хуже отсутствующей: JIT не может скомпилировать занятую страницу, и гость исполняет её
интерпретатором.

### Два правила, нарушение которых стирает запись

1. **Сессия записи должна грузить кэш.** Если она стартовала с `__aotNoAutoLoad`, её набор
   единиц пуст, и `save()` раньше удалял всё ранее сохранённое. Сейчас в этом случае
   пруннинг пропускается и в лог идёт предупреждение, но `index.json` всё равно назовёт
   только единицы этой сессии — чтобы уплотнить набор, перезапишите его из сессии, которая
   кэш загрузила.
2. **`__aotNoAutoLoad` живёт в localStorage** (`setWorkerFlag` / `dbgFlag`) и переживает
   перезагрузку. Один раз выставив его для A/B-арма, снимите обратно (`dbgFlag('__aotNoAutoLoad', null)`),
   иначе следующая запись пойдёт в холодную сессию.

Записывать можно несколько раз: свежая единица вытесняет старую, если пересекается с ней по
страницам, остальные сохраняются.

## Измерено

**Область: одна синтетическая CPU-демка `demo_fc_rebench`, 180 кадров, всего ~4 горячих
модуля, два прогона подряд байт в байт.** Это x87-нагрузка, которую
[RESULTS-2026-09-02.md](RESULTS-2026-09-02.md) сама дисквалифицирует как прокси для
графики (0.00% SSE против 15% у D3D9-демки). На игру эти числа не переносятся.

```
сессия 1 (холодная):  6 компиляций / 1.46 МБ   -> записано 4 модуля, сохранено 3 единицы
сессия 2 (тёплая):    загружено 3, зарегистрировано 2, 1 отклонена (content-mismatch)
                      вошли 2 единицы, ~9.0 млн входов (счётчик СЭМПЛИРОВАННЫЙ: chained-входы
                      считаются пачками по 32, jit.rs CHAIN_NOTE_MASK)
компиляций   6 -> 4       (-33%, то есть два модуля из шести)
байт эмита   1.46 МБ -> 0.44 МБ  (-70%)
```

Сырой вывод: `logs/roadmap/aot-roundtrip.txt`.

### На реальной игре: NFS Underground, макс. настройки (загрузка + фронтенд, НЕ заезд)

`tools/probes/nfsu-aot-ab.harness.ts`. Записано 146 модулей → 117 единиц; на прогреве
принято 112 из 117, вошли все 112 (3.58 млрд входов).

| | холодный (запись) | тёплый (кэш) | |
|---|---:|---:|---|
| компиляций | 176 | **21** | −88.1% |
| байт эмита | 32.3 МБ | **1.67 МБ** | −94.8% |
| кадр p50 | 17.0 мс | 17.0 мс | без изменений |
| кадр p95 | 20.25 мс | 19.0 мс | −6% |
| кадр **p99** | 27.0 мс | **21.5 мс** | **−20%** |

Оговорка, которая эти цифры ограничивает: скриншот арма показал экран «SELECT LOCATION»,
то есть окно снято в МЕНЮ, а не в заезде — восьми нажатий Enter до гонки не хватает.
Поэтому:

- числа по компиляции (176 против 21) остаются: это реальный код загрузки и фронтенда,
  и разница структурная, не разброс;
- хвост p99 27.0 → 21.5 относится к меню, а не к геймплею, снят одним окном 25 с на арм,
  и это **направление, а не результат**.

Утверждение «выигрыш A0 лежит в хвосте геймплея» пока НЕ подтверждено — нужен прогон, в
котором сцена проверена, а не предположена.

Чего в этой таблице НЕТ и почему: «время до заезда» первая версия скрипта показывала как
224 с в обоих армах — это были её собственные фиксированные `sleep`, а не измерение. Метрика
удалена; вместо неё компиляция считается **по фазам** (загрузка / меню / заезд), потому что
работа, попавшая на фазу заезда, и есть будущее подёргивание.

Прежняя цифра из дизайна (−68% компиляций / −81% байт / +27.7% cold FPS,
`plan/aot-compiler-design.md`) снята на другой нагрузке и с этой не сводится.

### Почему одна единица отклоняется — и почему это оставлено как есть

Отклоняется `0x21141`: 10 650 байт, 5 точек входа. Большая (375 КБ, 191 вход) проходит.

Диагноз снят побайтовым сравнением страницы (`tools/probes/aot-page-drift.harness.ts`):

```
capture-time (s1) против того же момента в s2 : идентично
бут s2 против «после игры» s2                : 834 байта в 102 участках, с +0x960
```

То есть страница **детерминирована между сессиями**, но **меняется в течение сессии**: на
бутe одна форма, после старта другая, и различающиеся байты — это x86-код. Страница держит
код, который патчим МЫ САМИ уже после boot-replay (thunk-прологи, JMP-патчи hle-lib).
Content binding отказывает правильно: на момент replay страница ещё не в той форме, из
которой единица снята. Это несовпадение по ВРЕМЕНИ, а не устаревшая единица.

Напрашивается отложенный повтор — и он был написан и **откачен**. `replay()` перестраивает
список живых регистраций, поэтому второй проход роняет то, что зарегистрировал первый:
измерено `alive` 2 → 0, то есть две работающие единицы (375 КБ и 13 КБ) обменивались на
шанс спасти одну 10-килобайтную. Причина и условие записаны в `aot-cache.ts` рядом с
`replay()`: всё, что повторяет попытку, обязано публиковать ИНКРЕМЕНТАЛЬНО, а не
перезапускать публикацию целиком.

`refusedUnits` в `bootStats` называет, КАКАЯ единица отклонена: единицы отличаются на два
порядка по размеру, и «1 отклонена» само по себе не говорит, потеряли мы 10 КБ или 375.

## Инварианты, которые легко нарушить

- **x87 покрыт полностью — потому что A0 ничего не компилирует.** Покрытие наследуется, а
  не реализуется. Измерено на тех самых страницах, которые A0 переиздаёт: интеджерный слайс
  компилятора взял бы 73.7% (стр. 0x401) и 84.4% (стр. 0x402), а блокер номер один — x87
  (`d9`/`d8`/`dd`/`de`, 242 из 438 на первой странице). Одна инструкция вне слайса закрывает
  единицу, поэтому для КОМПИЛЯТОРА эти страницы нерегистрируемы, а для A0 они работают.
- **`arm()` не подходит для записи игры.** Он именует уже горячие страницы; за сессию
  горячими становятся новые, а при выключенном tier-2 (в production `tier2Threshold = 0`)
  его набор вообще пуст. Пишет `armAll()` — каждый компилируемый модуль, с границей
  `maxPages` и счётчиком `dropped`, чтобы усечённая запись читалась числом.
- **Свежая единица вытесняет загруженную по пересечению страниц, а не по одной странице.**
  Загруженная 8-страничная единица, одну страницу которой JIT перекомпилировал отдельным
  модулем, теряется целиком. Покрытие может уменьшиться там, где ожидалось сложение.
- **`mem8` вбит константой в каждый модуль** (TLB-запись несёт `high + mem8`), и это
  результат `alloc::alloc`. Он входит в ключ версии (`mem8Base`, ABI 6) — без этого сессия
  с другой базой переиздала бы модули, читающие ЧУЖУЮ память: не отказ, а тихая порча,
  единственный класс, который content binding поймать не может (он хеширует гостевые
  страницы, а не раскладку wasm-кучи).
- **Единица переигрывается только в своём исходном слоте таблицы.** Слотов 900 и они
  переиспользуются, поэтому единицы из разных сессий могут конфликтовать за слот; вторая
  отказывается (`tx-begin-*` в `refusedUnits`). Релокация слота не реализована.
- **Набор растёт объединением по сессиям**, и на каждом бутe все файлы читаются,
  компилируются и хешируются с приостановленным эмулятором. Единица, отклонённая по
  content-mismatch, остаётся в наборе навсегда. Чистка — `dbg.aot('clear')` плюс перезапись.

## Чего это не даёт

- Ноль ускорения установившегося FPS, по построению.
- Покрывается только то, что вы сыграли: JIT компилирует от наблюдённых точек входа.
- Страница, которую патчат между сессиями, отказывается по content binding — так и надо.
