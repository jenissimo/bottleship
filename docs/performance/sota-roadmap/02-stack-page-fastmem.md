# 02. Stack-page fastmem: стековые обращения без TLB

## Видение

Нативные dynarec-и делают guest-доступ к памяти за ноль инструкций через hardware MMU.
В wasm каждый доступ это TLB-lookup: сдвиг, load `tlb_data`, and, compare, branch,
XOR-remap (`gen_safe_read` в codegen.rs). У нас identity-mapping, поэтому трансляция
тождественна и проверять нужно только права.

Стек это особый класс: в скомпилированном C++ значительная доля memory-ops идёт через
ESP/EBP, стековые страницы не двигаются и не декоммитятся под живым потоком. Один guard
при входе в единицу («страницы от ESP-N до ESP+M committed RW и не THUNK_CODE») делает
все ESP/EBP-относительные обращения единицы raw `i32.load/store` с offset.

Границы, которые остаются честными:

- Обращение с ESP/EBP-базой и известным смещением, укладывающееся в окно guard-а.
- Окно: N покрывает push/call/sub esp внутри единицы, M максимальное положительное
  смещение. Оба считаются статически по единице.
- Единица, меняющая ESP на невычислимую величину (`mov esp, [x]`, `sub esp, eax`,
  `leave` с неизвестным EBP), заканчивает fastmem-run; дальше обычный путь.
- Guard falsified (страница не RW, красная зона, граница региона внутри окна): вход по
  обычному пути, единица не деоптимизируется.

Win32-специфика: guard page стека (PAGE_GUARD) и рост стека через #PF. Guard-проверка
обязана считать guard-страницу не-RW, чтобы первое касание пошло по slow path.

## Как снять

До реализации:

1. Census (пункт 10) с классификацией memory-операндов: доля ESP/EBP-based с константным
   смещением от всех memory-ops. Это верхняя граница.
2. Потолок при нулевой цене guard-а: экспериментальный кодоген «unsafe raw» для стековых
   обращений без guard-а, только для CPU-арма демки, не для игр. Разница с текущим
   кодогеном это максимум, который guard может съесть.

После реализации: OFF/ON на CPU-арме демки и на Far Cry, с новыми профилерными
счётчиками `STACK_FASTMEM_ENTER`, `STACK_FASTMEM_GUARD_FAIL`, `STACK_FASTMEM_RUN_BREAK`.
Guard-fail rate выше нескольких процентов входов означает, что окно выбрано плохо.

## Измерено: потолок при нулевой цене guard-а (2026-09-02)

Шаг 2 из «Как снять» выполнен. В кодоген добавлен экспериментальный, ЗАВЕДОМО НЕВЕРНЫЙ путь
(`set_stack_raw_unsafe`, по умолчанию выключен, `vendor/v86/src/rust/codegen.rs`): 32-битное
ЧТЕНИЕ с базой ESP/EBP, без индекса, на плоском сегменте компилируется в сырой
`i32.load` по линейному адресу — без present/RW/has-code. Он существует, чтобы измерить
бюджет guard-а, и никогда не включается для игры.

Фикстура `stack_mix` (`bun run guestbench stack_mix --mix 20|50|80 --stack-raw`), 300 000
итераций, 7 повторов, медиана; 10 memory-операндов на итерацию, из них `mix`% стековые.

| mix | guarded, ms | raw, ms | raw/guarded | стековых обращений | экономия на обращение |
|---:|---:|---:|---:|---:|---:|
| 20% | 5.90 | 5.60 | 0.949 | 0.6 M | 0.50 нс |
| 50% | 5.60 | 4.81 | 0.859 | 1.5 M | 0.53 нс |
| 80% | 5.72 | 4.58 | 0.801 | 2.4 M | 0.48 нс |

Noise floor этой машины на этой же фикстуре и окне: две подряд GUARDED-серии дали медианы
5.53 и 5.55 мс — 0.4%. IQR внутри серии 4–12% (одиночные выбросы ОС видны в min/max и
поэтому разброс считается по интерквартильному размаху, а не по max−min).

Выводы, которые из этого следуют:

1. **Эффект есть и монотонен по доле стековых обращений**, как и предсказывает пункт. Это и
   было главной проверкой: если бы он не рос с долей, дальше идти незачем.
2. **Потолок — около 0.5 нс на обращение** и он устойчив по трём точкам (0.48–0.53). Это
   бюджет guard-а: guard, стоящий дороже ~0.5 нс на покрытое обращение, отрицателен.
3. Checksum во всех парах ARM-ов совпадает бит в бит, то есть сырой путь читает те же
   значения — arm-ы делают одну работу.

Что этот потолок НЕ говорит:

- Путь покрывает только 32-битные ЧТЕНИЯ; записи и другие ширины остались guarded, так что
  это НИЖНЯЯ граница полного рычага.
- У фикстуры идеальная локальность: TLB всегда попадает. Измерена цена ПРОВЕРКИ, а не
  промахов. На реальном коде с промахами экономия может быть больше — или guard может
  срабатывать чаще, чем на синтетике.
- База гостевой памяти в wasm запечена в момент компиляции. Настоящая реализация обязана
  инвалидировать единицы при росте памяти; здесь этого нет, и это одна из причин, по которым
  путь остаётся экспериментом.

Следующий шаг по пункту не «писать guard», а сначала census (пункт 10) на живой игре: доля
ESP/EBP+const среди всех memory-ops умножается на 0.5 нс и даёт ожидаемый выигрыш до
вычета цены guard-а. `opcodeCensus` уже отдаёт эту долю как `memory.stackConstPctOfMemory`.

## Синтетические тесты

Correctness differential (bun test поверх v86 wasm, по образцу `fpu-absolute`):

- **Paging parity**: страница стека декоммитится, guest трогает её через ESP-смещение.
  OFF и ON дают #PF на той же инструкции с тем же CR2.
- **Guard page growth**: PAGE_GUARD ниже текущей страницы; функция с большим frame делает
  `sub esp, 0x2000` и касается. Ожидается рост стека, а не raw store в guard-страницу.
- **Window overflow**: единица, чьё статическое окно меньше реального касания через
  `sub esp, eax`. Fastmem-run обязан прерваться на этой инструкции.
- **Red zone**: ESP установлен так, что окно перекрывает границу THUNK/RESERVED. Guard
  обязан отказать.
- **Self-check**: при намеренно отключённом guard-е тест обязан увидеть raw store в
  декоммиченную страницу. Тест, который не падает без guard-а, не проверяет ничего.

Perf fixture: `demo_stack_mix` с тремя режимами по доле стековых обращений (20/50/80%
memory-ops), фиксированное число итераций, checksum результата. Выигрыш должен расти
монотонно с долей; если не растёт, guard дороже сэкономленного.

## Критерий успеха

Положительная медиана на CPU-арме выше noise floor при 100% паритете paging-тестов и
guard-fail rate ниже 1% входов на Far Cry.
