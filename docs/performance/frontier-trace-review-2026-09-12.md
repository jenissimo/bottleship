# Проверка frontier-стратегии по сохранённым трассам

**Уточнение 13.09:** [пересчёт NFSU/NFSU2/Bard и проверка EIP-сэмплера](nfs-frame-work-diagnosis-2026-09-13.md).
Встроенный таймер читает EIP между заходами в Wasm; его частоты не являются
долями времени гостевых функций. CPU-профиль Chrome и эти наблюдения EIP имеют
разные механизмы измерения. Полное пересечение сохранённых EIP с libid выполнено
в новом отчёте с этим ограничением.

2026-09-12. Повторный анализ исходных Chrome traces в дереве, без новых запусков игр.
Это исправляет первый вариант [стратегии](frontier-strategy-2026-09-12.md): существующих
данных достаточно для выбора следующего эксперимента. Переснимать весь baseline до
такого выбора не требуется. Производительность нового кандидата здесь не измерялась.
Приоритет уточнён пользователем: **NFSU и NFSU2**. Quake II software — только
диагностический workload возможной общей проблемы; OpenGL, по сообщению пользователя,
уже работает в 60 FPS. Ниже сохранены его находки, но их бюджет не считается целевым.

## Источники и воспроизведение

Разобраны девять файлов: `p0-item1-race`, `p0-item1`, `prof-nfsu2`, `prof-painkiller`,
`nfsu-race-clean`, `ab-armA-baseline`, `ab-armB-new`, `ab-rv-new-4` в `logs/` и
`logs/bards/armG-60s.json.gz`. Даты файлов: NFSU/NFSU2/Painkiller — 11 сентября,
Quake II/Re-Volt/Bard — 12 сентября. Mtime используется для инвентаризации, не как
доказательство времени записи или идентичности текущей сборке.

Полные SHA-256 исходных сжатых файлов:
[manifest](../../logs/frontier-review-20260912/manifest.json).
Отчёты получены текущим `tools/analyze-trace.ts`, с `--js-owners --no-auto-map`:
метки внутри trace разрешены, случайный sidecar соседней сборки не подмешивается.

```powershell
bun tools/analyze-trace.ts logs/p0-item1-race.json.gz --thread worker --top 45 --js-owners --no-auto-map
bun tools/analyze-trace.ts logs/prof-nfsu2.json.gz --thread worker --top 30 --js-owners --no-auto-map
bun tools/analyze-trace.ts logs/prof-painkiller.json.gz --thread worker --top 30 --js-owners --no-auto-map
bun tools/analyze-trace.ts logs/ab-armB-new.json.gz --thread worker --top 30 --js-owners --no-auto-map
```

Для ancestor-union анализа использован отдельный
[скрипт](../../logs/frontier-review-20260912/inspect.ts), который переиспользует
mergeProfileChunks/analyzeThread штатного инструмента. Для каждого self-сэмпла
проверяется наличие interpreter/compilation/invalidation в цепочке родителей;
сампл считается один раз. В disjoint-разбиении compilation/invalidation имеют
приоритет над interpreter. Сумма категорий обязана совпасть с суммой timeDeltas.
Это устраняет двойной счёт вложенных helper и рекурсивных frames.

```powershell
bun logs/frontier-review-20260912/inspect.ts logs/ab-armB-new.json.gz logs/frontier-review-20260912/quake2-B.json
bun logs/frontier-review-20260912/inspect.ts logs/p0-item1-race.json.gz logs/frontier-review-20260912/nfsu-race-detail.json
bun logs/frontier-review-20260912/inspect.ts logs/prof-nfsu2.json.gz logs/frontier-review-20260912/nfsu2-detail.json
bun tools/analyze-wbuf-sequence.mjs logs/perf-campaign/wbuf-order.json
```

Ограничения: трассы — инструментированные наблюдения, не clean FPS A/B.
Present ledger недоступен в рассмотренных отчётах, поэтому cadence устанавливается
по достигшим worker меткам flip, без независимой проверки полноты presents. В файлах
Quake II/Bard сохранены traceEvents и hotblocks, но нет полного manifest загруженной
сборки. Для будущего A/B он потребуется; для приоритизации существующие стеки пригодны.
60-секундная Bard-трасса из кампании с риском заполнения trace buffer; её выводы
предварительны до сверки buffer telemetry. CPU samples покрывают около 60 секунд.

## NFSU: сведение приборов уже выполнено

`p0-item1-race.json.gz`: 15 секунд, 42 666 samples основного worker, 227 flip marks.
Прочитанный [отчёт](../../logs/frontier-review-20260912/nfsu-p0.txt) воспроизводит:

| Класс | % всего времени потока | % busy из roll-up |
|---|---:|---:|
| GAME CODE, сгенерированные JIT-функции | 31.0 | 37.8 |
| JS HLE + glue | 27.9 | 34.0 |
| Wasm hypercalls | 7.5 | 9.1 |
| other v86 core | 7.7 | 9.3 |
| indirect lookup | 1.7 | 2.1 |

В [портфеле, Project 0](../../plan/perf-campaign/perf-portfolio-2026-09-11.md) уже
сохранены результаты сведения на статичной и движущейся сценах: остатки 0.9 и 0.01 п.п.
Структурная причина ложных «93% v86»: drain находится перед thunk-таймером, а для fast
paths категория получает только 1/32 измерений, в отличие от агрегата по именам.
Мой первый план заново ставил завершённую работу. Этот пункт снимается.

В движущейся сцене JS под drain — 17.0% потока, из них механика кольца всего около 1.5%,
остальное payload. MOVES executor-only — 4.6% потока / 5.6% busy. Следовательно, ни
ускорение обхода кольца, ни его перенос не возвращают весь drain-бюджет.
Искомый срез — реально исполняемые setter/resolve эффекты, с учётом уже принятых правок.
37.8% guest вместо 34% немного улучшает сценарную арифметику: удвоение всего этого
busy-бакета даёт x1.233 busy-throughput при полном покрытии; это не FPS-прогноз.

## NFSU: подтверждённый шаблон D3D9, который детектор пропускает

Повторный запуск штатного `tools/analyze-wbuf-sequence.mjs` на сохранённом
`logs/perf-campaign/wbuf-order.json` воспроизвёл вывод последнего раздела портфеля:
4000 записей, 465 draws; 343 из 464 интервалов (73.9%) содержат
`VSConst · SetVertexShader · VSConst×2 · SetPixelShader · SetTexture`, затем draw.
Всего 14 форм с учётом длины bursts; top-8 покрывают 98.1%. Среднее — 7.6 записей
между draw. [Вывод инструмента](../../logs/frontier-review-20260912/nfsu-wbuf-sequence.txt).

Смежных alternating `CONST → DRAW` пар нет. Проверка текущего
`src/worker/core/thunking/thunk-dispatcher.ts` подтверждает: prefix extension всё ещё
требует `tailRun.pairs >= 2`, поэтому она тоже не решает этот случай. Это конкретный
отрицательный результат существующего predicate, а не доказательство бесполезности
обработки более широкого пакета.

Первый кандидат — обработать один реальный семейный шаблон с однократной подготовкой
состояния draw и reuse лишь при совпадении аргументов/generations. Размер выигрыша
ещё не известен: capture содержит имена API, а не полную стоимость и доказательство
совпадения ресурсов или доступности пакета в одном drain. Шаблон не разрешает сам по
себе объединять draw. Сначала восстановить эти условия и сравнить целые эффекты.
JS payload под drain ~15.6% потока: его удвоение целиком означало бы лишь +8.5%
throughput в условной модели. Для десятков процентов нужен также guest/HLE-компонент;
73.9% частоты не является 73.9% CPU-coverage.

## Переносится ли проблема JIT Quake II на NFSU/NFSU2?

Тот же ancestor-union скрипт применён к целевым трассам; знаменатель везде — всё время
основного worker, включая idle. Self helper не добавляются повторно.

| Класс | NFSU race | NFSU2 | Quake II software B |
|---|---:|---:|---:|
| Interpreter с потомками | 1.294% | 1.181% | 41.501% |
| Compilation с потомками | 0.082% | 0.098% | 11.238% |
| Invalidation, union (может пересекаться с interpreter) | 0.0035% | 0.0093% | около 0.115% |

Данные: [NFSU](../../logs/frontier-review-20260912/nfsu-race-detail.json),
[NFSU2](../../logs/frontier-review-20260912/nfsu2-detail.json).
В этих двух целевых окнах interpreter и compilation также не пересекаются.
Условное полное удаление обоих классов оставляет потолок около +1.4%/+1.3% при
неизменной остальной работе. Это ориентир конкретных наблюдённых расходов, не строгая
граница всех возможных downstream эффектов JIT-изменения и не замер чистого FPS.

**Вывод:** сильного проявления класса Quake II в текущих NFSU/NFSU2 нет. По этим
трассам он не обосновывает первый большой JIT-проект ради целевых игр. Общую причину
можно изучить ограниченным диагностическим срезом; возврат в основной план требует
общего дефекта корректности либо измеримого влияния на NFSU/NFSU2, включая другие сцены.

## Quake II / ref_soft: диагностический случай, не целевой FPS-трек

`ab-armA-baseline` и `ab-armB-new` — два ~20-секундных окна эксперимента с Proxy,
один worker `53364:35596`, 52 672 / 52 889 samples. Идентификация Quake II подтверждается
встроенной hotblocks-меткой: `quake2.exe` и `ref_soft`. Это software-renderer workload.

Агрегат «85.5% Wasm» из [Proxy-отчёта](v86-view-proxy-ownership-2026-09-12.md)
скрывает главное: большая часть времени тратится не на исполнение JIT-функций.

| Принадлежность стека | A, % времени потока | B, % времени потока |
|---|---:|---:|
| interpreter::run и потомки, union | 40.82 | 41.50 |
| jit_analyze_and_generate / jit_generate_module / finalize, union | 11.30 | 11.24 |
| Self всех JIT-функций с guest entry | около 18.23 | около 18.26 |
| JS | 3.06 | 3.04 |

Первые две строки не пересекаются в этих данных. Внутри interpreter union есть около
0.1% времени invalidation; эту часть нельзя ещё раз прибавить как отдельный выигрыш.
JSON: [A](../../logs/frontier-review-20260912/quake2-A.json),
[B](../../logs/frontier-review-20260912/quake2-B.json).

Это не единичная стартовая пауза: в каждом полном двухсекундном bucket B интерпретатор
занимает примерно 804–858 мс, компиляция 216–235 мс. Картина сохраняется до конца окна.
Она не доказывает, что причина именно SMC. Внутри этого software workload восстановление
JIT-покрытия имеет большой бюджет; приоритет кампании определяется NFSU/NFSU2.

**Если вернуться к этой диагностике:** на горячих страницах `ref_soft` связать
`RUN_INTERPRETED_*`, `COMPILE_PAGE`, `INVALIDATE_PAGE_HAD_CODE` с причинами и поколениями:

- Не достигнут threshold, уже идёт compilation или entry не опубликован?
- Есть compiled page, но не тот entry/state/address-space?
- Код действительно изменился, либо запись соседних данных выбросила весь модуль?
- Одни и те же bytes компилируются повторно, либо поток открывает новый код?

Эти счётчики уже перечислены в `vendor/v86/src/rust/profiler.rs`. Недостающий инструмент —
привязка причин к горячим страницам/поколениям, не ещё один общий trace.
`jit_dirty_page_ctx` удаляет и page, и entry_points и освобождает module forest;
`jit_increase_hotness_and_maybe_compile` заново накапливает heat. Это возможная цепочка
дорогих последствий короткой invalidation, а не установленный диагноз.

SMC — содержательная гипотеза: официальный Quake II `ref_soft` действительно имеет
`R_SurfacePatch` и вызовы `Sys_MakeCodeWriteable` в
[r_main.c](https://github.com/id-Software/Quake-2/blob/master/ref_soft/r_main.c).
Совпадение с конкретными страницами и частотой патчей этого бинаря ещё нужно доказать.

Механизм выбирается после причины: точнее ownership/invalidation для НЕизменившегося
кода, сохранение допустимой hotness, покрытие entry, либо ограниченный кэш по точным
code bytes/state для реально повторяющихся версий. Ни одного ослабления SMC/coherence.
При частом истинном изменении immediate возможен отдельный proof параметризованного
lowering; простое игнорирование записи некорректно. Глобальный рост MAX_PAGES не следует
из этой находки.

**Масштаб только для Quake II software:** если корректный механизм сократит полную стоимость
интерпретируемого класса вдвое, модель с p=0.415 даёт x1.262. Компиляция в этот пример
не включена. Это условный бюджет +26%, а не measured uplift и не обещание такого s.
Он не включается в прогноз NFSU/NFSU2 и не заменяет успех на них.

## NFSU2 и Painkiller: подтверждённые другие классы

NFSU2: GAME CODE 52.4% busy, JS 30.5%, hypercalls практически ноль.
Итог [повторного анализа](../../logs/frontier-review-20260912/prof-nfsu2.txt)
поддерживает приоритет невключившегося EAGL, уже подтверждённого live census в портфеле.
Сам trace не устанавливает размер EAGL-подмножества внутри guest-бакета.

Painkiller: GAME CODE 53.2% busy, JS 30.0%, indirect lookup 5.9%.
[Отчёт](../../logs/frontier-review-20260912/prof-painkiller.txt) сохраняет две популяции
просадок: худшие ~299–309 мс на 87–90% состоят из idle; после исключения >2×budget
кадров обычный tail имеет +8.29 мс guest-code excess и +4.08 мс JS excess относительно
median band. Не объединять I/O/парковку и CPU-work в одну причину. Семантические guest
ядра остаются здесь исследовательским треком, indirect lookup — вспомогательным.

## Bard: отдельно проверить принадлежность «гостевого» кода

В `armG-60s` roll-up даёт GAME CODE 34.3% busy, JS 28.6%, indirect lookup 7.3%.
Самая дорогая JIT-функция по сумме self-сэмплов — `g2a001060@t874`, **7.07% времени
потока**. Entry находится в нашем kernel32 HLE image: это `MEM_HLE_IMAGE_BASE=0x2a000000`,
slot 0, `.text` от +0x1000. Это не `MEM_THUNK_CODE_BASE=0x21000000`.

Поэтому автоматическое имя GAME CODE не гарантирует, что бакет состоит из вычислений
игры: туда попадают скомпилированные тела наших экспортов. Сам адрес входа не доказывает
полный охват функции — модуль может включать несколько страниц и entry. До назначения
всех 7.07% конкретному API нужно проверить mapping и байты текущего trace-артефакта.

Следующий срез — экспортные stubs и фактические tiers дорогих вызовов. В логах этой
кампании есть WASM MISS для SetEvent/EnterCriticalSection, а старый baseline отдельно
называет частые `_libm_sse2_sqrt_precise`. Эти зацепки не равны частотам окна armG;
проверять соответствие по конкретному вызову, не расширять HLE вслепую.
Рекурсивный union под `g2a*` — 21.0% потока и пересекается с JS: не складывать их.

Re-Volt остаётся capped контрольным workload: `ab-rv-new-4` показывает 60.1 FPS, и это
не сцена для доказательства +20% throughput. Его заметный ring/vertex путь — отдельная
гипотеза для CPU-bound DDraw-сцены, не основание включить его выигрыш в NFSU.

## Изменённый порядок работы

1. **NFSU2: EAGL правильной версии.** Найти реальную функцию, установить ABI/effects
   и текущий CPU-бюджет, затем один descriptor/handler и A/B. Ноль matches не позволяет
   считать весь guest-бакет устранимым через EAGL.
2. **NFSU: реальный D3D9 packet.** Проверить ресурсы/аргументы и границы drain для уже
   известного шаблона; один consumer, сокращающий повторную подготовку состояния.
   Порядок реализации первых двух кандидатов выбрать по net-cost и стоимости proof.
3. **NFSU/NFSU2: целые горячие guest-вычисления.** Если прикладные кандидаты не набирают
   17–23% сокращения кадра, искать крупные семантические regions этих игр. Выигрыш EAGL
   и D3D9 может пересекаться: нужен combined arm, а не сложение процентов.
4. **Quake II, Bard, Painkiller: диагностический и регрессионный набор.** Находки сохраняются,
   но положительный FPS-результат здесь не заменяет целевые NFSU/NFSU2. Quake II поднимать
   выше только при установлении общего дефекта или существенного целевого влияния.

Следующее измерение — короткая проверка бюджета EAGL и условий reuse draw-пакетов,
затем один candidate A/B.
Новые широкие traces нужны только для отсутствующей сцены или изменённой сборки, а не
как обязательные два дня подготовки к уже обоснованному выбору.
