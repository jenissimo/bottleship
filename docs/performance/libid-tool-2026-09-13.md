# libid: инструмент опознания библиотечного кода в guest-образах

2026-09-13. Шаг 1 работы «Перепись горячего кода NFSU — чей он». Собран и
откалиброван инструмент, который по бинарнику и списку адресов отвечает, чей
это код: игры или статически влинкованной библиотеки. Доли времени в этом
документе **не считаются** — здесь только инструмент и статический разбор
образов; время приходит из профиля на следующем шаге.

## Зачем

Гипотеза: заметная часть перфа лежит в статически влинкованных чужих
библиотеках — D3DX, CRT от MSVC, математика, — одинаковых у всех игр эпохи.
Проверить её нельзя, пока горячая функция называется `FUN_00672fc8`: это честное
имя и одновременно бесполезный ответ, если на самом деле там `__ftol` из CRT.
Аудит каталога (`library-hle-catalog-audit-2026-09-12.md`) прямо назвал
недостающее звено — связь профиля с владельцем кода, и отдельно потребовал не
записывать неопознанный код в «код движка».

## Что собрано

`tools/re/libid.py` (+ обёртка `libid.ts` в стиле `re.ts`, справка в
`tools/re/README.md`). Два режима: `index` открывает образ в Ghidra и строит
карту владельцев один раз на sha256; `ask`/`summary`/`selftest` читают готовый
индекс и Ghidra не трогают вовсе — список горячих адресов трассы разбирается за
доли секунды. Адреса принимаются и в виде имён из трасс (`g0040d001@t12`).

Источники опознания, каждый со своим весом и следом в ответе:

| источник | что доказывает |
|---|---|
| `fid` | Ghidra Function ID — FLIRT-аналог; база в поставке собрана с библиотек Visual Studio, поэтому попадание само по себе значит «не код игры» |
| `sig` | собственные сигнатуры, снятые с DLL-донора: strict — байты тела с замаскированными адресами, fuzzy — поток мнемоник. Закрывает то, чего в базах FID нет вовсе |
| `str` | строки-отпечатки (`lib-fingerprints.json`) плюс xref, в том числе через указатель в данных |
| `import` | thunk в импорт: код вообще не в образе |
| `shared` | то же тело найдено в образе другой игры — код общий, но библиотека не названа |
| `region` | функция без своей улики внутри плотного библиотечного блока: линкер кладёт объектники подряд |
| `vtable` | слот таблицы методов, большинство соседей по которой — подтверждённая библиотека |
| `callgraph` | в группу взаимно рекурсивных функций снаружи ходит только подтверждённый библиотечный код |

Категорий ответа четыре: `library` / `import` / `game` / `unresolved`. «Не
опознано» не сливается с «код игры» — иначе census получит долю «собственного
кода движка», которой никто не измерял. У каждого ответа есть `confidence` и
`reason` с названием источника.

## Калибровка

`libid selftest` сверяется с якорями, чьи владельцы установлены независимо
(`tools/re/libid-anchors.json`):

- **NFSU, 6 из 6.** `__ftol`, `_memcpy`, `_memset`, `_strlen`, `_malloc`, `_free`
  по адресам из аудита каталога — `library/msvc-crt`, confidence high, источник
  `fid/single`.
- **NFSU2, 2 из 2.** Диспетчер состояний D3DX Effect runtime `0x00669296` и
  helper `0x0066404c` из разбора Codex — `library/d3dx9`. Важно, каким путём:
  0x669296 не имеет ни строки, ни сигнатуры, ни имени; он опознан через группу
  взаимной рекурсии (0x669296 ↔ 0x6691b1 ↔ 0x668e0d), в которую снаружи ходят
  только Effect Pass/End, а те — слоты vtable эффекта. То есть инструмент пришёл
  к выводу Codex своей дорогой, а не переписал его.

Оба промаха, найденные по дороге, стоили отдельных механизмов: правило «все
вызывающие опознаны» на взаимной рекурсии не срабатывает никогда (потребовалась
конденсация по компонентам сильной связности), а строку `D3DX Effect Compiler`
GetDesc достаёт через указатель в данных — обрыв xref на первом шаге терял весь
кластер runtime.

## Что видно уже сейчас (статически, не по времени)

Доли **статического объёма кода**, не времени:

| образ | код игры | d3dx9 | msvc CRT/прочий MS | импорты |
|---|---:|---:|---:|---:|
| NFSU (`Speed.exe`, 9 800 функций) | 92.3% | 4.5% | 2.8% | ~0% |
| NFSU2 (`SPEED2.EXE`, 14 910 функций) | 79.7% | 18.3% | 2.0% | ~0% |

Существенное: **1 125 функций NFSU2 совпали побайтно с `d3dx9_24.dll`** —
статический D3DX в образе не «похож на», а собран из того же кода, что DLL
декабрьского SDK 2004. В NFSU строгих совпадений всего 31, но эффект-компилятор
D3DX там тоже статически влинкован (строки `ID3DXEffectCompiler: ...` около
`0x005b2d7a`) — то есть находка Codex по NFSU2 распространяется и на NFSU.

Это статический охват. Он ничего не говорит о доле времени: библиотечный код
может быть холодным, а 92% объёма игры — содержать один горячий цикл. Считать
время — задача следующего шага.

## Оговорки и дыры

- `game` ставится по отсутствию библиотечных улик и по раскладке образа
  (библиотеки линкер кладёт хвостом), подкреплённому отсутствием совпадений в
  корпусе чужих игр. Это довод, а не доказательство; confidence — medium.
- Корпус чужих образов сейчас из двух игр (GTA VC, Heroes 3). Чем он шире, тем
  крепче и «library:shared-code», и обратный довод за «код игры».
- Сигнатурный донор пока один — `d3dx9_24.dll`. Bink, Miles, zlib опознаются
  только строками и FID; для них донора не снимали.
- Файлы сигнатур (`tools/re/libsigs/*.sig.json`) — производные от системных DLL
  машины; в репозиторий не кладём, пересоздаются `libid.py sigs`.
- Индексы образов лежат в `tmp/libid/<sha16>.json` и привязаны к sha256 образа:
  подменённый или пропатченный образ получит свой индекс, а не чужой.
