# Codegen pair: наш x86→Wasm против Emscripten на одном C++ источнике

Дата: 2026-09-10. Задача: понять, что конкретно улучшать в нашей кодогенерации,
сравнив её выход с выходом хорошего компилятора на ОДНОМ исходнике, где нагрузка
повторяет реальную нагрузку игры.

## Нагрузка получена из RE, а не придумана

Горячие страницы NFSU совпали в двух независимых профилях (`eipProfile` и
`guestBlocks`). Через warm RE-сервис (`tools/re/re.ts`, Ghidra) они разобраны:

| Адрес | Функция | Что это на самом деле |
| --- | --- | --- |
| `0x63eaa0` (15.5% EIP-сэмплов) | `FUN_0063eaa0` | **winmm-таймер**: `GetTickCount` + `timeSetEvent`. Точка ожидания, не вычисление |
| `0x5cdca7` | `FUN_005cdca7` | Рекурсивный обход сцены: цепочки разыменований, 4-way диспетчер по тегу, вызовы leaf-хелперов, `float10` |
| `0x5d01ec` | `FUN_005d01ec` | Цикл по подобъектам с шагом `0xac`, `__controlfp` |
| `0x40f1e0` | `FUN_0040f1e0` | Аллокатор + сшивание двусвязного списка команд отрисовки |
| `0x40a580` | `FUN_0040a580` | Кадровый драйвер, вызовы через COM-vtable |

Самый горячий EIP оказался таймером — ровно та ловушка, о которой предупреждает
запись «Guest EIP table ranks yield points». Реальное горячее вычисление — это
**обход структур по указателям**: гистограмма инструкций горячих функций даёт
MOV 38.5%, PUSH 18.5%, CMP/JZ/JNZ ~20%, IMUL 4.6% (страйдовая индексация).

Поэтому демка (`tools/bench-v86/source-pair/fixture-codegen/`) — не пиксельная
арифметика, а шесть ядер по семействам: рекурсивный обход с диспетчером по тегу,
аллокатор со сшиванием списка, страйдовая индексация со смешанными 8/16/32-битными
доступами, косвенные вызовы через таблицу, x87-трансформация и составной «кадр».
Конверсия float→int намеренно оставлена вызовом `__ftol2_sse`: игра делает так же.

## Как достигнута привязка «модуль ↔ функция»

Каждая функция лежит в своей именованной code-секции (`__declspec(code_seg)`).
Секция PE выровнена по SectionAlignment 4096, а JIT публикует модуль на физическую
страницу. Сборка **отказывается продолжать**, если две функции попали на одну страницу.
Это необходимое условие привязки, но, как показано ниже, НЕ достаточное: модуль может
покрывать несколько страниц, поэтому точка входа ещё и проверяется.

Захват: `tools/bench-v86/source-pair/codegen-capture.ts` вооружает `jitBytes` до
загрузки бандла (после загрузки страница уже горячая, и arm поймал бы пустоту).

## Привязка модуля к функции проверяется, а не предполагается

Первая версия захвата называла файлы по секции, для которой запрашивала страницу. Это
оказалось неверно: модуль JIT может ПОКРЫВАТЬ несколько страниц, и тогда ключ слота —
не та функция, с которой он начинается. Из пяти захваченных модулей два начинались не
там, где я их подписал (`0x404000` вместо `0x409000`; `0x401040` вместо `0x40e000`).

Захват теперь читает точку входа из имени сгенерированной функции (`g<entry>@t<slot>`)
внутри самих байт и помечает модуль `attributable` только при совпадении с VA секции.
Неатрибутируемые сохраняются под именем `span-<entry>.wasm` — по ним нельзя считать
ничего «на инструкцию». Числа ниже — только по атрибутируемым парам.

## Результат: сколько операций мы выдаём

Границы функций совпадают на обеих руках (ядра явно экспортированы из Wasm, иначе LLVM
их инлайнит и сравнивать нечего):

| Функция | Инструкций x86 | Наш JIT, операций | Emscripten -O3, операций | Отношение | Наших локалей / у него |
| --- | ---: | ---: | ---: | ---: | --- |
| `cg_k1_walk` | 24 | **1169** | **35** | 33x | 28 / 3 |
| `cg_k3_stride` | 64 | **2298** | **82** | 28x | 28 / 7 |

То есть 49 и 36 операций Wasm на одну инструкцию x86.

**Это структурное сравнение, не время.** Операция Wasm не равна машинной инструкции
после V8, guard в реальности дёшев, и заявлять по этим числам ускорение нельзя. Но они
показывают, ЧТО именно мы эмитим.

## Из чего складывается наш выход

| Категория | `cg_k1_walk` (24 инстр.) | `cg_k3_stride` (64 инстр.) | Механизм |
| --- | ---: | ---: | --- |
| Всего операций | 1169 | 2298 | |
| Inline TLB-проверок | 15 | 32 | одна на КАЖДЫЙ доступ к памяти |
| Операций в них (~14 на проверку) | ~210 (18%) | ~448 (19%) | |
| Полных сбросов регистрового файла | 3 | 4 | 8 store на каждом выходе |
| Точек вызова медленного пути | 17 | 35 | |

Для сравнения: `cg_k3_stride` у Emscripten — 8 обращений к памяти (3 `i32.load`,
3 `i32.store`, 2 `i32.load16_u`) и **ноль** проверок: границы линейной памяти проверяет
железо.

Форма нашей проверки на каждый доступ (из захваченного модуля):

```wat
(i32.load offset=63922308            ;; запись TLB по (addr >> 12) * 4
  (i32.shl (i32.shr_u addr 12) 2))
(i32.and 4041) (i32.eq 1)            ;; биты разрешений
(i32.and addr 4095) (i32.le_s 4092)  ;; не пересекает ли страницу
(br_if ...)                          ;; иначе — вызов safe_read*_slow_jit
```

Плюс пролог загружает все 8 регистров в локали, а КАЖДЫЙ выход (нормальный, faulting,
медленный) записывает их обратно и обновляет счётчик retired.

## Первый кандидат на улучшение, с обоснованием

Проверка эмитится на каждый доступ и не переиспользуется, хотя подряд идущие доступы
адресуют одну страницу: `cg_k3_stride` в каждой итерации трогает три поля одной записи
`CgRow` (запись 0xac байт) — эти проверки избыточны по построению, а не по удаче.

Рычаг: **переиспользование результата проверки для доказанно той же страницы** (токен
страницы в локали, инвалидируемый при смене TLB), вместо повторной проверки на каждый
доступ.

Чего пока НЕ сделано и что нужно, прежде чем это станет заявкой на FPS:

1. Доля этих операций во ВРЕМЕНИ, а не в статике. Нужен side-channel эмиттера
   «гостевой EIP → диапазон Wasm-операций» (пункт 1 из списка пробелов
   `source-pair-lab-2026-09-09.md`) — теперь под него есть демка, на которой он
   проверяется однозначно.
2. Потолок так же, как он считался для WBUF: удельная экономия × измеренная частота.
   Не строить кандидата раньше этого числа (см. `negative-results.md`).
3. Корректностный оракул для новой демки: обе руки должны совпасть по состоянию.
   Ядра детерминированы и целочисленны (x87 при 53-битном PC и Wasm f64 совпадают на
   целых), но прогон обеих рук ещё не сведён.
4. Ядра k4 (косвенные вызовы) и k5 (x87) пока не дали атрибутируемого модуля: k4 не
   успел прогреться, модуль k5 начинается в `.text` (там же `__ftol2_sse`). Для них
   нужен либо более длинный прогон, либо развязка вызова конверсии.

## Замер фиксированной работы: инструмент вместо игрового стенда

Игровой стенд не разрешает единицы процентов (разброс до 12%, см.
`v86-fps-handoff-2026-09-10.md`). Демка даёт замену: фиксированное число итераций, время
меряет САМ гость (`GetTickCount` вокруг `cg_run`), а обе руки возвращают контрольную сумму
всего состояния, посчитанную ОДНОЙ общей C++-функцией.

| Ядро | Наш эмулятор | Emscripten в Node | Отношение | Разброс | Контрольная сумма |
| --- | ---: | ---: | ---: | ---: | --- |
| `k1` обход графа | 342 мс | 31.9 мс | **10.7x** | 3.0% | совпала (3944123003) |
| `k3` страйдовая индексация | 107 мс | 7.81 мс | **13.7x** | 3.8% | совпала (3282292374) |

Совпадение контрольных сумм — это и есть проверка, что руки сделали ОДНУ И ТУ ЖЕ работу;
без неё более быстрая рука может просто делать меньше. Бенч отказывается принимать прогон
с несовпавшей суммой (`--expect`).

Объём работы калибруется по ядру (`ROUNDS` в `build-codegen.mjs`): при общем числе раундов
половина ядер оказывалась ниже разрешения `GetTickCount`, а другая половина считала минутами
(k1 нативно 252 мс на 8 раундов против 0.20 мс у k3).

Это НЕ утверждение об FPS: 10.7x на ядре не переносится на кадр, пока не измерена доля
таких участков во времени кадра. Но теперь кандидат в кодогенерации можно принимать или
отклонять на замере со спредом 3-4% вместо 12%.

## Разрыв по семействам, и поправки к числам выше

Отношение «эмулятор / нативный Wasm» на одной и той же фиксированной работе, обе руки
сверены по контрольной сумме:

| Ядро | Семейство | Эмулятор | Натив | Разрыв | Спред |
| --- | --- | ---: | ---: | ---: | ---: |
| k2 | аллокатор + сшивание списка | 138 мс | 13.95 мс | 9.89x | 3.7% |
| k1 | обход графа по указателям | 323 мс | 31.49 мс | 10.26x | 0.9% |
| k6 | составной «кадр» | 337 мс | 32.12 мс | 10.49x | 4.6% |
| k4 | косвенные вызовы | 138 мс | 10.83 мс | 12.74x | 10.4% |
| k3 | страйдовая индексация | 105 мс | 6.6 мс | 15.91x | 38.2% |
| k5 | x87 | 664 мс | 10.53 мс | **63.06x** | 17.6% |

x87 — отдельный класс, и это уже ПОСЛЕ relaxed-FPU: парный ABBA-замер даёт 2216 мс с ним
выключенным против 714 мс с включённым, то есть relaxed-FPU стоит 3.1x и включён в шипе
по умолчанию. Суммы совпали в обеих руках. Спред k3 (38%) делает его 15.91x мягким.

**Поправки, без которых числа выше вводят в заблуждение:**

1. **Пару `cg_k1_walk` 1169/35 нельзя использовать «на инструкцию».** Захваченный
   `cgk1.wat` — это драйвер цикла (24 инструкции), а горячее тело (`cg_visit` + листья)
   лежит в неатрибутируемом `span-404000.wasm`. Разрыв k1 во времени — это в основном
   стоимость МЕЖМОДУЛЬНЫХ рёбер (сброс 8 регистров, счётчик, dynamic-chaining, пролог),
   которой в статической паре нет вообще. Чистое ядро одно — k3.
2. **«~19% операций — TLB-проверка» не равно 19% ВРЕМЕНИ.** По уже измеренной цене
   проверки (0.51–1.17 нс, sota-roadmap 02/03) полное снятие guard'ов на k3 даёт потолок
   1.3–1.7x, а не 13.7x.
3. **`stack_raw` +3.2% измерял не бакет.** Режим 1 покрывает только 32-битные ЧТЕНИЯ через
   ESP/EBP — на k3 это 4 обращения из 13. Вывод «рычаги по 3% не закрывают x10» верен, но
   этим числом он не доказан.
4. **«v86 residual = 92.5% кадра» — НЕ доля исполнения гостевого кода.** Категория `v86`
   в perfStats это «всё, что не под таймером thunk'а»: туда входят WASM-гиперколлы, OUT-трап
   и glue. Трассовое разложение той же игры (`nfsu-max-settings-ceiling-2026-09-02.md`)
   даёт код игры в JIT-блоках 23.0 мс, гость+v86 43%, наше 56%. Это решает потолок всего
   трека: при 92.5% ускорение гостя вдвое даёт кадр 1.86x, при ~37% — 1.23x. Разрешить
   это противоречие НАДО до следующего кандидата: `frameReport` должен делить residual тем
   же классификатором, что `analyze-trace`.

## Разрыв надо мерить наклоном: одиночный замер холодный

`JIT_THRESHOLD` — 200 000 retired-инструкций (jit.rs:1870), компиляция асинхронная, и V8 ещё
поднимает Liftoff→TurboFan внутри фазы длиной 100–700 мс. Всё это ФИКСИРОВАННАЯ стоимость: она
не растёт с числом итераций. Поэтому демка собирается в ДВУХ объёмах работы, а разрыв берётся
как наклон `(t_hi − t_lo) / (n_hi − n_lo)`.

k3, 4.096M против 16.384M итераций:

| Величина | Значение |
| --- | ---: |
| Наклон, наш эмулятор | 20.51 нс/итерацию |
| Наклон, Emscripten | 1.61 нс/итерацию |
| **Разрыв по наклону (установившийся)** | **12.75x** |
| Отношение одиночных замеров (холодное) | 20.88x |
| Фиксированная стоимость, вычтенная наклоном | 58 мс из 142 (41% малого прогона) |

То есть все ранее приведённые в этом документе однократные отношения — **верхняя граница
«холодный старт плюс разрыв кодогенерации»**, а не разрыв. Инструмент: `codegen-slope.ts`.

## Вес x87 измерен в кадре игры, а не в демке

Relaxed-FPU переключается в рантайме и стоит 3.1x на x87-ядре. Переключение ВНУТРИ одной гонки
NFSU, шесть окон в порядке 0-1-1-0-1-0, сброс JIT-кэша и прогрев на каждом переключении, все
шесть окон прошли проверки сцены/presents/физики, `mover/кадр` = 12.00 в каждом:

| Relaxed FPU | FPS |
| --- | ---: |
| выключен | 14.44 |
| включён | 17.12 |
| **отношение** | **1.186** |

Отсюда прямо считается доля x87 во ВРЕМЕНИ кадра: `frame_off/frame_on = 1 + (k−1)·t` при
k = 3.1 даёт **t = 8.9% времени кадра** (при уже включённом relaxed). Цензус в той же гонке даёт
x87 = 8.82% retired-инструкций — доли по времени и по инструкциям сошлись, что и есть контроль
на осмысленность обеих цифр.

**Потолок x87-направления, посчитанный ДО постройки кандидата:** довести x87 до уровня
целочисленного пути (63x → 12.75x, то есть 4.9x) даёт **+7.6% FPS**; вдвое — +4.6%. Это
реальный, но не кратный выигрыш, и теперь он число, а не ожидание от «63x».

## Как воспроизвести

```powershell
node tools/bench-v86/source-pair/build-codegen.mjs
bun tools/bench-v86/source-pair/codegen-capture.ts k1 k3 --seconds 18
node tools/probes/wat-ops.mjs logs/codegen-pair/k3/cgk3.wat
node tools/probes/wat-ops.mjs C:/Projects/bottleship-demos/demo_codegen_pair/web/codegen.wat cg_k3_stride
node tools/probes/wat-breakdown.mjs logs/codegen-pair/k3/cgk3.wat
node tools/bench-v86/source-pair/codegen-oracle.mjs 3 4096 1000 73      # эталонная рука + сумма
bun tools/bench-v86/source-pair/codegen-bench.ts k3 --runs 3 --expect <сумма>
```

Артефакты сборки: `C:/Projects/bottleship-demos/demo_codegen_pair` (`build.json`
содержит точные команды, версии и хеши, а также `sectionMap` со страницами ядер).
Захваченные модули и `capture.json` — в `logs/codegen-pair/`.
