# x87 pair guard: BYTEmark и браузерная проверка

Продолжение `v86-x87-pair-guard-experiment-2026-09-05.md`. Цель общего значительного ускорения v86 **не достигнута**. Кандидат пока не внесён в production codegen/Wasm.

## BYTEmark

Две корректные сборки из одного snapshot: baseline `c361f247…`, candidate `816054b9…` (полные хеши в предыдущем отчёте и manifest). SHIPPING_JIT целиком, idx21=0, relaxed=1. Свежий fs boot на руку. Порядок AB/BA/AB, три пары; ни одна рука не выброшена. Raw: `tools/bench-v86/results/x87-bytemark-3fSXf0`.

Парные throughput deltas: FOURIER **+5.65%, +3.31%, +0.91%**, медиана **+3.31%**; LU **+2.74%, +0.94%, +3.00%**, медиана **+2.74%**. Часы гостя/хоста согласованы, config readback проходит, tier2 promotions=0.

Это положительный сигнал шире synthetic add loop, но N=3 и нет отдельного A/A floor этой кампании. BYTEmark по-прежнему guest-timed, а не fixed-work. Точная величина и общий игровой эффект не доказаны.

## Браузер

Новый browser runner использует **тот же** `x87-workload.mjs`, что Node: те же guest bytes, абсолютные результаты, retired oracle, JIT-entry envelope и запрет новой компиляции внутри окна. Новые экземпляры v86, отдельный Chrome profile/server; игровая вкладка и production-файлы не затрагиваются. HeadlessChrome 153, без V8 performance overrides. Серии последовательные, BYTEmark к этому моменту завершился.

Порог разброса arm medians — 10%, контрольный median delta — не более 3%, ни одна пара не отбрасывается. Контрольный memory-код побайтно одинаков между руками. `judge-x87-browser.mjs` выдаёт ненулевой exit code при отказе.

Все три серии сохранены:

1. **`x87-browser-TkBQE0`** — порядок по рукам, в каждой три ядра. Все шесть пар spread выиграли, но разброс arm medians ~14%, контроль тоже нестабилен. **Гейт FAIL.**
2. **`x87-browser-FSe0lJ`** — порядок по ядрам, соседние A/B без двух других тестов между ними. Spread: медиана времени −19.21%, разброс 3.70%/5.02%; memory: +1.02%, разброс 3.83%/5.12%. Но baseline pair имеет 16.76% разброса, а одна A/A пара pair разошлась на 32.46%. **Общий гейт FAIL.**
3. **`x87-browser-PeMxrg`** — тот же порядок, по одному удерживаемому `WebAssembly.Module` на arm через документированный `wasm_fn`, при свежих Instance/memory на каждом запуске. Проверена гипотеза влияния повторной компиляции самого engine. Выбросы сохранились. **Гейт FAIL.** Это не доказанная причина шума и не разрешение принять эту серию.

В каждом каталоге: полный `result.json`, `result.judgement.json`; временные улучшения протокола и отвергнутые результаты не скрыты. Последующий запуск нельзя выдавать за первую попытку. Настройки V8 и порог 10% ради зелёного результата не менялись.

## Решение

У pair guard есть устойчивый Node fixed-work выигрыш на независимых накопителях и положительное направление на BYTEmark. Но общий browser acceptance не пройден, поэтому патч остаётся экспериментальным. Большой процент на одном x87 loop не заменяет требуемый значительный прирост v86 на широком workload.

Следующий кандидат — idx21 и контракт FP/conversion helpers. Предварительное чтение показывает конкретные функции, меняющие только FPU/SW/scratch, которые сейчас оплачивают полный flag spill/reload. Нужен точный whitelist по проверенным функциям, без обобщения на `fpu_*`: FCOMI/FCOMIP явно меняют EFLAGS и должны сохранить синхронизацию. Сам idx21 остаётся OFF в shipping. Это ещё гипотеза для отдельной реализации и проверки, не заявленный выигрыш.

Команды:

```powershell
node tools/bench-v86/run-x87-bytemark-pairs.mjs <pair-manifest.json>
bun tools/bench-v86/run-x87-browser.ts <pair-manifest.json>
node tools/bench-v86/judge-x87-browser.mjs <result.json>
```
