# Handoff: рост FPS v86, NFSU и WBUF

Обновлено 10 сентября 2026. Документ предназначен агенту, который продолжит работу
без истории переписки. **Цель пользователя — получить проверенный рост FPS. Она
ещё не достигнута.** Не подменять её уменьшением размера Wasm или ускорением
отдельного микробенчмарка. AOT для устранения холодных компиляционных хитчей —
отдельная полезная ось, не доказательство ускорения прогретой игры.

## Начать отсюда

1. Прочитать этот документ и `CLAUDE.md`, проверить текущие изменения файлов.
2. Проверить живые процессы и браузер. Не перезапускать существующий стенд только
   потому, что предыдущая команда ожидания закончилась.
3. Продолжить изолированное сравнение движков, описанное ниже. Последняя работа
   остановилась **после добавления выбора движка, до первой загрузки игры с ним**.
4. Следующий содержательный результат — измерение игры на baseline/candidate
   с контролем шума и семантики, а не ещё одна декларация перспективности WBUF.

## Какой стенд поднят

Страница: <http://127.0.0.1:5174/tools/bench-v86/source-pair/nfsu-entry.html>.
Один клик **«Войти в эталонную гонку»** загружает:

**NFS Underground / синий Skyline / Free Run / Olympic Square / без трафика /
максимальные настройки / один игрок.** Skyline принят пользователем вместо Golf.
После проверки сцены эмулятор оставляется на паузе. Во время замеров не рулить.

Это воспроизводимый вход в похожую сцену, **не побитовый savestate** и не гарантия
одинакового объёма работы без счётчиков. NFSPU выбрана пользователем второй игрой,
но её аналогичный стенд ещё не подготовлен.

Фактический bundle: `G:/WGB/running/nfs-underground.wgb`, доступ через существующий
`diskBundleUrl`, без копирования всей игры в репозиторий.

Механизм входа (`nfsu-entry.mjs`):

1. Создаёт iframe с отдельной сессией; сбрасывает сохранённые worker flags.
2. Делает backup пяти файлов профиля/настроек, записывает встроенную fixture
   `nfsu-entry-settings.json`, проверяет чтением точные байты.
3. Сохраняет предыдущий manifest override, добавляет `skipVideo:true`.
4. До построения BootFlow временно меняет два проверенных операнда списка экранов,
   направляя игру к выбору профиля. Использует `writeGuestCode` с инвалидированием
   JIT в том же JS-вызове. На экране профиля восстанавливает исходные инструкции
   **до измерений**. Если момент упущен, есть более медленный визуальный fallback.
5. Выбирает профиль, ждёт проверенное главное меню. Проверяет четыре сигнатуры
   кода, задаёт параметры и ставит штатный initializer игры в её очередь перехода.
   Прямого переписывания EIP для запуска гонки нет.
6. Проверяет отсчёт → активную гонку, продвижение физики и presents, изображения
   сцены/машины, режим 3, трассу 1003, трафик 0, одного игрока; ставит паузу.

Для ориентирования в адаптере: mode `0x777cc8`, track seed `0x7589e8`, traffic seed
`0x7589f8`, pending initializer slot `0x77a904`, initializer `0x4b5c00`.
Сигнатуры/визуальные шаблоны находятся в `nfsu-entry-guards.json` и
`nfsu-entry-templates.json`. Использовать адаптер, а не повторять записи вручную.
Идею Movies overlay с нулевыми видео не внедряли: рабочее решение — BootFlow.
`?menu=1` сохраняет старый, более медленный путь меню с Golf как диагностику.

## Как пользоваться

На момент handoff проверены слушающие процессы:

| Сервис | Адрес | PID на момент проверки |
| --- | --- | ---: |
| Vite | `127.0.0.1:5174` | 34572 |
| Collector | `127.0.0.1:63028/record` | 68584 |

PID/порты могут измениться. Проверка PowerShell:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 5174,63028
Get-Content tools/bench-v86/source-pair/navigation-record-config.json
```

Если сервисы действительно остановлены, запустить из корня в отдельных терминалах:

```powershell
bun run dev -- --host 127.0.0.1 --port 5174 --strictPort
bun tools/bench-v86/source-pair/navigation-record-server.ts
```

Collector выбирает свободный порт и **новую** `logs/nfsu-navigation-*`, записывает
endpoint/directory в `navigation-record-config.json`. Не запускать дубликат без
нужды: он переключит будущие записи в другую папку. Для запуска фоновых процессов
через Start-Process использовать `-WindowStyle Hidden`.

Origin должен быть именно `http://127.0.0.1:5174`: collector проверяет Origin.
OPFS этого origin отделён от localhost, но общий между его вкладками. Не вести
параллельно другую игровую сессию на том же origin во время опыта.

В интерфейсе есть три кнопки:

- **Войти в эталонную гонку** — новый guest и восстановление сцены.
- **Снять профиль готовой сцены** — clean window и отдельная инструментированная
  фаза через `nfsu-profile.mjs`; не нажимать во время другого замера.
- **Запустить текущий эксперимент** — динамически импортирует
  `nfsu-experiment.mjs?run=<timestamp>` и вызывает `run(context)`.
  Можно менять эксперимент на диске и нажимать эту кнопку **без reload**, сохраняя
  текущую сцену. Сейчас `run` снимает глобальные WBUF hits/fallbacks за 5 секунд,
  а не сравнивает FPS движков.

Контекст эксперимента: `{call,save,note,sleep,scene}`. `call(cmd,...args)` вызывает
существующий harness iframe и бросает исключение при ошибке. `save(kind,data)`
сохраняет JSON через collector. `scene` — worker-код получения состояния гонки,
present serials, raw intervals, JIT config и compile count. Cleanup ставит паузу.
В файле сохранены также `hotspots` и `memoProbe`; helper census и AOT paired —
отдельные импортируемые модули, перечисленные далее.

До прерывания IAB имел browser `1`, tab `4`, эта страница; гостевая игра стояла
на паузе. **Финальная проверка при записи handoff вернула пустой список вкладок**:
tab 4 больше недоступна. Поэтому следующему агенту нужно открыть страницу и
заново выполнить вход; не рассчитывать на живую paused-сцену. Сервисы и evidence
сохранились. ID/состояние перепроверять через CUA. Перед завершением работы с вкладкой вызвать
`markHandoff()`, иначе созданная агентом вкладка может закрыться. Не делать reload
просто для смены `nfsu-experiment.mjs`.

## WBUF: найденный кандидат

Подробности: [wbuf-routing-2026-09-10.md](wbuf-routing-2026-09-10.md).
В `vendor/v86/src/rust/jit.rs` helper `jit_wbuf_intrinsic_execute` сначала ищет
дескриптор в трёх HOT-копиях, затем в canonical hash table. Широкий min/max guard
в `jit_instructions.rs` пропускает и нерегистрированные AddRef/Release.
Они должны исполняться обычным путём: **не удалять refcount-операции**.

Изолированные сборки и Wasm→Wasm fixed-work loops (8 ABBA quartets, 8M calls/window):

| Изменение | Flat misses ratio | Flat scalar hits ratio | Решение |
| --- | ---: | ---: | --- |
| Miss cache до HOT | 1.943 | .894 | Отклонён: замедляет успехи |
| Miss cache после HOT | .884 | .911 | Отклонён |
| Только canonical hash table | 1.880 | 1.695 | Кандидат; с paging 1.436 / 1.207 |

Ratio = baseline time / candidate time. Это **не FPS**. Flat проверки: 88,
paged: 100 across both arms; разрешения, nonidentity mapping, page crossing,
registry lifecycle, capacity, no memory mutations on decline. Throughput покрывает
скалярные записи, не shader payloads и не реальное смешанное распределение/TLB игры.

Дополнительный hot-lifecycle probe выявил разницу: register ID77 → mark_hot →
register ID88 без повторного mark_hot даёт baseline ID77 (старая копия), candidate
ID88. После повторного mark_hot оба дают88. Нельзя утверждать безусловную
эквивалентность. TS `registerWbufDynarecIntrinsic` обычно повторяет mark_hot при
переданном hotSlot; нужно определить контракт и проверить остальных callers.

Архивы: `wbuf-miss-before-hot/`, `wbuf-miss-after-hot/`, `wbuf-hash-first/`
в основной evidence-папке. Последний содержит исходники обеих рук, `.wasm`,
manifest, raw timing/correctness/lifecycle JSON и снимки скриптов.
Пути внутри manifest указывают на исходную temp-папку; архивные `.wasm` лежат рядом.

Скрипты в `tools/bench-v86/`:

```powershell
node tools/bench-v86/prepare-wbuf-miss-cache.mjs --hash-first
node tools/bench-v86/test-wbuf-miss-cache.mjs <manifest.json>
node tools/bench-v86/test-wbuf-miss-cache.mjs <manifest.json> --paging
node tools/bench-v86/test-wbuf-hot-lifecycle.mjs <manifest.json>
```

Preparer копирует исходники в новую temp-папку и собирает cargo release, включая
zstd object и тот же linker/config; shipping source не редактирует. Требуются
локальные Rust/wasm target и emsdk wasm-as. Тесты отказываются перезаписывать результаты.
Baseline rebuild **побитово совпал** с текущим shipping binary.

## Незавершённое изменение перед handoff

Добавлена инфраструктура для первой проверки кандидата в игре; **её ещё не
использовали для загрузки гостя и не проверили typecheck**. Только `node --check`
для `nfsu-entry.mjs` прошёл. Следующему агенту проверить diff и boot.

- `src/worker/emulator.worker.ts`: DEV-only worker flag `__v86LabWasmPath`,
  принимающий только `/apps/source-pair-lab/engines/<64 hex>.wasm`.
- `src/worker/core/cpu/aot-cache.ts`: `engineFingerprint()` отказывает AOT save/load
  при таком override. Сейчас обычная реализация читает `/v86.wasm`, а не фактически
  загруженный binary; поэтому переиспользование AOT для другой сборки небезопасно.
  Защиту не снимать без привязки identity к загруженным байтам.
- `nfsu-entry.mjs`: query `?engine=<hash>` проверяет SHA256 файла, после reset flags
  выставляет override и `__aotNoAutoLoad=true`, пишет `engine-selection` evidence.
- В `public/apps/source-pair-lab/engines/` скопированы обе изолированные сборки.
  Это крупные лабораторные artifacts; не коммитить автоматически.

Baseline hash (текущий `public/v86.wasm`, 2600550 bytes):
`9aa38d8bf99d9b6d8c8371605c9d2070edaeb6af28de8e9d6f07ae86210af276`.

Candidate hash (2599898 bytes):
`3ee78d780847f28bd69a1def4eabfc5cc59dfc2bff70e178468c6d4a356294c0`.

Открыть entry URL с соответствующим `?engine=...` и нажать вход. **Обе руки**
должны использовать этот режим fresh JIT, затем одинаковый прогрев. Нельзя
сравнивать original с готовым AOT против candidate с холодным JIT.
Обычный URL без engine сбрасывает flags при следующем клике входа и возвращает
штатный выбор движка. Само открытие URL ещё не загружает игру.

До прерывания исходная подготовленная сцена работала на обычном движке;
при финальной проверке вкладка уже отсутствовала.
Основной `public/v86.wasm` не заменён WBUF-кандидатом; его SHA проверен при handoff.

## Дальнейшая стратегия и критерий приёмки

1. Разрешить hot descriptor update contract; расширить differential correctness
   на shader payloads, aliases и реально конфликтующие зарегистрированные targets.
2. Проверить новый DEV engine selector: успешный boot, фактически загруженные
   байты/версия, отказ несовместимого AOT, возвращение к обычному режиму.
3. Добавить отдельный engine comparison runner. Свежие одинаковые входы, одинаковый
   прогрев, несколько заранее заданных ABBA/BAAB серий и A/A контроль. Во время
   timing не собирать Rust, не запускать тяжёлые проверки, screenshot/census.
4. Сохранять raw frame intervals, scene параметры, physics/present deltas,
   JIT compile counts, work/frame и WBUF counters. Отделять compile/hitches от
   steady-state. Если raw ring ограничен, выбирать окна без потери кадров.
5. Принимать FPS выигрыш только если он повторяется на независимых входах и
   превышает измеренный контрольный шум. Одного удачного окна недостаточно.
   Не убивать чужие фоновые процессы: наблюдался шум хоста, но его причина не
   доказана. При необходимости выбрать спокойный интервал и задокументировать.
6. Если hash-first не даёт игрового выигрыша, сохранить отрицательный результат,
   перейти к точному membership guard/descriptor routing до helper. Инвалидация
   при register/clear обязательна; отсутствие цели в профиле не доказательство
   невозможности вызова. Бюджет/исключения/порядок drain сохраняются.
7. Дальше анализировать WBUF batching/coalescing только с контрактами lifetime,
   readback и drain ordering, а не удалением кажущихся лишними вызовов.
8. Подтверждённого кандидата проверить в движении и на NFSPU; cold AOT hitches
   оценивать отдельным маршрутом, особенно на старой физической машине.

Исходная идея пользователя остаётся полезной: парные демки одного C++ источника
через C++→Windows PE→v86 JIT Wasm и C++→emsdk Wasm. Native emsdk — образец формы
вычисления, не обещание достижимого коэффициента. Калибровать burst lengths,
OUT/гипервызовы, locality и live state через границы по реальному профилю игры.
WBUF сейчас — более конкретная гипотеза из измерений; не строить заново лабораторию,
пока существующие инструменты позволяют проверить её.

## Продолжение 10 сентября: селектор движка проверен, стенд дрейфует

Незавершённая инфраструктура доведена до работающего состояния и **исправлена по
существу**: как она была написана, обе руки молча грузили бы shipping `/v86.wasm`.

- Движок выбирается в `initV86`, который вызывается на сообщении `init` — то есть при
  создании iframe. `setWorkerFlag` после появления harness персистит флаг только для
  reload, которого `openWgb({reload:false})` не делает. Теперь `nfsu-entry.mjs` пишет
  флаги в `bs_debug_flags:nfsu-entry` **до** создания iframe и отказывается стартовать,
  если origin-wide `bs_debug_flags` непуст.
- `emulator.worker.ts` публикует `__v86EngineLoad` — путь, длину и SHA-256 **фактически
  инстанцированных** байт (из `sourceBytes` загрузчика). Вход сверяет их с запрошенным
  хешем и падает при расхождении. Без этого A/B сравнивал бы бинарь сам с собой.
- Проверено данными: `engine-selection` записал sha256
  `3ee78d78…` / 2 599 898 байт, и игра на кандидате дошла до валидированной гонки.
- `bun run typecheck` — чисто.

Новое: `engine-series.mjs` — runner серии. Рука = свежий вход + одно окно
(`nfsu-experiment.mjs` → `run`, kind `engine-window`) с проверками сцены, presents,
физики, отсутствия компиляции и совпадения JIT-конфига. `nfsu-entry.mjs` экспортирует
`window.__nfsuEnter(hash)`, поэтому руки чередуются без перезагрузки страницы.
Инвариант числа интервалов уточнён до `frames` или `frames-1`: сброс каденции идёт на
работающем госте, и это гонка двух чтений, а не потеря кадров (выход за ±1 по-прежнему
отказ — он и сработал дважды).

**Главный результат этой сессии — не число, а то, что стенд в текущем виде не может
ответить на вопрос о процентах.** BAAB (`series-summary`):

| Позиция | Рука | FPS | p50 мс | mover/кадр |
| ---: | --- | ---: | ---: | ---: |
| 1 | B кандидат | 18.29 | 52.11 | 11.61 |
| 2 | A база | 17.87 | 53.37 | 11.74 |
| 3 | A база | 16.22 | 58.15 | 11.83 |
| 4 | B кандидат | 14.21 | 64.96 | 12.00 |

Спад монотонный по ПОЗИЦИИ, а не по руке: −22% за четыре руки (~6 минут). Одиночные
окна в начале сессии давали 19.52 / 19.16 / 19.62. Формально квартет BAAB гасит
линейный дрейф и даёт ratio .9536 (кандидат медленнее), но спад ускоряющийся, а не
линейный, поэтому внешняя пара наказана — **это не приёмочное измерение ни в какую
сторону**. Перезагрузка страницы не восстановила скорость (16.08), значит накопление
не в состоянии страницы.

Ещё одно наблюдение, важное для семантики: `mover/кадр` растёт с падением FPS
(11.61 → 12.00). Работа гостя на кадр не постоянна — при меньшем FPS кадр дороже,
то есть дрейф самоусиливается, и FPS-руки не сравнивают одинаковый объём работы.

Следующий шаг — причина дрейфа, до любых новых заявлений о WBUF.

## WBUF hash-first закрыт расчётом потолка, а не ещё одной серией

Стоимость вызова взята из уже снятых изолированных fixed-work прогонов
(`wbuf-hash-first/fixed-work-*.json`, медианы по 16 окнам на режим), частота — из
`engine-window` этой сессии (5498 hits и 7532 fallbacks на кадр):

| Режим | baseline нс/вызов | candidate нс/вызов | Экономия |
| --- | ---: | ---: | ---: |
| hit, paged | 46.71 | 38.82 | 7.9 |
| miss, paged | 7.43 | 5.24 | 2.2 |
| hit, flat | 16.89 | 9.97 | 6.9 |
| miss, flat | 7.45 | 4.16 | 3.3 |

5498·7.9 нс + 7532·2.2 нс = **60 мкс на кадр** при кадре 54.13 мс — **0.11%**.
Оптимистичный flat-вариант даёт те же 0.12%. Ratio 1.44–1.88 в микроцикле реален и
не переносится: он относится к доле кадра, которой почти нет.

Это на два порядка ниже разброса стенда, поэтому две серии и дали противоположный
знак (.9536 и 1.0202). **Отрицательный результат: hash-first нельзя принимать как
источник FPS, и дальнейшая работа по WBUF-маршрутизации не окупается.**
Корректностные находки (hot-lifecycle расхождение ID77/ID88, контракт mark_hot)
остаются в силе как вопрос корректности, а не производительности.

## Что на самом деле мешает мерить, и куда идти дальше

Шум стенда измерен, а не предположен:

- Один и тот же baseline-бинарь за сессию: 19.52, 19.16, 19.62, 16.08, 16.40,
  12.81, 14.89, 17.01 FPS. Разброс одинаковых рук внутри одной серии — до 12%.
- Частота CPU при этом держится 110–113% (`% Processor Performance`), то есть
  троттлинга нет; колеблется фоновая загрузка хоста (`% Processor Utility` 11–70%
  от посторонних приложений).
- Перезагрузка страницы и четырёхминутный простой скорость не восстанавливают,
  так что дело не в состоянии страницы и не в накоплении внутри вкладки.
- Замер в отдельном CDP-браузере (`engine-series-cdp.ts`) правильнее по изоляции,
  но сам по себе разброс не убирает.
- `mover/кадр` растёт с падением FPS (11.6 → 12.0): при просадке кадр дороже,
  то есть руки сравнивают не одинаковый объём работы.

Отсюда два вывода для следующего агента.

1. **Порог обнаружения.** Последовательные руки на этом хосте разрешают в лучшем
   случае десятки процентов. Кандидат уровня единиц процентов требует
   ПЕРЕКЛЮЧАЕМОГО В РАНТАЙМЕ изменения, чтобы руки чередовались внутри одной
   загрузки посекундно; тогда дрейф хоста сокращается. Собирать это стоит только
   под кандидата с осмысленным потолком.
2. **Где вообще лежит время.** По профилю кадра: 54.13 мс, из них v86 residual
   50.36 мс, thunk 3.70 мс. Любой кандидат вне исполнения гостевого кода борется
   за считаные проценты. Прежде чем строить очередной изолированный движок, надо
   оценить его потолок так же, как сделано выше для WBUF — умножением измеренной
   удельной стоимости на измеренную частоту. Ранее сработавший в этом классе
   рычаг — качество кодогенерации JIT (branch hints, +12–14%), а не маршрутизация
   хелперов.
