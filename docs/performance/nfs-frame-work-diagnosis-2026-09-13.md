# NFSU / NFSU2 против Bard's Tale: выполненная диагностика

13.09.2026. Только offline-анализ существующих записей; игровой runtime не изменён.

## Что сделано

1. Повторно разобраны три исходных Chrome trace. CPU-сэмплы обрезаны по одному
   и тому же для каждого trace окну: первый flip включительно → последний
   flip исключительно. Нормировка по числу **интервалов**, не числу меток.
2. По полным именам Rust-функций раскрыта категория Wasm hypercalls; по дереву
   стеков посчитано время отдельных путей без повторного сложения рекурсивных вызовов.
3. Посчитаны реальные `DawnClientSerializer::Flush` и сумма их `args.bytes`
   на том же worker и в том же окне. Это размер сериализованных команд Dawn,
   **не** объём текстур, число draw или число `GPUQueue.submit`.
4. Все сохранённые top-50 EIP NFSU/NFSU2 пересечены с имеющимися libid-индексами.
5. Проверен механизм EIP-сэмплера. Его ограничение воспроизведено отдельным
   исполняемым Wasm-примером, без браузера и без загрузки игр.

Строки CPU **пересекаются**: capture включает дочерние операции, а drain —
обслуживание draw. Их нельзя складывать. Время `hypercall_eagl` включает вызываемые
помощники; поэтому оно больше суммы self-time Rust-функций с этим именем.
`drainWriteBuffer` self-time в NFSU — всего 0.476 мс/кадр: 11.302 мс нельзя
представлять как цену механики очереди или как полностью устранимые затраты.

NFSU относительно Bard: сериализованных байт **5.66×**, flush **2.52×**,
работы под drain **8.07×**, подготовки snapshot **10.64×**. Это уже измеренная
разница работы нашего графического пути, а не вывод из возраста или внешнего вида игры.
Однако без API-count/byte-upload census нельзя разделить число draw, сложность
состояния одного draw и накладные расходы на операцию. Делить CPU-время на байты
Dawn и объявлять получившееся «ценой draw» также нельзя.

## Найденный дефект атрибуции: EIP-сэмплер видит границы исполнения

`src/worker/core/diagnostics-commands.ts`, `dumpHotJitBlocks`:
`setInterval` в самом worker читает `cpu.instruction_pointer` и фильтрует
`scheduler.intentionalYield` / `v86.running`. Таймер на этом event loop не
может исполниться **внутри синхронного захода в Wasm**. Фильтр stopped не
превращает его в прерывающий CPU-профилировщик. Он наблюдает сохранённый EIP
между заходами; это полезный адрес для RE границы, но частота такого адреса
не является долей времени исполнения гостевой функции.

Воспроизведение: `logs/frontier-review-20260912/eip-sampler-repro.mjs` создаёт
Wasm с доступным JS глобальным `ip`. Внутри цикла `ip=HOT`, перед возвратом
`ip=YIELD`; рядом стоит `setInterval(1)`. Выполнены 40 заходов по 20 миллионов
итераций: **168.803 мс внутри Wasm, HOT=0, YIELD=79**. Это проверка механизма,
не замер игры и не сравнение производительности движков Bun/Chrome.

Показательный адрес NFSU2: `0x006f5b4d` получает 118 наблюдений, первое место
среди сохранённых EIP. Уже извлечённое тело
`tmp/nfsu2-eagl/decompiled-006f5b4d.c` показывает callback с `GetTickCount`,
самопланированием через `timeSetEvent` и вызовами помощников. Нельзя делать из
этого вывод «callback потребляет 22% кадра». Независимый Chrome CPU profile
лидирует другими сгенерированными модулями: `g00575340` и `g0066404c`.
Их имена тоже не дают права приписать всё время модуля одной исходной функции.

Новый `tools/probes/luna-nfsu-eip-census.ts` снимает весь хвост, но использует
тот же `setInterval`. Он исправляет усечение, **не** смещение по границам исполнения.
Увеличение длительности этого census не исправит механизм измерения.

Для временного ранжирования исходных гостевых функций нужен независимый CPU
sample → точный Wasm PC → guest-range mapping для реально опубликованных JIT/AOT
модулей. Альтернатива — явный учёт гостевых регионов с измерением своего overhead.
Счётчики блоков по retired instructions отвечают на другой вопрос: объём
гостевой работы, не host-время. До появления такой связи сортировка
«время библиотечной функции × число игр» не обеспечена данными.

Это **числа наблюдений**, не доли кадра. Непопадание в сигнатуры или в два
посторонних образа не доказывает, что код собственный: вывод libid `game`
в этом отчёте намеренно переведён в `unknown` с сохранением исходного ответа.
Совпадение с функцией внутри donor D3DX тоже требует семантической проверки:
сам donor может содержать CRT/helper общего происхождения. Называть любой
совпавший helper специфичным для D3DX нельзя.

## Что снимать первым после восстановления стенда

1. **Сопоставимый census рендер-команд NFSU/Bard**: дельты фактических draw,
   setters (с эффективными изменениями), размер констант snapshot, upload bytes
   по причине, flush/submit и present serial за один интервал. Проверить
   равенство submitted/encoded/consumed draw. Найденные 5.66× байт дают
   конкретную проверяемую цель: установить, какой класс команд создаёт эту разницу.
   Для NFSU2 аналогичная строка даёт 2.65× байт и 5.13× CPU под drain.
2. **Семантические участки D3DX effect / подготовка draw**, где можно убрать
   повторный проход целиком. В NFSU HLE уже работает: 6.088 мс находится под
   нашим EAGL. В NFSU2 этот путь не наблюдается, и новый ABI действительно нужен
   (см. `nfsu2-eagl-re-2026-09-12.md`). Из этих фактов нельзя вывести размер
   будущего ускорения NFSU2: его гостевой runtime ещё не имеет надёжной временной границы.
3. `eagl_read32_cold` — **не повод ещё раз запускать старый cache-эксперимент**.
   Просмотрен действующий код: один page-tag, замена при новой странице,
   сброс по выбранной политике, отдельный перевод/проверка на miss. Чтение
   vtable → stub → state закономерно ходит по разным страницам. Уже испытанный
   n-way cursor дал 1.007 / 0.994. Даже полное удаление измеренных 1.857 мс
   означает только около +2.9% FPS в этой записи. Приоритет ниже целых проходов.

Свежий игровой A/B здесь не проводился. Соседний отчёт
`nfsu-race-stand-down-2026-09-13.md` фиксирует падение стенда до гонки; это
существующее наблюдение, не повторно проверенный в этой работе отказ.
В общем дереве параллельно изменяется runtime. Ускорения от этой диагностики
не заявляются; код игры/эмулятора не изменён.

## Воспроизводимость и проверки

```
bun logs/frontier-review-20260912/frame-work.ts logs/p0-item1-race.json.gz logs/frontier-review-20260912/nfsu-frame-work.json
bun logs/frontier-review-20260912/frame-work.ts logs/prof-nfsu2.json.gz logs/frontier-review-20260912/nfsu2-frame-work.json
bun logs/frontier-review-20260912/frame-work.ts logs/bards/armG-60s.json.gz logs/frontier-review-20260912/bards-frame-work.json
python logs/frontier-review-20260912/join-eips.py
bun logs/frontier-review-20260912/eip-sampler-repro.mjs
```

Каждый JSON содержит SHA исходного trace, worker, границы окна, число
интервалов, все self-time строки и стеки. Покрытие CPU samples в окнах — 100%
для NFSU/Bard и 99.959% для NFSU2: 6.073 мс его окна вне покрытия профиля,
они не приписаны функциям и не восстановлены догадкой.
Отрицательные V8 timeDeltas обработаны монотонной границей без двойного учёта
пересечения; их число и сумма сохранены. Проверка на независимой синтетической
записи с обрезанием первого/последнего сэмплов, обратным timestamp и remap
профиля с profiler thread на worker дала A=30, B=90, C=40 мкс, сумму 160 мкс.

Записи относятся к разным сценам/сборкам и не являются контролируемым A/B.
Ledger гостевых present в этих trace отсутствует; полнота кадров им не доказана.
Telemetry заполнения trace buffer для длинного Bard capture отсутствует.
Связь SHA guest EXE с конкретным trace не сохранена. Эти ограничения сохранены
в выводах; разница строк таблицы не названа устранимым временем.
