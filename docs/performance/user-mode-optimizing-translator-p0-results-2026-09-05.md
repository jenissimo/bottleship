# P0 results: measured attribution, the selected kernel, and the MMU contract

Дата: 2026-09-05. Статус: выполненный этап P0
[плана реализации](user-mode-optimizing-translator-implementation-plan-2026-09-04.md).
Всё ниже — измерения и исполнимые проверки; ни одного performance claim о трансляторе здесь нет.

## Итог в одном абзаце

Два блокера P0 закрыты. (1) Снята реальная attribution на живой NFSU: **корпус `k3`/`k4`/`k5`
несёт 0.00% работы гостя** в обеих снятых сценах, поэтому P0-kernel выбран заново — по
измеренной доле CPU-времени, а не по форме инструкций. Новый кейс `k8` = байт-точная функция
`Speed.exe` VA `0x0064a71f`, **10.03% всех retired guest instructions in-race**. (2) Оракул
получил настоящие MMU-сценарии (#PF через собственный IDT-gate, A/D-биты как сравниваемый
эффект), закрыв `permission_fault_gate: BLOCKED` из `k3-differential`.

## 1. Как снималась attribution

`tools/aot/opt/capture-attribution.harness.ts`. Вход в сцену — **воспроизведение записанного
человеческого прогона** (`logs/recordings/nfsu-to-race.json`, 52 сэмпла) через `hostReplay`,
gated по present serial. Это не «нажать Enter восемь раз»: два прогона key-скрипта попадают в
разные места, а весь смысл упражнения — воспроизводимый знаменатель.

Три окна снимаются раздельно, потому что они несовместимы:

| Окно | Что даёт | Почему отдельно |
|---|---|---|
| clean (disarmed) | единственный источник p50/p95 | `trace2` arming инструментирует каждый блок на армированной странице и замедляет гостя |
| counted (armed) | `exec * static instructions` по блокам | count-weighted, иммунно к загрузке машины |
| sampled | EIP-сэмплинг → `module+rva` | time-weighted, но см. §3 — ранжирует yield-точки |

Сцена проверяется `sceneProbe`, причём по **каждому** сэмплу, а не по среднему: один
переходный кадр вытягивает среднее статичного экрана выше любого порога — статичная сцена ниже
набрала `motion` 0.72 при отдельных сэмплах 2.06 / 0.03 / 0.08 и прошла бы порог по среднему.
Прогон отказывается, если хотя бы один сэмпл ниже порога.

## 2. Результат: корпус не на горячем пути

Две сцены, оба раза одно и то же.

**In-race** (motion 21.5, покрытие census = **76.0%** всей retired-работы — это
`countedCoveragePct`, то есть весь census; сумма возвращённых top-60 строк даёт 73.42%, и
именно её первая версия скрипта печатала под этим ярлыком):

| Страница | Доля всей работы гостя |
|---|---:|
| `0x64a000` | 49.01% |
| `0x585000` | 11.35% |
| `0x64b000` | 9.18% |
| `0x684000` | 3.61% |
| `0x649000` | 0.28% |
| **`k3` / `k4` / `k5`** | **0.00% / 0.00% / 0.00%** |

**Статичный экран.** Второй прогон, снятый одноразовым пробником до того, как скрипт захвата стал
общим: покрытие 77.32%, `0x585000` = 57.5%, `0x684000` = 18.3%, `k3`/`k4`/`k5` снова 0.00%,
страница `0x5d4000` живая на 1.23% — но **ни один блок не входит внутрь 16 байт `k3`**. То есть
дело не в том, что страница холодная: горячий код на ней — другие функции.

Оговорка к этим числам: JSON того пробника не сохранился и §9 его не воспроизводит, поэтому
проценты здесь **нечем перепроверить**. Load-bearing вывод — 0.00% у корпуса — держится не на
них, а на in-race прогоне выше, чей артефакт (`tmp/p0-attribution-race.json`) на месте.
Качественное наблюдение про spin-wait (§3) тоже независимо: оно следует из дизассемблирования
`0x585bf0..0x585c1c` и `__allshr`, которое воспроизводится из бинаря одной командой
`python tools/pe-disas.py`.

Инвентарь [kernel-inventory](user-mode-optimizing-translator-p0-kernel-inventory-2026-09-04.md)
это и предсказывал: он выбирал `k3` за форму (32-битный GPR/load-store/setcc/цикл) и честно
писал, что свежего трейса с fixed-work знаменателем нет. Теперь он есть, и гейт P0 «выбранный
bucket имеет достаточную измеренную долю CPU-time» для `k3` **не выполняется**.

`k3`/`k4`/`k5` остаются в корпусе как conformance-векторы — их формы по-прежнему нужны
дифференциалу, — но перестают быть P0-целью производительности.

## 3. Почему одного канала было бы мало

Sampled-канал in-race выглядел так: `0x2a001000` 21.3%, `speed.exe+0x254b2f` 21.0%,
`+0x23eaa0` 13.5%, `+0x249385` 9.4%, `+0x247ec2` 8.0%, `+0x40a6f6` 7.6%, `+0x241ad0` 5.7%.
Дизассемблирование (`tools/pe-disas.py`) показало, чем это является:

* `0x654b2f` — инструкция сразу после `call ebp` в главном цикле, который заканчивается
  `timeEndPeriod`;
* `0x641ad0` — инструкция сразу после `call WaitForSingleObject`;
* `0x40a6f6` — сразу после `call [edx+0x44]` (COM vtable);
* `0x649385`, `0x647ec2` — точки возврата из обычных вызовов;
* `0x2a001000` — не `speed.exe`, а наша thunk-арена.

То есть sampled-топ почти целиком — **точки, где worker паркуется**, а не где считает.
Единственный настоящий вычислительный вход в нём — `0x63eaa0` (fixed-point на глобалах).
Count-weighted канал ранжирует совсем другое, и именно он использован для выбора.

Отдельное наблюдение: на статичном экране 76% работы гостя — это `0x585bf0..0x585c1c` плюс
`__allshr` (`0x6849a0`), то есть `fild/fimul/fcomp/fnstsw/test ah,5` — **таймерный spin-wait**.
Wall-MIPS, снятые в меню, измеряют ожидание.

## 4. Выбранный P0-kernel: `k8`

`Speed.exe` VA `0x0064a71f`, file offset `0x0024a71f`, 209 байт,
SHA-256 `99c682f06c6f5fa6ba9fe26538235905426dded02318e9fee85b9beb96c23fd6`.
Целая функция от `push ebp` до `ret`. Ноль вызовов, ноль x87, ноль SSE, ноль строковых
операций — целиком внутри существующего integer-слайса.

```c
void k8(const u8 *src, int stride, u32 *dst, int bias) {
    for (int i = 0; i < 8; i++) {
        for (int j = 0; j < 8; j++) dst[j] = (u32)(src[j] + bias) << 16;
        src += stride;
        dst += 0x40 / 4;          /* пишет 8 dword, пропускает 8 */
    }
}
```

Почему именно она интересна плану, а не просто «горячая»:

* **10.03%** всей retired-работы гостя in-race (5 hot-блоков, 68 статических инструкций).
  Функциональная attribution целиком: `0x64a8c1..0x64aaa5` 13.43%, `0x64a71f..0x64a7f0` 10.03%,
  `0x64aaa5..0x64abc0` 7.45%, `0x64af67..0x64b110` 7.38% — кластер `0x64a`/`0x64b` = **58.19%**.
* Каждый из восьми развёрнутых элементов **заново читает `src` из `[ebp+8]`, `dst` из
  `[ebp+0x10]` и `bias` из `[ebp+0x14]`**. Это 24 стековых загрузки на строку там, где хватило
  бы трёх, и каждая сейчас платит полную v86 safe-read подготовку. Ровно та обязательная
  работа, которую должны убрать оба кандидатных механизма плана (P2-M scoped memory proof и
  load forwarding по недоказуемо-escaping фрейму) — на настоящем коде, а не на фикстуре,
  написанной под механизм.
* Обёртка кейса строит **настоящий cdecl-фрейм** (аргументы справа налево + подставной адрес
  возврата), потому что тело содержит собственный `push ebp; mov ebp,esp` и читает аргументы со
  стека. Попытка «засеять ebp» регистром давала молча пустой результат.

### Учёт работы проверен, а не заявлен

Аналитический `insPerOuter` для `k8` = 502 (обёртка 7 + тело 490 + `call`/`pop`/`dec`/`jnz` 5).
Разложение тела: 5 пролог+jmp, 57 строка 0, 7×60 строки 1..7, 5 финальный инкремент+тест,
3 эпилог. Сверка с собственным счётчиком движка на двух счётах:

`node tools/aot/opt/accounting-check.mjs` делает эту сверку для всех кейсов: гоняет один и тот
же кейс на двух outer-счётах и берёт наклон, так что любая фиксированная цена настройки
сокращается.

```
k3: PASS  analytic=457   measured=457
k4: PASS  analytic=390   measured=390
k5: PASS  analytic=1175  measured=1175
k8: PASS  analytic=502   measured=502   (counter 332974 -> 634174 over 600 outer iterations)
```

Совпадение точное на всех четырёх. Гейт умеет падать: `insPerCall` +1 даёт
`analytic=503 measured=502` и выход 1. Кейсы со своим прологом/эпилогом объявляют `insPerCall` явно: их стоимость
не кратна «за итерацию», и делать вид, что кратна, — это тот самый счётчик, инкрементируемый из
`expectedCount`, который CLAUDE.md §3.4 запрещает называть выполненной работой.

### Arm A baseline (`k8`)

Изолированный node-стенд, 5 повторов, outer 20000, warmup 4000: медиана **499.8 ns** на outer,
разброс 468.3–551.2 (±8%). Это baseline изолированного kernel'а, не браузерная скорость.

## 5. MMU-контракт: `permission_fault_gate` закрыт

`--fault` в оракуле мутирует **входные байты** — негативный контроль на «заметит ли компаратор
изменившийся результат», и ничего не говорит об отказе страницы. Добавлено настоящее, и
`k3-differential` теперь **исполняет** реальный #PF, а не сообщает о его отсутствии: он гоняет
`pf-absent-dst` и проверяет шесть свойств (отказ произошёл; это запись; CR2 — отозванная
страница; ни один store не лёг; чистый прогон при этом отличается, иначе «не изменилось» ничего
бы не значило). Статус гейта входит в общий вердикт дифференциала.

**`tools/aot-oracle/corpus/mmu.mjs`** — сценарии, патчи PTE, применимость, декодеры.
**Захват отказа.** v86 входит в multiboot с фиктивными селекторами (`sreg[i] = 0xB002`) и без
таблиц дескрипторов, поэтому #PF некуда доставить и он тройной-фолтит, уничтожая то состояние,
ради которого мы пришли. Образ со сценарием ставит плоский GDT, перезагружает CS дальним
переходом и вешает настоящий IDT-gate на вектор 14; обработчик сливает CR2, код ошибки,
faulting EIP/CS и **регистровый файл на момент отказа**, затем HLT. Оба дескриптора base=0
limit=4GB, поэтому `IS_32/SS32/CPL3/FLAT_SEGS` — весь ключ JIT-кэша v86 — не меняются.

**Сценарий ничего не считает по-другому.** Гейт проверяет ровно это:
`scaffolding-is-transparent` сравнивает все сравниваемые регионы обычного прогона со сценарным.
Это НЕ утверждение о побайтовой идентичности образов — сценарный образ больше и вставляет
установку таблиц в драйвер. Отдельно: образ без сценария не изменился этим этапом при COUNT ≤ 256;
при 257…512 он изменился намеренно (§6.1).

**A/D как сравниваемый эффект.** Дворды PTE выставлены обычным сравниваемым регионом, так что
accessed/dirty проверяются как любые другие байты. Измерено на `k3`: страница кода
accessed-not-dirty, источник accessed-not-dirty, приёмник accessed+dirty.

### Матрица сценариев

| Сценарий | Что доказывает | Наблюдено (`k3`) |
|---|---|---|
| `ad-observe` | положительный контроль + метаданные | клин, `taken=0`, A/D как выше |
| `pf-absent-src` | отказ на ЧТЕНИИ | CR2 `0x10d000`, err `0x0`, EIP `0x103011` |
| `pf-absent-dst` | отказ на ЗАПИСИ, порядок отказов | CR2 `0x110800`, err `0x2`, EIP `0x103017` |
| `pf-readonly-dst` | protection-violation, не not-present | err `0x3` — proof, проверяющий только присутствие, тут неправ |
| `mapping-change-src` | отображение отозвано под живым пейджингом + INVLPG | CR2 `0x10d000`, err `0x0` |
| `mapping-change-src-no-invlpg` | **контроль**: то же без INVLPG | `taken=0` — устаревшая TLB-запись обслуживает старое отображение |
| `readonly-dst-no-wp` | **контроль**: read-only без CR0.WP | `taken=0` — supervisor-запись проходит |
| `pf-absent-code` | отказ на ВЫБОРКЕ инструкции | CR2 == EIP == `0x103000` |
| `pf-partial-dst` | **часть stores уже совершена** | `ecx` ровно на границе страницы, 512 элементов записано, 512 не тронуто |

`pf-partial-dst` — самый ценный: он ловит ошибку, которую guard сделает вероятнее всего —
перезапуск scope, чьи ранние stores уже легли, и повторное их выполнение.

Два последних сценария — парные контроли, и без них соседние строки не были бы доказательствами.
Без `mapping-change-src-no-invlpg` сценарий смены отображения был бы побайтово тем же фикстуром,
что `pf-absent-src`, под вторым именем: касание страницы перед патчем — то, что создаёт TLB-запись,
которую INVLPG затем сбрасывает. Без `readonly-dst-no-wp` строка `pf-readonly-dst` одинаково
проходила бы на CPU, отказывающем на любой записи в read-only независимо от WP.

Контроль без INVLPG **неприменим** к кейсу, чей kernel ещё и ПИШЕТ в тронутую страницу (k5):
запись не авторизуется read-записью в TLB, поэтому она пере-обходит таблицы и отказывает без
всякого INVLPG. Гейт помечает это SKIP и прямо говорит, что для такого кейса различие не доказано.

Замечание по семантике, которое было записано неверно и исправлено по факту: без CR4.PAE+NX
(v86 их отвергает) x86 **не** ставит I/D-бит в коде ошибки. Свидетельство выборки инструкции —
равенство CR2 и faulting EIP, а не флаг.

### Применимость как явное предусловие

Сценарий — это утверждение о том, КАКОЙ доступ отказывает, и раскладка кейса может тихо сделать
это утверждение недостижимым. У `k5` строка-источник и битмап-приёмник **на одной странице**,
поэтому «отозвать страницу приёмника» отзывает и источник, и первым отказывает чтение — прогон
выглядел бы как успешный write-fault сценарий, не будучи им. `applicability()` проверяет
`requires_distinct_pages` и `requires_span_past_page`; arm **отказывается** запускать
неприменимый сценарий (`MMU_SCENARIO_INAPPLICABLE`), а гейт считает это SKIP и печатает его.
Матрица, всё пропустившая, не читается как PASS.

### Гейт

`node tools/aot/opt/mmu-conformance.mjs --case <id>` — включая мутационные проверки, каждая из
которых подсовывает обход, который она обязана отвергнуть.

```
k3: PASS 54/54   k4: PASS 45/45   k5: PASS 34/34   k8: PASS 45/45
```

## 6. Найденные по дороге дефекты корпуса

Обе — латентные и обе тихие; обе нашлись потому, что проверка умела падать.

1. **`SRC1` заполнялся фиксированными `0x400` байтами независимо от `AOT_ORACLE_COUNT`.**
   Любой прогон с COUNT > 256 читал нули за концом заполнения, ветвление по данным
   вырождалось в одну сторону, и kernel переставал проверять то, ради чего выбран. Инвентарь
   при этом прямо предписывает прогонять два счёта (64 и 256), то есть жил на самой границе.
   Теперь заполнение покрывает фактический COUNT и упирается в `DST1` с явной ошибкой.
2. **Структуры MMU стояли сразу за `IMAGE_END`**, куда при большом COUNT дорастал `DST3` —
   гость падал внутри `LGDT`, до всякого kernel'а. Разнесено, и добавлена проверка перекрытия.
3. **`DST3` имел 0x100 байт до `DST4`**, то есть любой счёт выше 64 перекрывал соседнюю
   destination-область — включая предписанный инвентарём sweep 64/256. Вреда не было только
   потому, что в прогоне k3 `DST4` всегда нули. Раскладка исправлена (0x2800 у `DST3`,
   старт со смещением внутри страницы, чтобы пересечение границы вообще было возможно), а
   `assertCountFits` называет именно тот span, который счёт превысил, вместо `RangeError` из
   `DataView` где-то ниже по стеку.
4. **`insStatic`/`insPerIter` у `k8` были посчитаны неверно**, и `body_instructions` считался
   из `insPerIter`, из-за чего один и тот же объект `work` содержал два расходящихся на 26
   инструкций учёта. Теперь `body_instructions` берётся из `insPerCall`, а `verify-corpus`
   декодирует retail-тела и сверяет счёт с `insStatic` — раньше это делалось только для
   синтетических кейсов.
5. **Sampled-канал ранжирует yield-точки** (§3) — не дефект корпуса, но именно поэтому выбор
   kernel'а сделан по count-weighted каналу.

## 7. Что это меняет в плане

* §5 P0 «выбрать основной kernel по CPU-time» — **выполнено**, и результат отличается от
  предположения инвентаря. P2-механизм теперь выбирается по attribution `k8`, а не вслепую.
* §5 P0 «absent, read-only, cross-page, A/D-unset, code-page и mapping-change cases» —
  выполнено, **кроме cross-page**: доступ, пересекающий границу страниц, требует невыровненного
  операнда, которого нет ни в одном из реальных kernel'ов корпуса. Это отдельная фикстура и
  честный остаток, а не пропущенная галочка.
* §4.2 accounting: для `k8` конвенция счётчика сверена с движком численно.
* §1 «первым workload выбирается реальный integer memory/branch kernel, для которого актуальный
  профиль показывает повторную memory/permission/fault preparation» — `k8` подходит под этот
  критерий буквально: 24 избыточных стековых загрузки на строку.

## 8. Что осталось незакрытым в P0

1. **cross-page доступ** (см. выше) — нужна отдельная фикстура с невыровненным операндом.
2. **Bucket-разбор Arm A** (`dispatch/body/memory_preparation/materialization/exit`) — все
   bucket'ы в `result-schema.mjs` пока `missingBucket()`. Без них известна общая цена, но не
   доля, которую может убрать конкретный механизм; это вход в решение P2-M против P2-B.
2a. **`raw`-арм не поддерживает `k8`**: его аргументы лежат на стеке, статического фрейма нет,
   и плоский список аргументов чужого модуля не на что навести. Нужна отдельная ABI-договорённость;
   выдумывать её означало бы дать `run-raw` `undefined` и получить расхождение, которое наше, а
   не кандидата.
3. **Матрица владельцев generation'ов** остаётся аудитом, а не API:
   [contract audit](user-mode-optimizing-translator-p0-contract-audit-2026-09-04.md) фиксирует,
   что единых `codeGeneration`/`mappingGeneration`/`segmentGeneration` в рантайме нет. Это
   блокер P3, не P0, но именно на нём держится время жизни любого scoped proof.
4. **`tier2Total = 0`**: перечисление tier-2 страниц вернуло ноль, поэтому census не мог сам
   выбрать горячий набор — страницы пришлось называть явно. Пока это обходится, но означает,
   что автоматический выбор страниц сейчас недоступен.
