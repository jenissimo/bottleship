# Захват версий JIT: реализация и текущая проверка

Цель остаётся прежней: воспроизводимые +20% FPS в NFSU. Ускорение пока не
измерялось и не заявляется. Совместный игровой корпус ещё не снят.

## Реализовано

- В `vendor/v86/src/cpu.js` opt-in hook `__jitPublicationCapture` получает именно
  байты, переданные WebAssembly.instantiate, после тестовой мутации и до
  переиспользования Rust-буфера. Публикация отмечается после успешного table.set,
  отдельно от начала компиляции. Ошибка инстанцирования не считается публикацией.
- Harness `jitPublications`: `arm {maxRecords,maxBytes}`, `seal`, `export`, `clear`,
  без аргументов — статус. По умолчанию 8192 записи / 64 MiB удерживаемых Wasm-байтов;
  лимиты включают pending-компиляции. Счётчики dropped/droppedBytes сохраняют потери.
  Экспорт требует seal; pending при seal остаются явно pending. Экспорт и SHA-256
  выполняются после захвата, одинаковые байты экспортируются один раз с сохранением
  всех событий. Лимит байтов относится к удерживаемым исходным байтам; временные
  копии/строки при экспорте требуют дополнительной памяти.
- Session UUID, generation, table index/slot, start, времена начала и публикации,
  отдельный порядок публикации, полный SHA-256. Свертки по странице нет.
- `tools/jit-corpus.ts` связывает CPU profile с Debugger.scriptParsed в одном CDP
  соединении одного worker. Worker выбирается строго по parentId нужной вкладки
  и наличию preemption. Байты sampled Wasm получает через getScriptSource после
  остановки профиля; scriptParsed.hash и адрес в имени не заменяют полный SHA-256.
- `join-jit-profile.mjs` раздельно сообщает покрытие точными байтами и поколениями
  публикаций. При неполной истории, потерях или повторных одинаковых публикациях
  поколение unresolved. Живой захват после старта worker всегда помечен неполным;
  точная идентичность байтов при этом возможна. Guest instruction map unavailable.
- Артефакты: manifest, profile, publications, scripts, modules по SHA, static,
  hotness. Число статических шаблонов не превращается в их долю времени.

## Проверка

- JS-обвязка v86 пересобрана существующей Closure-командой из build-wasm.sh:
  0 errors, 0 warnings. Rust/Wasm не пересобирались.
- `public/v86.wasm` сохранил baseline SHA-256
  `3a50af7f4ade1197eb39f3bdff9764fb039a884989b2b5c7acf059977a03cb3a`.
  Это проверка файла на диске, а не загруженного worker.
- `bun run gate`: 4193 pass, 0 fail, 353 файла;
  `logs/jit-publications-gate-20260905.log`.
- После gate добавлены отказы на неполные samples/timeDeltas, неизвестный node и
  duplicate script ID, а также проверка второго гостя. Повторные адресные тесты:
  6 pass / 33 assertions; typecheck прошёл.
- Тест использует настоящий текст codegen_finalize, управляемое завершение
  instantiate и тестовую мутацию; проверяет ошибку компиляции, порядок публикаций,
  несколько версий одной страницы, переиспользование slot, лимиты и неоднозначный join.
- Прямой smoke-import `CPU` из собранного libv86.mjs невозможен: этот экспорт
  оказался undefined. Компиляция JS и тест исходного finalize проходят, но это
  не заменяет проверку hook на новом живом worker.

## Текущее препятствие и следующий запуск

NFSU подтверждена через report: speed.exe, без crash. В Chrome 9333 также работает
чужая вкладка Worms Armageddon `?game=dev&bs=wa`; ping подтвердил hasProcess=true,
paused=false. Разрешение поставить её на паузу запрошено у пользователя, ответа
на момент записи нет. Чужой гость не изменялся. Preflight нового CLI корректно
отказал до запуска профиля: `logs/jit-publications-preflight-20260905/manifest.json`.

Перед совместным захватом:

1. Перезагрузить NFSU worker для нового JS/harness и восстановить проверенную сцену
   по основному плану. В старой живой вкладке нового hook нет; `arm` должен отказать.
2. Обеспечить отсутствие второго активного гостя с разрешения его владельца.
   Capture сам не ставит чужие игры на паузу. При разрешённой паузе восстановить её
   исходное состояние в finally.
3. Проверить idx21=0, сцену и настройки, сохранить действия и screenshots.
4. `bun tools/jit-corpus.ts logs/nfsu-jit-joint-<unique-run> 10`.
   Каталог должен быть новым. `--content-only` явно допускает захват на старом
   worker без журнала публикаций; это не совместный корпус.
5. Проверить actual coverage и ограничения CDP на реальном захвате. При недостатке
   новых публикаций после прогрева захватывать от холодного запуска или очищать
   кеш только до прогрева, вне FPS-окон. Текущее completeFromWorkerStart=false
   нельзя менять вручную ради повышения покрытия поколений.
6. Измерить overhead диагностики отдельно, затем продолжить A/A и отбор расходов.

Ни +20%, ни первый совместный корпус, ни аттестация игрового сценария этой
реализацией ещё не закрыты.

## Проверка CDP на живой NFSU при продолжении

Предыдущий проход классифицирован как progress: исходники захвата, тесты и gate
изменили проверяемое состояние. В этом проходе FPS не измерялся.

- Добавлена операция `bun tools/jit-corpus.ts <new-directory> --inspect-identity`:
  штатная пауза только выбранного гостя, чтение объектов восьми JIT-функций и
  runtime-функции, проверка трёх небольших контрольных Wasm-модулей, cleanup и
  возврат исходного состояния паузы в finally. Она не собирает timings.
- Прямое соединение с worker и ручной attach сами по себе зависали на Runtime
  командах. После `Target.setAutoAttach` родительской вкладки операции работают.
  Выбор sessionId остаётся ограничен точным worker targetId; чужие worker не
  используются как fallback. На worker-команды теперь установлен таймаут 15 секунд.
- CDP `[[FunctionLocation]]` вернул scriptId для всех 12 функций. getScriptSource
  вернул реальные Wasm-байты; все три контрольных модуля совпали побайтово.
- Два экземпляра одинаковых байтов получили одинаковый scriptId (1416 в первом
  контрольном проходе); изменение константы дало другой scriptId (1417). Поэтому
  сохранение ссылки на функцию не устраняет неоднозначность поколения публикации.
  Не добавляем этот затратный механизм ради ложного повышения покрытия.
- Байты runtime-функции get_jit_config прочитаны непосредственно из загруженного
  V8-модуля: 2 581 025 байтов, SHA-256
  `3a50af7f4ade1197eb39f3bdff9764fb039a884989b2b5c7acf059977a03cb3a`.
  Это подтверждает именно загруженный baseline в проверенной NFSU worker-сессии.
- Сырые данные: `logs/nfsu-jit-identity-bytecode-20260905/identity.json` и
  `logs/nfsu-jit-identity-runtime-hash-20260905/identity.json`.
- После проверок ping NFSU подтвердил paused=false. Неуспешные попытки с уже
  выполненной паузой также завершили resume в finally. Зависшие собственные CLI
  после завершённого cleanup остановлены по их точным exec handles; чужие процессы
  не завершались. CLI теперь выходит после await cleanup, без ожидания фоновых
  таймеров транспорта harness.
- Повторный `bun run gate`: 4194 pass, 0 fail, 353 файла;
  `logs/jit-publications-identity-gate-20260905.log`.

Worms снова проверена: hasProcess=true, paused=false. Дополнительно обнаружены
живые процессы `bun tools/probes/wa-mp-styles.harness.ts` (PID 58008) и
`bun tools/probes/wa-paint3.harness.ts` (PID 59224). Поэтому отсутствие другой
active-задачи в списке Codex не доказывает отсутствия сторонней работы с гостем.
Разрешение на её прерывание по-прежнему не получено; совместный профиль ожидает
освобождения измерительного окружения. Идентичность байтов доказана, покрытие
горячих samples, накладные расходы, A/A и +20% FPS ещё не доказаны.

## После закрытия Worms пользователем: совместный профиль и чистый пилот

Ограничение выше снято сообщением пользователя «закрыл worms, действуй».
Измерения ниже выполнены при единственной игровой вкладке. Baseline runtime,
прочитанный через CDP bytecode, совпал с pinned SHA-256
`3a50af7f4ade1197eb39f3bdff9764fb039a884989b2b5c7acf059977a03cb3a`;
idx21 оставлен 0. Никакое ускорение ещё не принято.

- `logs/nfsu-jit-warm-content-20260905/`: 10 секунд, 4967/4967 Wasm samples
  привязаны к точным байтам, без журнала публикаций.
- `logs/nfsu-jit-joint-20260905/`: 12 секунд, 6018/6018 точных Wasm samples,
  224 публикации, 51 832 543 байта, без потерь. Захват включён после части
  компиляций, поэтому журнал покрывал лишь часть горячего JIT.
- `logs/nfsu-jit-joint-rewarm-20260905/`: журнал включён перед однократной
  очисткой JIT вне профиля, затем 15 секунд прогрева и 12 секунд профиля.
  138 публикаций, 23 079 115 байтов, без потерь. Всего 7767 samples,
  5809 Wasm samples с точными байтами; все 2859 generated-JIT samples
  имеют совпадающий SHA-256 в журнале публикаций. Это идентичность байтов,
  а не экземпляра: generation coverage остаётся 0, поскольку захват не
  начинался при создании worker и CDP объединяет одинаковые модули.

`ranking.json` строится командой
`bun tools/bench-v86/report-jit-corpus.mjs <corpus-directory>`.
Самостоятельные samples: generated JIT 36.81%, JavaScript 21.78%, CPU
dispatch/loop/tier drain 11.23%, EAGL HLE 10.79%, memory helpers 7.74%,
прочий Wasm 6.99%, V8 idle/program 3.42%, x87/fallback 1.24%.
Это классификация имён, не критический путь и не достижимый процент FPS.
Просмотр родителей `read32s` и `safe_write32` показал преимущественно EAGL:
их нельзя автоматически относить к накладным расходам обычного JIT load/store.

Чистый пилот `logs/nfsu-stationary-pilot2-20260905/`: четыре окна по 20 секунд,
15 секунд прогрева, по 330 сырых present intervals. FPS:
16.517616, 16.545840, 16.522214, 16.507309; max/min spread 0.2334%.
Во всех окнах прошли проверки raw count = present serial delta - 1,
guest/all present serial equality, raceState=4, advancing physics, stable
config/presenter, no capture/dump, no pause. p95: 65.925, 64.390, 65.555,
66.350 мс. Окна одной загрузки — не независимые A/A наблюдения и не CI.

Сцена: Circuit / Olympic Square, Golf GTI, automatic, 2 laps, catch-up on,
minimum traffic, medium opponents; автомобиль стоит, камера сзади.
Восстановлен `fixtures/nfsu-max`; до восстановления пользовательские файлы
сохранены в `fixtures/nfsu-before-jit-joint-20260905`.
Rage.cfg, Rage.opt и два save-файла побайтово совпали с fixture. Profiles.usr
после загрузки профиля отличается хвостом после Rage/NUL (0x0c -> 0x45).
Причина не доказана; pilot сохраняет оба SHA и явно ограничен одной загрузкой.
Первая попытка `logs/nfsu-stationary-pilot-20260905/` отказала на этом preflight
до любых замеров. Максимальные настройки ещё требуют проверки меню.

Приоритеты следующего эксперимента:

1. Generated JIT (36.81% self samples): локализовать дорогие участки в точных
   модулях; static TLB/CR0 counts не показывают устранимое время. Для общего
   +20% потребовалось бы устранить около 45% этой доли при идеальном совпадении
   с критическим путём. Старые shared-read-pair и micro-TLB не повторять.
2. HLE вместе с переходами и памятью: отдельно посчитать непересекающиеся
   стеки, проверить механизм, затем причинно различимую абляцию. Read-cursor
   TLB policy, COM stubs и skip filters уже baseline, не новые кандидаты.
3. Dispatch-only: даже полное устранение 11.23% даёт ориентир лишь +12.6%;
   не тратить на него всю программу. Tier drain при threshold=0 занимает
   1.94% self samples, самостоятельно цели не достигает.

Остаются: независимые A/A, движение, проверка overhead, ещё две игры,
изолированные A/C артефакты и все проверки итогового +20% FPS.

## Проверка новой загрузки и исправление пресета

`logs/nfsu-independent-baseline-boot2-20260905/` содержит новую загрузку из
fixture с побайтовым readback перед запуском, пошаговые screenshots и
timeOrigin=1788614249812.24. Olympic Square, параметры гонки и Golf GTI
подтверждены кадрами 10/11/15. Самостоятельные чистые окна в
`logs/nfsu-stationary-boot2-20260905/` дали 18.649184, 18.657104, 18.669598,
18.684857 FPS (373 intervals каждое). Все пять файлов совпали с fixture.
Это НЕ принято как независимое A/A: фаза относительно старой долгой сессии
не совпадает. За первое окно moverCounter изменился на 4473 против 15888
в старом пилоте. Прирост FPS без изменения бинарника нельзя считать оптимизацией.

Профиль новой загрузки `logs/nfsu-jit-fresh-content-20260905/`: 7775 samples,
5993/5993 Wasm с точными байтами, loaded runtime снова pinned baseline.
Generated JIT 36.28%, JavaScript 19.92%, dispatch/loop/drain 16.44%, EAGL 9.40%,
memory helpers 6.86%. Чувствительность dispatch к сессии подтверждает необходимость
фиксировать фазу гонки в будущем A/C, а не переносить потолок одного профиля.

Меню `logs/nfsu-graphics-card-20260905.png` подтверждает 1024x768 и high details.
Однако `logs/nfsu-graphics-leave-20260905.png` обнаружило, что исходный `nfsu-max`
оставлял Light Trails и Motion Blur OFF. Все предшествующие профили и пилоты
этой сессии относятся именно к этому пресету, не ко всем включённым эффектам.

По прямому указанию пользователя «просто пропиши в конфиг» изменены две строки
`fixtures/nfsu-max/overlay/C/NFS Underground/Rage.cfg`: `MOTIONBLUR: 1` и
`LIGHTSTREAKS: 1`. Те же байты записаны через fsWrite в живой гостевой файл;
fsRead подтвердил полное совпадение. Исходные 309 байтов сохранены в
`logs/nfsu-max-effects-off-original-20260905.cfg`. Разрешение не изменялось.
Копия `fixtures/nfsu-max-all-effects` также содержит эти строки, но основным
пресетом для следующих запусков остаётся `nfsu-max`. Новые замеры должны
начинаться с чистой загрузки этого исправленного пресета.
