# Аудит data-oriented организации v86 и границы HLE

Дата: 2026-09-07. Проверены текущие исходники, проведены headless измерения закреплённой сборки.

## Вывод

Называть DOD-направление исчерпанным нельзя. В форке уже есть компактный CPU state,
GPR в Wasm locals, прямой TLB, плоские таблицы диспетчеризации, memo возвратов,
пакетная очередь команд и кэш чтения EAGL. При этом остаются зависимые чтения,
разреженные таблицы с полной очисткой при публикации и повторные общие обходы
при удалении модулей. В HLE есть отдельные повторные преобразования и копирования.

Новая измеренная находка — чувствительность **реального Wasm resolver** к порядку
зависимых запросов: на искусственном наборе из 128 страниц перемешанный порядок
занял примерно в 1,50–1,515 раза больше времени, чем сгруппированный, при одинаковом
смещении входов на страницах. Контроль с разнесёнными смещениями сократил отношение
до 1,154. Это цена локальности в конкретных тестах, не готовая оптимизация и не
прогноз FPS; распределение адресов существенно влияет на величину.

Ни одна production-оптимизация в рамках аудита не включалась. Нового подтверждённого
прироста FPS нет; эффективность предлагаемых изменений требует отдельных A/B.

## Конкретные находки и следующие эксперименты

### 1. Цепочка meta→slab сохранилась; комментарий обещает больше, чем делает код

`jit.rs:1419` утверждает независимость загрузок. Фактически `dispatch_state_lookup`
на `:1469` получает номер slab из уже прочитанного meta. Generated AbsoluteEip
на `:4789` содержит ту же зависимость.

Это **не цена каждого RET**: speculation может обойти lookup, межмодульный путь
может отказаться ещё до чтения slab, а dynamic chaining часто попадает в memo.
Новый headless probe измеряет один конкретный in-page resolver, а не весь этот граф.

Следующий содержательный эксперимент: снять частоту этих путей и распределение
реальных адресов, затем проверить представление, сокращающее зависимость или
активный набор. Вариант обязан учитывать произвольные byte-offset входы,
state flags, virtual aliases, invalidation и `0 = miss`. Полная замена на огромную
прямую таблицу может обменять одну зависимость на больший рабочий набор.

### 2. Публикация разреженной страницы очищает 8 КиБ

`dispatch_meta_set` на `jit.rs:1510` делает `fill(0)` всех 4096 u16 ячеек и затем
записывает entries. Это относится к публикации и code-TLB refill, не к каждому hit.

В искусственной 128-page fixture по две записи на slab: очищается 8192 байта
ради четырёх байт входов. Это соотношение размера очистки и полезных ячеек,
не измеренная частота очисток в игре. Полезная занятость всей fixture — 512 байт,
выделенные живым slabs области — 1 МиБ; линии, содержащие живые ячейки, — 129×64 байт.

Кандидат: список прежних занятых offsets для очистки только старых entries либо
более мелкие подтаблицы. Сначала измерить частоту перепубликаций и стоимость
maintenance; список тоже нужно хранить и обслуживать. Должны сохраниться clean
reuse, произвольные входы и отсутствие ложных dispatch hits.

### 3. Освобождение и публикация модулей ищут владельцев общими обходами

При free `jit.rs:5952` просматривает valid TLB entries, фильтрует `ctx.pages` и
проходит hidden-index vectors. Удаление дерева повторяет это для каждого модуля.
Публикация на `:3860` также сканирует valid TLB, а на `:3897` ищет overwritten
modules по страницам. Global clear вызывает удаление по страницам (`:6131`).

Кандидат: обратные индексы module→physical pages и physical page→virtual
publications либо один маркирующий проход для batch free. Это направлено на
компиляцию/инвалидирование и возможные задержки, а не на steady-state арифметику.
Нужно сохранить hidden forests, aliases, pending compilation, обновления TLB,
epochs и однократное освобождение slots. Один прогретый throughput-тест этот
класс расходов не проверяет.

### 4. Отчёт о memo неправильно объясняет cold misses

`src/worker/harness/cmds/dispatch.ts:250` выводит из преобладания cold, что target
set больше любого memo. В Rust `jit.rs:2773` cold включает запись старого epoch;
code-TLB eviction или освобождение модуля инвалидирует весь memo через global epoch.
Отсюда нельзя различить первый доступ, churn инвалидирования и недоступный target.

Это дефект интерпретации, а не установленная большая потеря времени. В историческом
NFSU-окне было лишь 11 668 cold против 10 812 151 memo hits; оно не обосновывает
крупный эффект от борьбы с churn. Перед выбором кандидата нужны epoch-change и
раздельные причины miss; простое увеличение memo или регионов из данного вывода
не следует.

### 5. CPU state: повторная публикация важнее плотности структуры

Вход модуля загружает восемь GPR (`jit.rs:4502`), полные spill/reload находятся в
`codegen.rs:5012`; ordinary/fault exits публикуют состояние. Для коротких модулей
кандидат — анализ прочитанных до первой записи и изменённых регистров, со всеми
CFG/entry/fault/budget/context-switch условиями. Частота исполненных активаций
важнее числа модулей на диске.

x87 даже при idx10=1 записывает mantissa/tag в backing memory (`codegen.rs:3636`).
Отдельная гипотеза — ограниченный register-only scope с отложенной публикацией;
это отличается от проверенного write-through cache. Уже отвергнутый pair-guard
повторять без новой причины не нужно.

**Поправка к прежнему ответу:** текущий `wasm_builder.rs:1330` уже сохраняет лишь
dirty flag words. Утверждение о безусловных пяти stores вокруг каждого helper
устарело; reload на `:1346` всё ещё полный. idx21 остаётся выключенным.

`set_tlb_entry` также обслуживает permission mirror при выключенных читателях
(`cpu/cpu.rs:339`, `cpu/perm_map.rs:98`). Это потенциально лишний maintenance,
но не расход каждого TLB hit. При ленивом обслуживании runtime enable обязан
синхронизировать зеркало. Приоритет зависит от частоты этих обновлений в реальной нагрузке.

### 6. HLE: повторные преобразования есть, но основной поток уже пакетный

Это расширение аудита за пределы универсального v86.

- EAGL class6 дважды разбирает metadata (`hypercall_eagl.rs:1312`): handle tables,
  descriptors, vtable/stub checks, default constants. Журнал проверенных операций
  может убрать повторный разбор. Payload **не читается целиком дважды**: scan
  проверяет крайние dword, commit копирует слова (`:1036`).
- Три соседних u16 default fields читаются тремя `safe_read16` (`:1243`), обходя
  уже действующий EAGL read cursor. Узкий cursor-aware 16-bit вариант требует
  точного диапазона чтения и сохранения page/MMIO semantics.
- В `vendor/v86/crates/d3d9-webgpu/src/arena.rs:1014` каждая пара пишет в один
  live VS mirror. При authoritative compact mode >=2 промежуточный consumer
  отключён (`:1024`). Можно проверить публикацию только последнего mirror,
  сохранив каждую instance payload, итоговый state, logical count и версии.
  Устранимый объём записей: `(pairs−1) × floatCount × 4`; эффект по времени не измерен.

Для scan/replay отсутствие guest execution между проходами не доказывает
disjointness: commit сам пишет guest memory. Нужны alias/fault/MMIO tests,
shadow-model overflow, HRESULT/partial-success ordering и exactly-once ring ledger.
Существующий `eagl-token-dispatch.test.ts` проверяет symbolic routing, но не является
дифференциальным oracle реального Rust handler132. Старые inclusive 8,2–12,7%
EAGL из профилей не равны стоимости повторного scan и не переносятся на текущий FPS.

## Headless измерения

### BYTEmark

Fresh Arch boot, три теста, тот же закреплённый двигатель и shipping config.
Это контрольные повторения одной сборки, не upstream-vs-fork и не A/B оптимизации.

| Прогон | NUMERIC SORT | STRING SORT | LU | guest/host clock |
|---|---:|---:|---:|---:|
| A1 | 679,19 | 223,86 | 272,08 | 4041/4043 = 0,9995 |
| A2b | 706,21 | 208,40 | 268,26 | 4023/4027 = 0,9990 |

Изменения второго запуска той же сборки относительно первого: +3,98%, −6,91%, −1,40%.
Это **разброс повторов одной сборки**, не выигрыш/регрессия изменения. N=2 не даёт
точного noise floor. Оба clock gates и config/tier2 readback прошли. Первый boot
и калибровка занимали больше времени, поэтому wall time двух процессов не сравнивается
как ускорение. Первоначальный A2 не запустил движок из-за hashbang в инструментальной
копии runner; исправленный A2b — новый запуск, журнал A2 сохранён.

Census после A2b выполнен после фиксации scores/wall_ms, с остановленным эмулятором:

- 793 активные страницы/slabs; 6 496 256 байт областей живых slabs.
- 35 981 ненулевая опубликованная ячейка, 71 962 полезных байта: **1,108%** заполненности.
- Медиана 42, p95=100, максимум 147 ячеек на slab из 4096 возможных.
- Ненулевые ячейки пересекают 27 453 условных 64-байтных линии — около 1,68 МиБ
  адресного покрытия. Фактический cache traffic не измерен.
- 256 metadata lines содержат активные meta; некорректных записей и дублирующих
  владельцев slab не найдено.

Это инвентарь **после загрузки Linux и трёх nbench задач**, включая оставшийся kernel
code. Он не показывает heat/frequency и не является рабочим набором игрового кадра.

### Реальный resolver с синтетическим порядком запросов

`audit-dod-dispatch.mjs` выполняет гостевые циклы на 128 страницах, подтверждает
ESI=19 200 000, ECX=0, HLT и 128 опубликованных модулей. Все targets независимо
проверяются реальным `jit_find_cache_entry_in_page`. Pending compilation запрещена,
число finalized неизменно во время измерения, диагностические counters выключены.
Таймер включает Wasm batch loop, чтение запросов и вызов resolver.

Берётся одна валидная точка на страницу, каждая повторяется 32 раза. Grouped и
shuffled имеют одинаковое мультимножество запросов и одинаковый результат. Это
контролируемая искусственная локальность, а не снятая с игры последовательность.
Фиксированный stride slab 8 КиБ и похожие offsets могут создавать давление на
cache sets; аппаратные cache-miss counters здесь не измерялись.

Семь раундов `G,S,S,G,G,G,S,S`, восемь warmup окон. Контроль — максимальная
абсолютная дельта соседних G/G или S/S в этом процессе; это не доверительный
интервал и не noise floor независимых запусков. Все raw samples сохранены.

| Страниц | Независимые запросы G/S, нс | Зависимые запросы G/S, нс | S/G в зависимом режиме | max control |
|---:|---:|---:|---:|---:|
| 1 | 3,056 / 3,043 | 5,582 / 5,604 | 1,004 | 2,51% |
| 8 | 3,155 / 3,156 | 5,740 / 5,775 | 1,002 | 1,80% |
| 32 | 3,069 / 3,180 | 6,136 / 8,036 | 1,314 | 2,02% |
| 128 | 3,231 / 3,614 | 6,236 / 9,489 | 1,515 | 3,61% |

G/S — медианы всех samples каждой руки; S/G — медиана парных геометрических
отношений, поэтому не обязана совпадать с отношением этих двух медиан. Последняя
колонка относится к зависимому режиму; независимые controls составили соответственно
5,80%, 4,90%, 4,72%, 6,70%.

Независимый режим: 80 млн запросов/окно; зависимый: 40 млн, с округлением вверх
до полного набора. В зависимом режиме адрес следующего запроса зависит от
результата resolver через XOR с ожидаемым значением. Дополнительные инструкции
означают, что сравнение **между режимами** не является A/B оптимизации.

На 32/128 страницах все семь зависимых пар превышают каждый same-order control.
На 1 странице grouped/shuffled одинаковы и заметного эффекта нет. В независимом
режиме строгий критерий не пройден ни для одного набора — дельту 128-page режима
не принимаем как установленный эффект. Первичный короткий запуск на 8 млн
запросов/окно имел controls 9,9–20,8%; это smoke, а не performance evidence.

Независимый запуск нового процесса воспроизвёл зависимый эффект: на 32 страницах
S/G=1,27445, max control=1,16297%; на 128 — 1,50068 и 1,37027%. Все семь пар
в обоих случаях снова превышают каждый control. На 1/8 страницах эффекта нет.
Исходные серии не объединяются: это два наблюдения воспроизводимости механизма.
Выбранные targets основной fixture имеют **одинаковый offset 0x40** на каждой
странице; перенос результата на реальные распределения адресов требует проверки.

Дополнительный контроль изменяет fixture: входы размещены на 32 разных смещениях
`0x40 + (page % 32) × 64`. Абсолютное выполненное guest work и результат прежние,
но это **иная раскладка гостевого кода**, а не разрешённая production-перестановка.
На 32 страницах G/S=5,873/5,921 нс, paired S/G=1,011, control=3,17% — эффекта
выше контроля нет. На 128 страницах G/S=5,850/6,732 нс, paired S/G=1,154,
control=1,87%; все семь пар выше контроля. Это ограничивает первоначальную
формулировку: 50% штраф нельзя считать общей ценой случайного dispatch, он сильно
зависит от распределения offsets. Cache-set/TLB эффекты правдоподобны, но без
hardware counters их конкретный вклад здесь не установлен.

### Масштабирование полного сброса JIT

`audit-dod-lifecycle.mjs` создаёт новый экземпляр для каждого наблюдения, выполняет
ту же форму циклов и измеряет только синхронный `jit_clear_cache_js`, включая его
обычные JS callbacks очистки function table. Порядок размеров обращается в каждом
втором раунде. Сборка, guest execution, хеширование памяти и census вне таймера.

| Реально опубликованных модулей/страниц | N | Медиана, мс | Все значения min–max, мс |
|---:|---:|---:|---:|
| 16 | 5 | 0,0256 | 0,0242–0,2584 |
| 64 | 5 | 0,0782 | 0,0761–0,1324 |
| 128 | 5 | 0,1756 | 0,1745–0,3306 |
| 256 | 5 | 0,4736 | 0,4452–0,6574 |

Все 20 проверок прошли: guest RAM SHA-256 и регистры сохранены, loop-count oracle
верен, pending compilation нет, publications/slots/module ownership очищены,
double-free counter=0. Выброс первого 16-page вызова не удалён. Сырые cells и
high-water могут оставаться после clear — проверяется отсутствие живой публикации,
а не обнуление всей зарезервированной памяти.

Наблюдается рост стоимости со структурой кэша, но этот тест **не устанавливает**
асимптотику и не выделяет время отдельных обходов. Здесь нет гостевого paging,
виртуальных aliases и сложного hidden forest. Предварительные полный RAM hash и
census влияют на host caches. Данные не обосновывают большую цену clear в каждом
кадре или приоритет такой переделки ради FPS без частоты реального churn.

## Границы аудита

Нет новой записи игрового trace, Chrome/M1 FPS A/B, host assembly или hardware
cache/branch/IPC counters. Разреженность не доказывает cache bottleneck; цена
resolver probe не равна доле resolver в кадре. Перестановка гостевых объектов или
инструкций ради локальности требует доказательства наблюдаемой эквивалентности.

Существующий `tools/guestbench/lib/harness.mjs` не применяет/readback весь
SHIPPING_JIT и relaxed FPU: его default результаты нельзя автоматически считать
контролем продукта. В этом аудите для timed запусков использовался отдельный
проверенный envelope.

Приоритет следующей реализации определяется свежей частотой операций: publication
и ownership indexes при churn; более компактный dispatch при частом попадании в
зависимый путь; GPR/x87 scopes при большой цене публикации состояния. Обещать
один из этих выигрышей по одному виду исходного кода было бы преждевременно.

## Инструменты и проверки

Добавлены только отчёт и инструменты аудита:

- `audit-dod-snapshot.mjs` — копия существующего engine, конфигурация и источники.
- `dod-dispatch-census.mjs` — read-only инвентарь metadata/slabs и ограниченный набор targets.
- `audit-dod-dispatch.mjs` — actual resolver, grouped/shuffled, optional dependency и spread offsets.
- `audit-dod-bytemark.mjs` — сохранённая инструментальная копия штатного runner;
  census добавляется после измерения. Production runner не редактируется.
- `audit-dod-lifecycle.mjs` — свежие экземпляры, реальный cache clear, state/RAM/ownership oracles.

Самопроверка `node tools/bench-v86/audit-dod-dispatch.mjs --self-test` прошла:
положительный census, duplicate/invalid metadata, неизменность входных массивов,
отказ при неправильном checksum и абсолютное число вызовов независимого mock oracle
для обоих Wasm loops. Syntax checks всех новых runners прошли. Производственный
код не менялся; общий application build/gate не запускался.

Пример воспроизведения последнего контроля из корня репозитория:

```powershell
node tools/bench-v86/audit-dod-dispatch.mjs --manifest tools/bench-v86/results/dod-audit-vp9s2T/manifest.json --dependent --spread-offsets --lookups 40000000 --out tools/bench-v86/results/dod-audit-vp9s2T/new-spread-run.json
```

Результаты намеренно не перезаписываются. Новый контрольный engine можно закрепить
через `node tools/bench-v86/audit-dod-snapshot.mjs`; он не заменяет рабочий Wasm.
