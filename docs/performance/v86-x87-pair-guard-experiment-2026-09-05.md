# Объединённая проверка пустоты x87: фиксированная работа

## Результат

Кандидат корректен в выполненных проверках и даёт устойчивое ускорение **синтетического ядра с семью независимыми накопителями**: медиана парных изменений времени **−17.04%**, диапазон шести пар **−15.48…−18.48%**. Это примерно +20.5% пропускной способности именно этого ядра. На последовательной цепочке зависимых сложений выигрыш не различим на фоне шума. Результат не переносится на FOURIER/LU, браузер или игру без замеров.

Production codegen и shipping Wasm не заменены. Кандидат сохранён как `tools/bench-v86/experiments/x87-pair-guard.patch`; `git apply --check` из vendor/v86 проходит. Результаты позволяют переходить к интеграционному performance-тесту, но не объявлять общий FP uplift.

## Изменение

Отделена проверка представления от проверки непустоты. Пять двухоперандных consumers (arithmetic, FCOM, FUCOM, FUCOMPP, FCOMI) используют общий предикат:

```text
repr_ok(ST0) && repr_ok(STi)
    && (((empty * 0x101) >> TOP) & (1 | (1 << i))) == 0
```

Байт empty дублируется в младшие 16 бит, поэтому сдвиг TOP сохраняет wraparound физического индекса `(TOP+i)&7`. Предикат ничего не записывает и выполняется до helper/stack mutation. Однооперандные consumers сохраняют исходный полный guard. Дополнительный источник истины о пустоте не вводится.

`prepare-x87-pair.mjs` копирует одну рабочую базу в два временных каталога и собирает обе руки одинаковыми cargo/linker options. Отличие источников — только этот patch. Baseline rebuild побайтно совпал с исправленным shipping Wasm:

## Корректность

- Полный существующий `fpu-relaxed-diff.mjs` на candidate: **all variants match**, включая strict/relaxed и idx10=1.
- Новая matrix: все TOP 0..7 × STi 0..7 × четыре комбинации empty (никто/ST0/STi/оба). **256 случаев**, каждый сравнивается с интерпретатором при idx10 OFF и ON: **512 сравнений PASS**.
- Сравниваются результат, status word, оставшиеся и выполненные итерации. Проверяются реальные fast hits для непустых операндов и fallback для пустых.
- Битовая формула ранее проверена отдельно против пооперандного oracle на всех 524288 сочетаниях empty/TOP/operand-mask.

Это не полный ISA/exception proof. Новая матрица непосредственно упражняет FADD; остальные consumers покрывает существующий дифференциал, не полная такая же матрица для каждой инструкции.

## Бенчмарк и защита от разного объёма работы

`x87-fixed-work.mjs` создаёт multiboot guest без ОС, прогревает настоящий v86 JIT асинхронно, затем измеряет синхронные вызовы `cpu.main_loop()` до HLT. Таймер — host `performance.now()`, гостевые часы не используются. Это включает обычную диспетчеризацию; измерение не подменяет JIT-таблицу JS-обёрткой.

Три ядра, каждое **5 млн итераций** на измерение:

| Ядро | Работа | Абсолютный результат | Retired instructions | JIT entries в каждом sample |
|---|---|---|---:|---:|
| pair | 8 × FADD ST0,ST1, последовательная зависимость | ST0 = 40 млн | 55,000,011 | 551 |
| spread | 7 × FADD STi,ST0, независимые ST1..ST7 | каждый из 7 = 5 млн | 50,000,024 | 501 |
| memory | 8 × FADD m64, однооперандный контроль | ST0 = 40 млн | 55,000,011 | 551 |

Retired oracle вычисляется по числу инструкций setup/loop/epilogue, включая HLT. Проверяются все семь накопителей, guest iteration counter, ECX=0 и SW. Новая компиляция внутри измеряемого окна запрещена. JIT entry census читается до/после окна и проверяется по пределам loop-safety chunks + setup activation; в итоговой серии числа выше одинаковы на обеих руках и во всех samples. Эти входы прямые, не sampled chaining, поэтому прежний дефект idx27 здесь не участвует.

Отдельная инструментированная companion-рука доказывает fast hits >0 и fallback=0. В timed arms FPU counters OFF. Первоначальный вариант setup через interpreter FLD1 был отвергнут ливнес-проверкой: ST1 оставался в каноническом F80 и заставлял arithmetic идти через helper. Теперь setup использует FLD m64 с relaxed representation.

Captured Wasm у pair/spread отличается между руками. У memory в финальной серии **одинаковый hash**: `47ff0368935b0b4983fa494327be94c476b1293f68050b3777cf75888967044b`. Таким образом контрольный путь не был случайно изменён кандидатом.

## Протокол и сырые результаты

Node v22.14.0, Windows, Ryzen 9 7900X3D. SHIPPING_JIT, relaxed=1, idx21=0, idx10=0, tier2=0. По 3 прогрева по 2 млн итераций после первоначального JIT-прогрева; затем 7 samples по 5 млн. Одна arm-summary — медиана семи samples. Свежий процесс на каждую руку. Сначала две A/A пары, затем шесть A/B пар с порядком AB/BA/AB/BA/AB/BA. Другие тесты/сборки во время performance-серии не запускались.

Финальный каталог: `tools/bench-v86/results/x87-fixed-pwZ2kw` — manifest, 16 raw JSON/logs, summary, matrix.json, fpu-diff.log. Время ниже: `candidate/baseline - 1`, отрицательное означает быстрее.

| Ядро | A/A, % времени | Шесть A/B изменений, % времени | Парная медиана |
|---|---|---|---:|
| pair | −1.40, +0.60 | +2.80, −0.76, +0.08, +1.44, −3.07, −1.58 | −0.34% |
| spread | −0.73, +1.12 | −16.86, −15.48, −18.48, −17.04, −18.21, −17.04 | **−17.04%** |
| memory | +0.00, +0.67 | +0.28, −0.82, −0.63, −0.97, −3.44, −1.57 | −0.89% |

До добавления пооконного entry census была ещё серия с теми же тремя ядрами (`x87-fixed-qaMNYQ`): spread −17.87%, pair −0.60%, memory +0.17%. Она согласуется с итоговой, но основной результат — серия с усиленным gate. Самая первая серия только pair/memory (`x87-fixed-M2viCg`) дала соответственно +0.006%/+0.30%; её нулевой результат не удалён.

Две A/A пары не дают точной оценки распределения шума. Однако все шесть выигрышей spread намного больше и этих контрольных отклонений, и сдвигов неизменённого memory-кода. Для pair/memory причинный эффект не заявляется.

## Воспроизведение

```powershell
node tools/bench-v86/prepare-x87-pair.mjs
# Скрипт печатает путь manifest.json и candidate/build/v86.wasm.
node tools/bench-v86/x87-fixed-work.mjs --wasm <candidate-wasm> --matrix --out matrix.json
$env:V86_WASM_PATH = '<candidate-wasm>'
node vendor/v86/tests/fpu-relaxed-diff.mjs
Remove-Item Env:V86_WASM_PATH
node tools/bench-v86/run-x87-fixed-pairs.mjs <manifest.json>
```

Следующий содержательный шаг — сравнить эти же две корректные сборки на интеграционной FP-нагрузке и в браузере. Синтетика показывает, что объединение может окупаться при независимой работе; она также показывает, что оно не ускоряет любую последовательность x87-инструкций.
