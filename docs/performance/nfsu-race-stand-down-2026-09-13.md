# Стенд NFSU «сразу в гонку» не доезжает до гонки (13.09.2026)

Это отчёт о **неудаче**, а не перепись горячего кода. Шаг 2 работы «Перепись
горячего кода NFSU — чей он» требовал прогнать стенд входа в эталонную гонку и
снять профиль. Стенд сегодня не доходит до гонки: гость выходит из процесса на
экране загрузки, до профиля. Долей времени в этом документе нет — их не на чем
считать, и придумывать их нельзя.

Инструмент опознания (`tools/re/libid.py`, шаг 1) работает и ждёт адресов:
`libid summary tmp/nfsu/Speed.exe` отвечает мгновенно, `ask` на произвольных
адресах — тоже (проверено по ходу, см. ниже).

## Что происходит

`bun tools/bench-v86/source-pair/engine-series-cdp.ts --enter --profile`
(и ручной `__nfsuEnter`) доходят до `Ожидаю: profile` и падают по таймауту:

```
Остановлено: Error: Экран не подтверждён: {"name":"profile","distance":44.0541087962963}
```

Это не медленная загрузка. `report()` на остановившемся госте:

| поле | значение |
|---|---|
| `lastThunk` | `kernel32:ExitProcess` |
| потоки | все 7 — `TERMINATED` |
| `faults[0].eip` | `0x592a29`, чтение `[ECX+0x94]` при `ECX=0` |
| `faults[0].lastThunk` | `d3d9:IDirect3DDevice9_SetDepthStencilSurface` |
| `faults[0].outcome` | `ACCESS_VIOLATION caught by guest __except handler 0x670e4c` |
| `d3d9.api.present` | 29 (то есть экран загрузки уже рисовался) |
| `stubs` | пусто; `gpuErrors.total` 0; `gpuDevice.status` ok |

Хвост кольца вызовов читается как готовый сюжет: `TestCooperativeLevel` → `BeginScene`
→ две пары `SetRenderTarget`/`SetDepthStencilSurface` (все вернули `S_OK`) → падение
на разыменовании нуля → `SetUnhandledExceptionFilter` → `GetModuleHandleA("mscoree.dll")`
→ `ExitProcess`. Это штатный обработчик аварии самой игры, а не наш стоп.

`libid` про место падения: `0x00592a29` → `FUN_005929c0`, **код игры** (medium:
вне библиотечных блоков образа, без библиотечных улик, тела нет в чужих образах
корпуса). То есть нулём игру накормили снаружи — из нашего HLE, — а не библиотека
внутри неё.

## Что уже исключено

Четыре прогона, три разных конфигурации, **побайтно одинаковый** снимок экрана
(sha256 совпал) и одинаковая до 13-го знака `distance` — отказ детерминированный.

| проверка | результат |
|---|---|
| прямой вход (`directRace`) | падает |
| записанный путь через меню (`?menu=1`) — штатный диагностический контроль | падает так же |
| движок v86 из поставки (`755c2d3d`, собран 12.09) | падает |
| движок до харвеста (`9aa38d8b`, 11.09 16:44, плюс `__aotNoAutoLoad`) | падает так же |

То есть ни путь навигации, ни бинарь движка, ни сохранённый AOT-кэш ни при чём.

## Когда сломалось

Последний удачный вход — **11.09.2026 18:45**, `logs/nfsu-navigation-Bau3pi`:
10 записей `entry-complete`, ни одной `entry-failed`. Сегодняшний каталог
`logs/nfsu-navigation-ax5yTj` — 0 и 4.

## Версия, которую подтвердить не удалось

В рабочем дереве сейчас лежит очень крупная **незакоммиченная** правка (порядка
сотни файлов в `src/worker`), в том числе смена сигнатуры быстрых путей
диспетчера (`registerFastPath('d3d9', …, (cpu, _mem, _mem32, view))` →
`(esp, view)`), `thunk-dispatcher.ts` +290/−91, `d3d9-device.ts` +196/−56
(правлен сегодня в 08:47), `d3dx9/effects.ts` +872. Dev-сервер отдаёт рабочее
дерево, так что гость исполняет именно это. Быстрый путь не попадает в кольцо
вызовов `recentCalls` — что сходится с тем, что нуль пришёл от вызова, которого
в кольце не видно.

**Это версия, не вывод.** Проверить её честно — значит поднять стенд на чистом
дереве, а сделать это сегодня не вышло:

- `git worktree` на `a0e29c5` + свой vite на 5175 (свой `cacheDir`, чтобы не
  трогать чужой оптимизатор) поднялся; лаборатория переехала на новый origin;
- но на свежем origin гость NFSU **не взлетает по своей причине**: первый прогон
  — тихий выход (`ExitProcess` без единого падения, `d3d9.api.present` = 0,
  пустой бирюзовый кадр), второй — зависание внутри `waitScreen`.

Это другой отказ, не тот, что на общем дереве. Так что чистое дерево не
оправдано и не обвинено — оно просто не проверено. Поднимать NFSU с нуля на
новом origin — отдельная работа, не эта.

## Что нужно сделать дальше

1. Дождаться, пока соседняя сессия закоммитит или отложит правку `src/worker`,
   и прогнать стенд ещё раз — это самая дешёвая проверка версии.
2. Если после этого падение осталось — бисект по быстрым путям d3d9: отключить
   их и посмотреть, доживёт ли гость до профиля.
3. Перед прогоном поднять сборщик улик:
   `bun tools/bench-v86/source-pair/navigation-record-server.ts` — без него
   вход падает на первой же записи.
4. Когда стенд снова доедет до гонки, перепись собирается так: полная
   гистограмма EIP (`tools/probes/luna-nfsu-eip-census.ts` — окно 30 с, шаг 2 мс,
   со снимком сцены до и после), адреса → `bun tools/re/libid.ts ask
   tmp/nfsu/Speed.exe --addrs hot.txt --json`, доли — по сэмплам.
   Штатного `guestBlocks` для переписи мало: он отдаёт только топ-50 точных EIP,
   и знаменатель остаётся неизвестным.

## Оговорка про машину

Прогоны шли на общей машине: рядом работали два гостя RA3 соседней сессии.
На детерминированный выход из процесса это не влияет, но для будущих замеров
времени — влияет, и мерить доли кадра рядом с ними нельзя.
