# План статистического и статического анализа JIT v86

## Цель и критерий завершения

Добиться воспроизводимого прироста не менее +20% FPS относительно зафиксированной
сборки в NFS Underground на максимальных настройках, при сопоставимой сцене,
без потери корректности и без игровых спецслучаев в эмуляторе. Другие игры нужны
для проверки общности оптимизаций и отсутствия регрессий. Быстрее работающий
микротест, меньше Wasm-операций или готовый анализатор сами по себе цель не закрывают.

Рабочий репозиторий: `C:\Projects\bottleship-oss`. Не перепутать с IdleProtectors,
который может быть указан рабочим каталогом новой сессии. Прочитать местные
AGENTS.md, если есть, и CLAUDE.md. Дерево содержит много чужих незакоммиченных
изменений; не сбрасывать и не включать их автоматически в свои изменения.

## 1. Сначала сделать измерение воспроизводимым

1. Проверить доступную игру, настройки графики, камеру, runtime/config и состояние
   сценария. Сохранить manifest: версии, хеши, JIT-флаги, разрешение, настройки,
   окружение браузера/ОС, длительность, действия и сырые результаты. Неизвестное
   записывать как неизвестное, не восстанавливать догадками.
2. Превратить запуск и вход в сцену в проверяемый сценарий: действия разрешаются
   наблюдаемым состоянием игры; после каждого этапа проверить достижение состояния.
   Старый `logs/recordings/nfsu-to-race.json` содержит около 61 с действий по времени
   хоста и ненадёжен при холодном запуске. Не считать его детерминированным replay.
   `fixtures/nfsu-max` и `tools/probes/v86-nfsu-restart-windows.harness.ts` — исходные
   материалы. Восстановление OPFS fixture требует остановленного гостя.
3. Отдельно измерять прогрев/компиляцию и устойчивое исполнение. Не чистить JIT-кеш
   внутри измерительного окна. Неподвижная сцена годится для пилота; финальная
   проверка включает воспроизводимое движение/отрезок игрового процесса.
4. До кандидатов провести A/A на нескольких независимых запусках и определить
   шум, длительность окна и число повторов. Не подбирать протокол после результата.
   Сохранять frame times; отчёт: FPS, p50/p95/p99 frame time, паузы и контроль сцены.
5. Для A/C: парные окна с заранее заданным сбалансированным порядком, одинаковым
   прогревом и A/A, C/C контролями. Экспериментальной единицей считать запуск или
   пару окон, а не тысячи коррелированных кадров. Доверительный интервал строить
   по независимым парам/запускам; кадры внутри окна не считать независимыми.
6. Заранее зафиксировать критерий: для заявления «не менее +20%» нижняя граница
   95% интервала парного отношения FPS должна быть >=1.20. Отдельно показать
   стабильность frame times и повторение эффекта в независимой сессии. Увеличивать
   выборку по заранее заданному правилу, не повторять до случайного PASS.

Во время замеров не запускать сборки, тесты или второго активного гостя.
При отдельном микробенчмарке поставить пользовательскую игру на паузу штатной
кнопкой приложения, затем возобновить в finally. Не завершать чужие процессы.

## 2. Собрать связанный корпус: профиль + точные модули JIT

Это корпус сгенерированного JIT, не обязательная новая система AOT-компиляции.
Сначала довести захват одной сцены NFSU до достоверной связи, затем добавить две
доступные игры с отличающимися нагрузками. Названия выбрать по реальным fixtures
и установленным играм; при отсутствии подходящих узнать у пользователя.

Текущий следующий шаг — устранить потерю идентичности между дампом и профилем:

- В `vendor/v86/src/cpu.js` hook `__wasmDump` сохраняет start, table_index, len,
  bytes. Нет идентификатора поколения и времени публикации.
- `keepLatestPerPage` заменяет предыдущую версию; `jitBytes snap` в
  `src/worker/harness/cmds/codegen.ts` также сворачивает записи по странице.
  Этого недостаточно для профиля, за время которого страница перекомпилировалась.
- Без `keepLatestPerPage` записи накапливаются, но существующий maxPages ограничивает
  только ветку keepLatestPerPage. Для полного корпуса нужен явный лимит байтов/
  записей и счётчик потерь; нельзя просто включить неограниченный dump всей игры.
- Ввести opt-in диагностический журнал публикаций с session ID, поколением,
  гостевым start, полным SHA-256 Wasm, table slot, порядком/временем публикации.
  Хеширование и экспорт вынести из горячего пути. Переиспользование slot учитывать
  явно; одинаковые байты можно дедуплицировать, сохраняя события публикации.
- Сопоставить журнал с доступными V8/CDP script/module ID и samples. Если однозначной
  связи нет, отмечать запись unresolved, не угадывать по странице или индексу.
  Встроенное имя `g<адрес>@tN` даёт entry, но не точную горячую гостевую инструкцию.
- Сохранять гостевые байты/дизассемблирование и карту x86 -> Wasm там, где источник
  позволяет получить точную карту. Не выдавать приближённую карту за точную.
- Измерить накладные расходы захвата сравнением с захватом, выключенным в той же
  сцене. Диагностические прогоны отделить от финальных FPS-замеров.

Артефакт на игру/сцену: manifest, сырой профиль, журнал публикаций, модули по SHA,
карты при наличии, действия, статический отчёт, покрытие разрешённых samples,
число потерь и неподдерживаемых модулей. Проверить корректность join тестом с
переиспользованием slot и несколькими версиями одной страницы.

## 3. Развить анализатор ровно настолько, насколько помогает поиск

Основа уже есть: `tools/bench-v86/analyze-jit-wasm.mjs` и 7 тестов в соседнем
`.test.mjs`. Он валидирует Wasm, распознаёт конкретные шаблоны CR0, TLB-чтений,
аффинных адресов и прямых пар чтений. Поддержка ограничена одним defined function;
это распознавание форм, не SSA, CFG или доказательство эквивалентности.

Добавлять по потребности:

1. Корректный CFG и def-use для Wasm locals, учёт merges, ветвей и выходов.
2. Классификацию доступов к состоянию CPU и гостевой памяти по реальному ABI.
   Старую эвристику module-stats для AOT ABI к v86 применять нельзя.
3. Контракты эффектов хелперов: чтение/запись состояния, fault, смена адресного
   пространства, MMIO, invalidation. Неизвестный вызов консервативно разрывает
   доказательство; контракт подтверждать кодом и регрессиями.
4. Поиск повторных публикаций/перезагрузок состояния, материализации флагов,
   трансляций адреса, x87/SSE-проверок, дорогих helper fallback и межблочных выходов.
5. Для каждой находки — байтовые offsets, точная версия модуля, доказанные условия,
   недостающие условия и покрытие распознавателя. Неподдерживаемые случаи видимы.

Не начинать с универсального оптимизатора Wasm. Сначала отчёт, который указывает
на реально дорогие места и позволяет быстро проверить гипотезу вручную.

## 4. Ранжировать по потенциальному времени, а не количеству операций

Итоговая таблица: семейство расхода, игры/сцены, доля времени в соответствующем
коде, достоверность привязки, статические примеры, оценка устранимой доли,
стоимость реализации, риск корректности, следующий эксперимент.

Само время в модуле не равно времени конкретного шаблона внутри него. Не умножать
число его вхождений на sample share и не объявлять результат затратами шаблона.
Использовать точные offsets, целевую диагностику или изолированную абляцию.
Отдельно учитывать CPU JIT, хелперы, JS/HLE, графику и компиляцию; V8 idle не означает
автоматически доступный резерв производительности.

Для крупных кандидатов проверять потолок по Амдалу: если доля всего критического
времени p ускоряется в s раз, общий потолок 1/((1-p)+p/s). Для +20% при полном
устранении расхода нужно убрать минимум 1/6 исходного критического времени.
В многопоточной/перекрывающейся CPU/GPU работе это ориентир, а не сумма samples.
Кандидаты с малым потолком не должны занимать всю программу поиска.

## 5. Цикл оптимизации и приёмка

Выбрать 1–3 крупнейшие гипотезы по профилю. Для каждой заранее записать механизм,
ожидаемый эффект и условие отказа. Делать одну причинно различимую перемену за раз.

1. Изолированные A/C source snapshots; A обязан совпадать с pinned baseline.
2. Доказать, что нужный путь исполняется: счётчик вне замера или мутационный тест.
3. Проверить семантику: interpreter differential, flags, DF, budget/normal/fault
   exits, точный EIP, порядок побочных эффектов, page crossing, CPL/permissions,
   MMIO, aliasing, invalidation и релевантные режимы x87/SSE.
4. Короткий фиксированный объём работы для раннего отсева, с контролем retired
   instructions и результата. Окна достаточной длительности; живость и меньше
   Wasm-операций не считать ускорением.
5. При положительном сигнале — парный игровой A/C по протоколу раздела 1,
   затем контроль других игр. Не переносить процент из микротеста на FPS.
6. Интеграция только после подтверждения пользы и корректности; выполнить
   `bun run gate` и относящиеся к изменению vendor-тесты. Среди обязательных для
   затрагиваемых зон: dead-flags, fpu-relaxed, SSE differential/fault suites,
   `aot:opt:gate`, validate-jit-exports. Проверить актуальные scripts в package.json.
7. Сохранять отрицательные результаты в append-only registry с сырыми данными.
