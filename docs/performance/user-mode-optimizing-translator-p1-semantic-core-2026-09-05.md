# P1: семантическое ядро, лифтер и контрольный дифференциал

Дата: 2026-09-05. Статус: выполненный этап P1
[плана реализации](user-mode-optimizing-translator-implementation-plan-2026-09-04.md),
продолжает [результаты P0](user-mode-optimizing-translator-p0-results-2026-09-05.md).
Здесь нет ни одного performance claim: этап целиком про семантику и её проверяемость.

## Итог

Rust-ядро разложено по модулям плана §3 и получило три вещи, которых у него не было: **execution
envelope** (§4.1) как обязательное поле региона, **внутрирегионный поток управления**, и
**типизированную дельту учёта**. На этом основании написан лифтер для `k8` — ядра, выбранного в
P0 по измеренной доле CPU-времени, — и дифференциал: интерпретатор IR против v86 сходится по 512
байтам приёмника, трём определяемым ядром регистрам и всем шести флагам.

Отдельно построен **кросс-арм оракул отказов**: оба арма отказывают на одном смещении внутри
тела, тем же видом доступа, и 512 уже записанных элементов совпадают побайтово.

Крейт: 42 теста. Общий гейт `bun run aot:opt:gate` (корпус, учёт, MMU-матрица на четырёх кейсах,
оба дифференциала, self-test раннера, тесты крейта) проходит целиком.

## 1. Структура

```text
tools/aot/opt/compiler/src/
  contract.rs     execution envelope: предпосылки, их владельцы, срок действия
  ir.rs           значения, адреса, эффекты, потоки управления, регионы
  verify.rs       структурные и семантические инварианты
  decode.rs       лифтер k3 (пиновый) + общие ошибки декодирования
  decode_k8.rs    декодер и лифтер k8
  interpret.rs    эталонный интерпретатор
  bin/k3_wire.rs  проводной адаптер k3
  bin/k8_wire.rs  проводной адаптер k8
```

`lower_wasm.rs` и `passes/` пока отсутствуют — это P1.6 и P2, и пустой модуль вместо них был бы
заявкой на то, чего нет.

## 2. Execution envelope

Регион не может существовать, не объявив, при каких условиях он верен. Поля — режим декодирования,
CPL, модель сегментов, модель адресации, модель исполнения, политика FP, и список зависимостей с
владельцем у каждой.

Две вещи здесь сделаны намеренно узко:

* **FS вне модели сегментов.** `SegmentModel::FlatDataSegments` покрывает DS/ES/SS. FS
  переключается на каждом переключении потока, поэтому ни один регион не имеет права свернуть его
  базу в адрес — это прямо записано в типе, а не в комментарии.
* **`ExecutionModel::SingleGuestCpu`.** На этом поле держится время жизни любого scoped memory
  proof: при одном исполняющем CPU и без yield внутри scope никто не может отобрать страницу
  посреди него. Под SMP проверка на входе не мешает конкурентному unmap ПОСЛЕ неё, и нужен другой
  контракт сериализации.

`verify` **выводит** требуемый набор зависимостей из того, что регион реально делает, и отвергает
недообъявление. Семь тестов доказывают, что проверка падает: убрать `NoCodeWriteBarrier` у региона
со store, убрать `MappingAndPermissions`/`OrdinaryRam` у региона с памятью, убрать `CodeBytes` или
`SegmentState`, подсунуть неканоничный список, поднять версию. Отдельный тест показывает, что
регион без памяти обязан объявлять МЕНЬШЕ — иначе проверка не смогла бы падать там, где это важно.

Матрица владельцев из [аудита](user-mode-optimizing-translator-p0-contract-audit-2026-09-04.md)
остаётся невыполненной на стороне рантайма: единых `codeGeneration`/`mappingGeneration`/
`segmentGeneration` нет. `DependencyKind::owner()` называет владельца для каждой зависимости, но
это описание обязательства, а не API — регион с такими зависимостями непубликуем, пока рантайм их
не предоставит. Это блокер P3, и он не притворяется решённым.

## 3. Поток управления внутри региона

У `k3` был один self-loop, и обе его дуги были выходами: регион исполнял тело один раз за вход.
Для настоящего цикла это не работает — регион, выходящий на каждой итерации, корректен и измеряет
только собственную цену входа.

Добавлен `Continuation`:

```text
Continuation = InRegion { instruction } | Exit(Statepoint)
```

и `Opcode::Jump`. Безусловный переход — не ветвление с константным условием: у цикла есть дуга,
которая не является выбором, и скрывать это от каждого прохода бессмысленно.

Базовых блоков намеренно нет. Регион остаётся плоским списком инструкций со входом, чего хватает
для сводимого CFG над индексами; блоки стоит вводить тогда, когда их потребует конкретный проход,
а не носить в IR структуру, которую никто не читает.

Интерпретатор получил **настоящий program counter** и отдельный счётчик `retired`. Прежнее
`retired = index` было верно ровно потому, что регион был прямолинейным: с циклом инструкция
исполняется много раз, и индекс перестаёт быть числом исполненных инструкций.

Верификатор: позиционное правило «терминатор только последним» заменено на **достижимость**. Для
прямолинейного региона это то же самое; для региона с циклом первое правило нарушается по
построению, а второе ловит настоящую проблему — инструкцию, до которой не доходит ни один путь.

## 4. Учёт: дельта стала типом

```text
AccountingDelta = Fixed(u32) | Retired
```

Прямолинейный регион retires фиксированное число, и сказать об этом полезно: lowering свернёт его в
константу. Регион с обратной дугой — нет: число зависит от того, сколько итераций реально
завершилось. Константа там — это ровно «учёт по намерению», который CLAUDE.md §3.4 запрещает
называть выполненной работой, поэтому `verify` **отвергает** `Fixed` в регионе с обратной дугой.

Двух вещей для этого мало, и обе выяснились на ревью.

Во-первых, **`Retired` недосчитывал единицу на каждом выходе через ветвление**: терминатор,
который выходит, сам уже исполнился — его продолжение это цель перехода, а не он сам, — а
дельта материализовалась до инкремента. `Opcode::Exit`, стоящий за немоделируемой инструкцией,
наоборот не исполняется. Теперь это различие — параметр одной функции выхода, а не порядок двух
строк. Пока каждый выход нёс написанную руками константу, ошибка была невидима: `Fixed(7)` у k3
случайно совпадал, то есть два механизма гасили друг друга.

Во-вторых, **`Fixed(n)` нигде не сверялся с путём**. Теперь интерпретатор сравнивает объявленную
константу с фактическим `retired` и возвращает `AccountingMismatch`, а не кредитует гостю число,
которого никто не исполнял. Тест проверяет обе стороны: подмена константы отвергается, а замена
`Fixed(7)` на `Retired` даёт то же самое значение — то есть механизмы согласны, а не гасят
друг друга.

Проверка сходится численно. Для `k8`: `insPerCall` = 490, регион заканчивается перед `ret`,
интерпретатор сообщает `accounting = 489`, и дифференциал требует именно `insPerCall - 1`.
Отдельно `node tools/aot/opt/accounting-check.mjs` сверяет аналитический `insPerOuter` со
счётчиком самого движка на всех четырёх кейсах (k3 457, k4 390, k5 1175, k8 502 — точное
совпадение) и падает при сдвиге на единицу.

## 5. Лифтер k8

`k8` — целая cdecl-функция: собственный пролог, цикл с обратной дугой, эпилог. 209 байт, 68
инструкций. В отличие от `k3`, лифтер здесь — настоящий (узкий) декодер, а не перечисление: 68
инструкций руками означало бы записать ту же информацию дважды.

Допускаются ровно те формы, которые встречаются в `k8`; всё остальное **отвергается**, а не
угадывается. SIB и disp32-only дают `Unsupported`: декодер, принимающий незнакомую форму за
правдоподобную, порождает регион, неверный именно на тех входах, которые никто не проверял.

**Граница по неподдержанной инструкции.** `ret` уходит по `[ESP]`, чего слайс не моделирует.
Регион заканчивается ровно ПЕРЕД ним, с `continuation_eip`, указывающим на сам `ret`, — baseline
его исполняет. Это возможно только потому, что длина инструкции известна, чего план и требует от
каждой такой границы.

**Реконструкция.** У выхода из цикла последние определения `ECX` и `EDX` лежат по БОЛЬШЕМУ индексу
инструкции, чем ветвление, которое из региона выходит: SSA-ссылки, доминирующей по порядку
индексов, для них не существует. Консервативный регион отвечает на это честно — `ValueRef::LiveGpr`
и `FlagRecipe::Live` означают «реконструкция не нужна, состояние никогда не переставало быть
каноничным». Право так сказать даёт поле `Region::keeps_state_canonical`. Что `verify` при этом действительно
делает, стоит сформулировать точно: он проверяет **согласованность заявления с формой** — регион,
не заявивший каноничность, не может использовать `LiveGpr`/`Live`, — но вывести саму каноничность
из опкодов он не может, потому что она свойство lowering'а, а не IR. То есть это объявление,
которое lowering обязан соблюсти, а не доказательство.

Отдельно сужено значение самой формы. `LiveGpr(r)` в слоте `i` означает «слот `i` по-прежнему
держит регистр `i`»; любая другая пара — это перестановка, то есть настоящая реконструкция, и
`verify` её отвергает. Плюс интерпретатор снимает снимок регистрового файла до реконструкции:
он его же и перезаписывает, поэтому чтение «вживую» дало бы уже подменённое значение.

## 6. Дифференциал k8

`node tools/aot/opt/compiler/k8-differential.mjs`.

У двух арм **нет** общей архитектурной поверхности, как было у `k3`, и это записано явно:

| | сравнивается | почему |
|---|---|---|
| `K8_DST` (512 байт) | да | полностью определяется ядром, и ради него всё |
| `eax`, `ecx`, `edx` | да | счётчик цикла и два продвинутых указателя — тоже определяются ядром |
| 6 флагов | да | см. ниже про `lea` |
| `ebx`, `esp`, `ebp`, `esi`, `edi` | **UNCOMPARED** | зависят от того, что было у драйвера на входе; изолированный интерпретатор этого не разделяет |

Последняя строка помечена UNCOMPARED, а не «совпало»: объявить совпадение по состоянию, которого
ни одна сторона не устанавливала, — это как дифференциал приходит к согласию ни о чём.

**Флаги стали сравнимы благодаря находке самого дифференциала.** Первый прогон разошёлся по `ZF`.
Причина оказалась не в лифтере: v86 снимает состояние ПОСЛЕ эпилога обёртки, а `add esp, 0x10`
переписывает флаги, которые произвёл kernel. Очистка стека переведена на `lea esp, [esp+0x10]` —
LEA флагов не трогает, число инструкций то же, — и обёртка стала прозрачной по флагам для любого
кейса с `stackArgs`.

Мутационный контроль гоняет компаратор на трёх намеренных порчах (`dst_hex`, `ecx`, `zf`) и требует,
чтобы каждая была поймана. Флаг «мутация замечена», вычисленный без запуска компаратора, доказывал
бы только что строка изменилась.

## 6a. Дифференциал отказов

Чистый прогон не проверяет то, что механизм памяти обязан не сломать: кандидат может
воспроизвести любой чистый результат и всё равно перезапустить scope, чьи stores уже легли.
Поэтому оба арма гоняются под одним и тем же отзывом страницы.

Сценарий — `pf-partial-dst` при 1024 элементах, единственный в матрице, где записи **успевают
завершиться до отказа**: иначе «ничего не записано» сошло бы за согласие. Rust-стороне страница
отзывается через `BS_K3_REVOKE_PAGE`, гостю — через патч PTE.

| Проверка | Результат |
|---|---|
| оба арма отказали | да |
| одно и то же смещение внутри тела | 8 == 8 |
| один и тот же вид доступа | permission-write / not-present write |
| **совпали уже совершённые эффекты** | 512 элементов побайтово |
| префикс непустой (совпадение не вырождено) | да |

Смещение сравнивается **внутри тела**, а не по абсолютному EIP: образ ставит перед телом
регистровый пролог обёртки, и длина пролога выводится из кейса, а не предполагается нулевой.

Этот арм сразу нашёл дефект, который чистый прогон не мог увидеть: проводной адаптер k3 заполнял
фиксированные 256 слов источника, тогда как образ после правки P0 заполняет по фактическому
`COUNT`. При счёте выше 256 два арма считали «одно и то же» из разных входных данных.

## 6b. P1.5 / P1.6: юнит, исполняемый движком, и матрица выходов

Rust-компилятор эмитирует **юнит, который движок исполняет через собственный dispatch**
(`wasm_table[slot + 1024]`), поставленный той же транзакцией, что использует эмулятор.
Идентичность наследуется от живого capture — слот таблицы, хеш страницы, SHA движка, база TLB —
поэтому юнит, собранный против другого движка, в этот попасть не может.

`bun run aot:opt:arm-b` — весь цикл одной командой:

```
PASS  capture a live job (table slot, page hash, engine identity)
PASS  lower the code AT THE ENTRY and verify   11 instructions, 38 contract checks, slot 899
PASS  the engine enters the unit through its own dispatch
      registered, entered, owns the page, relocations re-derived
PASS  positive and negative controls   CORRECT->CORRECT, DIVERGENT->DIVERGENT
```

Оракул даёт `memory_identical`, `state_identical`, `first_divergence: null` — совпадают память,
регистровый файл, **сырой ленивый кортеж флагов v86** и счётчик инструкций. Отрицательный
контроль по-прежнему расходится, то есть оракул не ослеп.

### Матрица выходов (`bun run aot:opt:exits`)

Дифференциал сравнивает два РАЗДЕЛЬНЫХ исполнения: он доказывает, что кандидат умеет посчитать то
же, но не что он умеет вернуть управление. Матрица доказывает второе — юнит опубликован в движке,
выведен через один класс выхода за раз, и гость затем доходит в baseline до той же точки захвата.

Здесь сравниваются **все восемь регистров** и ленивый кортеж, потому что оба арма стартуют из
одного состояния драйвера. Это и есть разница с изолированным дифференциалом, где пять регистров
честно помечены UNCOMPARED.

```
PASS  boundary-exit   все регионы, регистры, кортеж и счётчик идентичны
PASS  fault-exit      pf-absent-src / pf-absent-dst / pf-readonly-dst / mapping-change-src
PASS  budget-exit     граница снижена до 8, гость всё равно доходит до того же состояния
```

Не проверено исполнением: ветвь диспетчера для неизвестного индекса. Она достижима только из
индекса, которого движок для одновходового юнита не порождает; форму покрывает верификатор
(N16/B2), и это слабее, чем прогон.

### Что изменилось после измерения

`ret` в этом срезе был граничным выходом. Пока сравнивались только результаты, это выглядело
консервативно и работало; под нагрузкой оказалось, что юнит уходит по адресу на СВОЕЙ странице,
движок компилирует её сам и забирает у юнита. Теперь `ret` — настоящий терминатор, а публикация
отказывает юниту, который отдаёт управление на своей странице по адресу, которого не обслуживает.
Подробности и контроль — в отчёте о цене Arm B.

### Что нашлось только на этом этапе

Ни валидатор Wasm, ни верификатор контракта этого увидеть не могут — только исполнение и оракул:

| Дефект | Чем пойман |
|---|---|
| Юнит поднимал тело ядра, а по входу на странице лежит обёртка | `#GP` в движке |
| Медленный путь записи пропускал inline-store: хелпер **разрешает адрес**, а не пишет (N49) | чтение референса |
| Отображение `br_table` инвертировано — юнит сразу уходил в блок выхода | оракул, первое расхождение в DST3 |
| Re-dispatch писал абсолютный EIP вместо младших битов | верификатор C4/D9 |
| `flags_changed` без бита `FLAG_SUB` — v86 считал AF по формуле сложения | оракул, `eflags 0x46` против `0x56` |
| Блок с граничным `Exit` кредитовал `ret`, который исполняет baseline | оракул, счётчик разошёлся ровно на число вызовов |
| Кредит блоком вперёд завышал счётчик на отказе | матрица выходов |
| Отказавшая инструкция не кредитовалась вовсе | матрица выходов, недостача ровно в единицу |

Последние два — про то, что план §4.2 разводит явно. **Счётчик движка** следует v86, который
инкрементирует ПЕРЕД исполнением и коммитит на выходе из цикла, поэтому отказавший доступ
посчитан. **Ledger логической работы** сообщает только завершённое, поэтому не посчитан. Одно
число на оба — это дрейф на единицу за каждый отказ, и он был.

Кредит поэтому отложенный: перед каждой отказоспособной инструкцией кредитуется всё, что уже
исполнилось, плюс она сама; перед терминатором — всё оставшееся, потому что кредит ПОСЛЕ него
попадает в недостижимый код и не начисляется никогда.

## 7. Что этот этап НЕ доказывает

* Ни одного утверждения о скорости. Интерпретатор — эталон семантики, а не арм производительности.
* Динамический ledger эффектов теперь именно динамический (k8: 389 операций с памятью, k3: 128),
  а не статическая граница, переписывавшая счётчик на выходе. Но `k8` не имеет независимого
  ожидания в корпусе (`expected_ledger: null`), поэтому его число пока сверяется только с ручным
  подсчётом по дизассемблеру, а не с оракулом.
* **Ни одного числа о скорости на этом этапе.** Arm B консервативен по построению: каждый доступ
  платит полную safe-memory подготовку, а все шесть флагов материализуются на каждой
  арифметической операции, даже когда их никто не читает. Измерение — отдельный шаг, и оно
  сделано отдельно: `user-mode-optimizing-translator-arm-b-cost-2026-09-05.md`.
* Уровни оракула §4.3 покрыты частично: architectural/effect equivalence — да, включая путь
  отказа (§6a); canonical continuation (baseline исполняет suffix после каждого выхода) — нет;
  representation compatibility (сырой lazy-flags кортеж, dirty masks) — нет.
