# Первый положительный результат source-pair методики: exact ror32 inline

Получен заметный локальный выигрыш **готового AOT-Wasm относительно неизменённого
shipping JIT-Wasm**. На синтетическом pixel-update ядре медиана времени уменьшилась
с 151,35 до 114,63 ms: **1,32× по пропускной способности, −24,3% времени**.
Это не сравнение с заведомо более медленным альтернативным x86-компилятором.

Оптимизация опциональная, офлайн. Глобальные настройки JIT не изменены, idx21 остаётся 0.
Ускорение настоящих игр, старых физических машин и холодного запуска не измерено.

## Откуда взялась оптимизация

В исходнике `pair_pixels` есть `carry = rol(carry, 5) + value`. MSVC выпускает
`ror eax, 27`; shipping v86 превращает его в вызов `e.ror32`. Прямой Emscripten
использует Wasm-вращение. Это указало на место проверки, но прямой Emscripten не
используется как baseline для заявления об ускорении эмулятора.

`tools/aot/lib/inline-rotate.mjs` встраивает **точное тело ror32 из текущего runtime**,
включая обновления `flags_changed` и CF/OF. Это не замена на один `i32.rotr` с
потерей x86-семантики. Тело runtime сверяется с просмотренной последовательностью
байтов; несовпадение означает отказ. Сигнатуры и привязка CPU memory проверяются.
Добавляются два локальных i32, локальные индексы helper-а перенумеровываются,
смещения `metadata.code.branch_hint` пересчитываются. Импорты, таблица, точки входа,
проверки памяти и выходы исходного модуля сохраняются.

Гипотеза объяснения: исчезает вызов между модулями, а браузерный компилятор видит
побочные эффекты helper-а вместе с окружающим кодом. Разделение этих двух источников
выигрыша машинным профилем пока не сделано.

В decoder лаборатории исправлено чтение аргументов `return_call` и
`return_call_indirect`. Старые статические отчёты, использовавшие этот decoder на
tail-call модулях, не следует считать точными; актуальные отчёты пересчитаны collector-ом.

## Измерение через штатный AOT

PE делает 8 388 608 обновлений за раунд. Инициализация, handshake ready/go и запись
результата находятся вне измеряемой фазы. Новый `logPhase` фиксирует host wall time
и число JIT-компиляций на двух гостевых маркерах, непосредственно в worker.

Один прогретый движок на режим. После захвата `AotCache.snapshot` преобразованные
байты устанавливаются через `aotArtifacts replace`, затем **штатные drop/replay**
публикуют их с исходными слотами и страницами. В каждом режиме зарегистрирован 1 unit,
отказов replay нет. Рука A использует исходную неизменённую функцию под той же AOT
регистрацией; C — функцию преобразованного replay. Импорты идентичны, JS-обёртки
для подсчёта вызовов не добавляются.

Три прогрева A, пять C, затем квартеты ABBA/BAAB. Собираются два чистых квартета,
не более шести попыток. Если внутри фазы возникла JIT-компиляция, **весь квартет**
исключается независимо от таймингов; сырые данные остаются в отчёте. Потеря владельца
страницы/функции или отсутствие входов в модуль останавливают эксперимент.

| Режим | A, ms | C, ms | A/C | Принято / исключено раундов |
|---|---:|---:|---:|---:|
| Вычисления, длинные фазы | 151,35 | 114,63 | **1,320×** | 8 / 0 |
| GetTickCount, Wasm hypercall | 148,10 | 113,64 | **1,303×** | 8 / 4 |
| GetFileAttributesA, sync JS | 1131,09 | 1086,16 | 1,041× | 8 / 4 |
| Sleep, async park/resume | 235,57 | 172,40 | 1,366× | 8 / 0 |

Каждый раунд сравнил все 1033 слова состояния с независимым oracle. Во всех 32
принятых фазах — ноль новых JIT-компиляций, положительный прирост module entries,
сохранённые функция и владелец страницы. Между режимами различаются burst и число
граничных мутаций: сравнивать нужно A/C внутри строки. Async включает ожидания и
остаётся чувствительным к планировщику; его число не заявляется как чистый CPU gain.

**Контроль с неизменёнными байтами:** тот же drop/replay и протокол, но C получает
исходный Wasm; 1,014×, что существенно меньше наблюдаемого эффекта преобразования.
Контроль запускается через `browser.html?control=identity`.

Браузер — Codex in-app Chromium, UA Chrome/152.0.0.0, Windows. Это не отдельный
прогон stock Chrome и не старое железо. Абсолютные времена на общей машине заметно
менялись между прогонами; основной вывод опирается на чередование внутри одного
прогретого движка. `performanceAccepted:false` в сырых JSON сохраняет отсутствие
приёмки для целевого браузера/железа и глобального включения оптимизации.

## Семантика и проверки

- Helper differential: все 32 маскированных счётчика; граничные и 100 случайных
  операндов; вложенные вызовы. Сравнение результата и всей 64 KiB памяти плюс
  независимые ожидаемые CF/OF/flags_changed. Проверены metadata и отказы при drift.
- Существующий архитектурный oracle **K6 CORRECT** после двух подстановок ror32:
  память, guest STATE (включая EFLAGS/регистры) и host state идентичны.
- Негативный K6 `src-first` ожидаемо дал **DIVERGENT** в SCR6. Производительность K6
  не используется: его steady-state gate не прошёл, это correctness-only запуск.
- `bun run gate`: 4345 pass, 0 fail (лог ниже).

Данные и инструменты:

- `logs/source-pair-OX3N8F/main-accepted/result.json` — основной полный прогон,
  исходные captures, AOT версии, все принятые и исключённые samples.
- `logs/source-pair-OX3N8F/identity-control.json` — контроль без изменения байтов.
- `logs/source-pair-OX3N8F/k6-oracle.json`, `k6-negative.json` — архитектурный oracle.
- `logs/source-pair-OX3N8F/quality-gate-final.log` — общий gate.
- `logs/source-pair-OX3N8F/optimized-final/index.json` — готовый оптимизированный кэш.

Офлайн-команда, повторяющая преобразование готового кэша:

```sh

```

Для этого артефакта: 51 867 → 51 933 bytes, один inlined site. SHA-256 результата
`bf076ad2d85dd28e6918e17eb7c08e003ad2bd4aad99bbc902ff7bc275fc435b` **побайтно совпал
с кандидатом, исполнявшимся в измерении**. Engine SHA-256:
`9aa38d8bf99d9b6d8c8371605c9d2070edaeb6af28de8e9d6f07ae86210af276`.
CLI сохраняет полную версию кэша, включая RAM base, fingerprint, слоты и хэши страниц.
Он также принимает capture manifests существующего AOT oracle. Кэши с relocations
этот проход не поддерживает.

## Что это доказывает для методики

Поиск через C++ → PE → JIT-Wasm против C++ → Emscripten дал полезный локальный паттерн,
который можно перенести в готовый Wasm с сохранением обязательств эмулятора.
Частые JS-границы почти скрыли выигрыш, поэтому профиль границ действительно нужен.
Следующий отдельный этап — измерить частоту этого паттерна в реальных горячих модулях
и проверить перенос эффекта на целевые машины; текущий результат не обещает +30% FPS.

## Продолжение: проверка применимости к игровому корпусу

`tools/bench-v86/helper-census.mjs` пересчитывает статические вызовы из hash-verified
Wasm и сопоставляет CDP self samples с тем же script ID/hash. Прямое время helper-а
считается только для подтверждённого runtime script. Сэмплы модуля, содержащего
вызов, отдельно обозначены как **покрытие**, а не стоимость helper-а.

На историческом `logs/nfsu-jit-warm-content-20260905` разобраны 125 JIT-модулей;
сам многопроцедурный runtime исключён. `ror32` отсутствует. `rol32` встречается
четыре раза в трёх модулях; прямые self samples — 9,283 ms из 10 093,976 ms
суммарного профиля (~0,092%). Это не учитывает call barriers и вторичные оптимизации,
но оснований переносить синтетические 1,3× на всю NFSU не даёт. Корпус относится к
старому runtime `3a50af7f…`, а не к текущему `9aa38d8b…`; старые модули не публиковались
в текущий движок. Результат: `logs/source-pair-OX3N8F/nfsu-helper-census.json`.

Добавлено точное встраивание родственного `rol32`, с независимыми формулами CF/OF
и сравнением всей памяти для всех маскированных счётчиков. Опция CLI `--both`
включает оба вращения, прежний default остаётся только `ror32`, чтобы сохранить
воспроизводимость основного эксперимента. Новый K6-кандидат содержит пять замен
(два ror32 и три rol32), архитектурный oracle — CORRECT, `src-first` — ожидаемо
DIVERGENT. Производительность расширенного прохода пока не принята.

```sh
node tools/aot/optimize-cache.mjs <capture.json> public/v86.wasm <new-output-dir> --both
node tools/bench-v86/helper-census.mjs logs/nfsu-jit-warm-content-20260905
```

Это продолжение **не закрывает цель широкого значимого ускорения AOT**: пока доказан
локальный выигрыш первого паттерна. Для дальнейшего выбора есть профиль расходов
helper-ов (включая SHUFPS и арифметику SSE), но он не заменяет причинного эксперимента
и актуального захвата реальной нагрузки.

### Следующий кандидат: специализация SHUFPS

В трёх исторических модулях NFSU найдены 21 вызов `instr_0FC6`; непосредственно
перед каждым стоят три константы: SSE scratch 1136, номер XMM и imm8.
Маски — преимущественно 0, также 64 и 228. У текущего helper-а переменная индексация
lane и временный spill v128 на host stack, хотя аргументы JIT-вызова уже известны.

`tools/aot/lib/shufps-specialize.mjs` — **семантический прототип**, ещё не проход
переписывания AOT. Он генерирует scalar i32 загрузки выбранных четырёх lane и записи
результата. Сохраняется запись `fpu_simd_dirty = 1` по адресу 632; исходная проверка
всей памяти обнаружила её отсутствие и была исправлена именно реализация.
Источник ограничен штатным non-aliasing scratch 1136: ABI исходного helper-а
не допускает прямой alias source/destination (JIT предварительно копирует источник).

Дифференциальный тест исполняет точное извлечённое тело текущего runtime с памятью
и stack global против кандидата: 256 масок × 8 регистров, битовые NaN/нули/inf/
денормалы. Независимая lane-модель проверяет результат. Вся память совпадает за
исключением 16 байт внутреннего compiler spill по `sp-16`; CPU scratch, flags и
dirty-состояние сравниваются. Обработка guest memory, CR0/OSFXSR и fault exits
не входит в этот isolated helper test и должна остаться в вызывающем JIT-коде.

Далее требуется реальное AOT-переписывание с сохранением metadata и его causal A/B;
производительность прототипа и выигрыш игры ещё не доказаны.

### SHUFPS: реализован проход и проверен AOT replay

Последующее состояние: `specializeShufpsCalls` заменяет вызовы с тремя константами
в настоящем JIT-Wasm. Общее переписывание локальных переменных и branch hints вынесено
в `rewriteHelperCalls`, которым пользуются и вращения. Декодер дополнен v128.load/store
с явным отказом для остальных SIMD opcode. Тело текущего SHUFPS привязано к проверенному
SHA-256; другой helper означает отказ, а не предположение о неизменности ABI.

Тест 256 × 8 теперь исполняет **переписанный вызывающий модуль**, а не только готовое
тело специализации; вызов исходного helper-а в руке C вызывает ошибку теста. Проверка
runtime вынесена в фабрику `createShufpsSpecializer`, выполняемую один раз на кэш.
До этого повторная проверка 2048 раз вызвала timeout общего теста; после исправления
тот же полный тест проходит в Bun примерно за секунду без увеличения timeout.

`tools/bench-v86/shufps-aot-paired.mjs` использует существующий fixed-work v86 стенд.
Новый SIMD-цикл делает восемь SHUFPS за итерацию, перемежая их с проверками CF через
ADC. Это синтетическая пара обратных перестановок, не запись работы NFSU; её финальное
состояние само по себе могло бы пропустить удаление обеих перестановок, поэтому
обязателен независимый тест каждой маски выше. До измерения очищается JIT-кэш, кандидат
публикуется **существующим `publishUnit` через AOT transaction**, с хэшами страниц,
исходным слотом и без JS-обёртки счётчика. Оригинал и кандидат чередуются ABBA/BAAB
под одной регистрацией. Проверяются владение функцией/страницей, результаты, retired
instructions, число входов и отсутствие компиляции внутри интервала.

Node causal probe после AOT replay: **92,47 → 81,62 ms, 1,133×**.
Каждая рука исполнила 46 000 016 x86-инструкций и вошла в JIT-модули 460 раз.
Контроль неизменённых байтов через тот же replay: **0,9995×**.
Это свидетельство локального эффекта прохода, **не браузерная/игровая приёмка**.

Артефакты:

- `logs/source-pair-OX3N8F/shufps-aot-replay.json` — основной AOT probe.
- `logs/source-pair-OX3N8F/shufps-aot-replay-identity.json` — контроль.
- `logs/source-pair-OX3N8F/shufps-replay-cache/` — исходный и преобразованный кэши
  отдельного повторного прогона (`shufps-aot-replay-saved.json`).
- `logs/source-pair-OX3N8F/shufps-cli-cache/` — результат отдельного CLI-прохода:
  побайтно совпал с соответствующим исполнявшимся кандидатом.

```sh
node tools/bench-v86/shufps-aot-paired.mjs
node tools/bench-v86/shufps-aot-paired.mjs --identity
node tools/aot/optimize-cache.mjs <index.json> public/v86.wasm <new-output-dir> --shufps
```

По-прежнему не измерен суммарный эффект на реальной игре. Следующий шаг — актуальный
игровой либо source-paired SIMD browser-прогон с характерными масками/границами,
после которого можно решать, стоит ли расширять этот проход на другие SSE helper-ы.

### SHUFPS в браузере: полезный broadcast/add вместо только обратных перестановок

Node и browser Worker теперь запускают один `shufps-aot-paired.mjs`, один workload
и один AOT loader. В браузере хэшируется именно буфер, переданный WebAssembly.compile;
полученный Module явно передаётся V86 через `wasm_fn`. Offline endpoint обязан вернуть
совпадающие engine/input/output SHA. Подготовка/трансформация не входят в тайминг.

Добавлен `flags-sse-broadcast`: SHUFPS imm=0 (маска, преобладавшая в историческом
игровом корпусе), затем ADDPS с [1,2,3,4], четыре раза за итерацию. SHUFPS влияет
на последующее накопление. После N итераций ожидаются float32 lane
[4N,4N+1,4N+2,4N+3]; выбранный размер N=2 000 000 остаётся в точном целочисленном
диапазоне float32. CF проверяется через ADC между SIMD-операциями.

Каждый браузерный sample — сумма четырёх отдельных проверенных fixed-work batches;
каждый batch заново инициализирует цикл. Все samples сохраняются, выбросы не отбрасываются.
Последовательность fresh workers: identity, candidate, candidate, identity, для каждого
из двух workload. Внутри worker — прежний ABBA/BAAB. Это лабораторный CPU worker,
не полноценный WinAPI/рендеринг сценарий и не source-paired PE demo.

В `logs/source-pair-nQJiXP/shufps-browser/result.json` для **broadcast/add**:

| Прогон | A, ms (4 batches) | C, ms | A/C |
|---|---:|---:|---:|
| Identity до | 387,93 | 383,35 | 1,012× |
| Кандидат 1 | 406,50 | 290,88 | **1,397×** |
| Кандидат 2 | 403,35 | 294,37 | **1,370×** |
| Identity после | 379,77 | 388,81 | 0,977× |

Оба контроля укладываются в ±3%; оба кандидата превышают 1,10×. Пройдены состояние,
объём работы, отсутствие JIT-компиляций в интервале и владение AOT-модулем. Для reverse
lanes один контроль дал 0,955×, поэтому **его браузерный speedup не принимается**.
Следующие запуски UI записывают эти два независимых verdict в `acceptance`.
Первый короткий браузерный запуск (до увеличения batches) имел шум контроля до 9%
и не используется как performance acceptance.

Негативный `--broadcast --mutation-skip` удаляет SHUFPS при сохранении прочего кода.
Первый запуск остановился на ошибке подготовки AOT, поэтому не был доказательством
чувствительности. Найдена и исправлена гонка: pending JIT compilation могла опубликоваться
во время await offline transform. Владение перепроверяется после await и после hashing.
Повторный `shufps-broadcast-negative-v2.json` успешно публикует AOT, затем падает на
**absolute work/result mismatch** с неправильными SIMD lane — правильный негативный контроль.

Итог: есть измеренный значимый выигрыш на характерной SIMD-операции в браузере.
Его доля в игровом времени, поведение на старом железе и суммарный FPS по-прежнему
не проверены. Широкая цель не закрыта этим лабораторным результатом.

### Контроль уровня компиляции V8

Проверен вопрос, не объясняется ли выигрыш разным прогревом базового Liftoff.
Установленный Node 22.14.0 / V8 12.4.254.21-node.22 поддерживает `--no-liftoff`:
в этом режиме Wasm сразу компилируется оптимизирующим компилятором. В JSON стенда
теперь сохраняются V8 version, execArgv, NODE_OPTIONS и путь исполняемого Node.
Это контроль конкретного установленного V8, не подтверждение уровня компиляции IAB.

Последовательные отдельные процессы, broadcast workload, тот же AOT replay и ABBA/BAAB:

| Прогон с --no-liftoff | A, ms | C, ms | A/C |
|---|---:|---:|---:|
| Identity до | 72,4182 | 71,73555 | 1,0095× |
| Кандидат 1 | 72,33495 | 60,85755 | **1,1886×** |
| Кандидат 2 | 71,9752 | 60,76735 | **1,1844×** |
| Identity после | 71,40385 | 71,28225 | 1,0017× |

Все четыре отчёта status=ok: состояние, объём работы, владение AOT и отсутствие
гостевых JIT-компиляций прошли проверки. Артефакты:
`logs/source-pair-nQJiXP/optimized-only-{control-before,candidate-1,candidate-2,control-after}.json`.
Предварительная пара `shufps-broadcast-optimized-only*.json` также сохранена,
но ещё без встроенного hostCompiler provenance.

Дополнительный одиночный probe с `--no-liftoff --experimental-wasm-inlining`
дал 71,5700 → 61,33365 ms (**1,1669×**), identity 0,9992×;
`optimized-inlining-{candidate,control}.json` в том же каталоге.
В этой версии Node экспериментальный Wasm inlining выключен по умолчанию.
Его включение не устранило эффект; это не доказательство того, какие именно вызовы
были встроены — для такого вывода нужна трасса/дизассемблирование.

Следствие: эффект SHUFPS-прохода не сводится к сравнению Liftoff с оптимизированным
кодом в этом V8. Обобщать 18% на нынешний браузер, старые машины или FPS игры нельзя.
Игровой сценарий всё ещё требуется. При его подготовке выяснено, что новый iframe
не изолирует сохранения: emulator.worker.ts выбирает OPFS overlay по gameId манифеста.
Следовательно, для игрового стенда нужна отдельная origin или отдельная идентичность
тестового контейнера, а не только новый iframe.

### Неподвижная сцена: значимого выигрыша нет

Пользователь подготовил неподвижную машину/камеру и сообщил «готово». На исходном
OPFS-кэше повторён A/C replay без перезапуска между измеряемыми руками.
`logs/source-pair-qHo4rj/game-paired/stationary-main.json`: восемь проверенных
интервалов, медианы **A 28,3191 FPS, C 28,2080 FPS**, C/A **0,99607**.
Оба целевых модуля исполняются: idx722 примерно 19–21 тыс. входов/интервал,
idx807 примерно 488–494 тыс. входов/интервал. Это всё ещё не счётчики самих helper sites.

Затем проведён C/C контроль на той же сессии с одинаковыми байтами обеих рук:
`stationary-control-cc.json`, медианы **27,1655 / 27,0009 FPS**, отношение **0,99394**.
Контрольный payload сохранён как `control-candidate-equal.json`: original==candidate
и inputSha256==outputSha256 для обоих модулей. Поле `identity` в JSON стенда остаётся
false, поскольку оно отражает URL query, а не равенство байтов payload; контроль
здесь устанавливается именно сохранёнными байтами. Такой payload нужен потому,
что после первого replay массив AotCache уже содержит C, и replace проверяет его SHA.

Все интервалы обоих прогонов прошли проверки, но межинтервальный разброс контроля
шире основного прогона. Нельзя заявлять точную регрессию в 0,4%; значимый прирост
FPS **не обнаружен**. Нельзя распространять этот отрицательный результат на все
оптимизации Wasm AOT или отменять локальный выигрыш синтетических тестов.
Сводка и исходные FPS — `stationary-assessment.json`.

Текущая сессия оставлена на паузе после C/C контроля; в её оперативном AotCache
и целевых слотах C. OPFS по-прежнему хранит исходный кэш. Публичный payload пока
тоже C/C; перед новым экспериментом необходимо явно выбрать согласованные входные
байты (replace проверяет текущий input SHA), а не повторять исходный A→C payload.
Нужны замер доли целевых операций и следующий проход для реального горячего кода.
